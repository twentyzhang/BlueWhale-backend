# 热点数据识别（Redis 缓存候选）

> 路线图任务 3 的识别分析。**已落地实现**（手写 `CacheUtil.getOrLoad` + `RedisUtil.deleteByPrefix`，非 Spring Cache 注解）。
> 三个待定项的最终决定：商品详情库存取**方案 1（短 TTL）**、优惠券组列表与商品搜索**不缓存**。
> 实现见 `实现说明.md`「热点读缓存」、取舍见 `重要决策说明.md` 第 47 条。

## 识别准则

1. **读多写少**：被频繁读取、很少变更。
2. **无需实时一致性**：可容忍短暂延迟。
3. **查询/计算成本较高**：多表关联、聚合、或应用层递归/组装。

三条同时满足度越高，缓存收益越大。

## ✅ 推荐缓存（按优先级）

| 优先级 | 对象            | 接口 / 方法                                                                        | 读多写少        | 弱一致可接受                | 查询成本                                    | 说明                                                  |
| ------ | --------------- | ---------------------------------------------------------------------------------- | --------------- | --------------------------- | ------------------------------------------- | ----------------------------------------------------- |
| P0     | 商品分类树      | `GET /api/categories` · `ProductCategoryServiceImpl.getCategoryTree`          | ✔ 极少变更     | ✔                          | ✔ 全表 `selectList` + Java 递归组装树    | 最佳候选：近乎静态、每次都全量查+递归                 |
| P0     | 商店列表 / 详情 | `GET /api/stores`、`GET /api/stores/{id}` · `getStoreList`/`getStoreById` | ✔ 商店信息稳定 | ✔                          | 中（分页/单查）                             | 浏览入口高频、内容稳定                                |
| P1     | 商品详情        | `GET /api/products/{id}` · `getProductDetail`                                 | ✔ 商品属性稳定 | ⚠**见下方库存注意**  | ✔ 关联分类 + 聚合评分(avg/count)           | 评分聚合较贵；**stock 字段会随下单频繁变化**    |
| P1     | 商品评论列表    | `GET /api/products/{id}/reviews` · `getProductReviews`                        | ✔ 只增、很少删 | ✔                          | ✔ 分页 + 批量查回复 + 批量查用户名         | 多次查询组装，分页缓存                                |
| P1     | 订单报表        | `GET /api/stores/{id}/reports/orders`、`GET /api/admin/reports/orders`         | ✔ 偶尔查看     | ✔ 分析数据，容忍分钟级延迟 | ✔✔`GROUP BY`/`SUM`/跨表 `JOIN` 聚合 | 成本最高、最容忍延迟，**短 TTL 纯时间失效即可** |

### 缓存键 / TTL / 失效触发（初版建议，可调）

| 对象     | 缓存键（建议）                                                             | 建议 TTL                | 失效触发                                                     |
| -------- | -------------------------------------------------------------------------- | ----------------------- | ------------------------------------------------------------ |
| 分类树   | `category:tree`（单键，全局唯一）                                        | 1 小时                  | `createCategory` / `deleteCategory` 后清除               |
| 商店详情 | `store:detail:{storeId}`                                                 | 30 分钟                 | `updateStore` 清该 key                                     |
| 商店列表 | `store:list:{page}:{size}`                                               | 10 分钟                 | `createStore`/`updateStore` 清前缀                       |
| 商品详情 | `product:detail:{productId}`                                             | 5~10 分钟（短，因库存） | `updateProduct`/`updateStock`/`deleteProduct` 清该 key |
| 商品评论 | `product:reviews:{productId}:{page}:{size}`                              | 10 分钟                 | `createReview`/`replyToReview` 清该商品前缀              |
| 订单报表 | `report:store:{storeId}:{start}:{end}` / `report:global:{start}:{end}` | 5 分钟（纯 TTL）        | 不主动清，靠 TTL 自然过期                                    |

## ⚠ 需要讨论的注意点

- **商品详情的 `stock`**：库存随每次下单/取消/补货变化（高频写），与"读多写少"冲突。三种处理方案，待定：   选择方案1
  1. 缓存商品详情但 **TTL 短**（如 5 分钟），接受库存短暂不准（前端下单时以服务端实时校验为准，本就有 `stock >= q` 守卫兜底）；
  2. 缓存详情时 **剔除 stock**，库存单独实时查（拆分冷热字段）；
  3. 在 `updateStock` 及下单扣减处主动清除该商品缓存（清除频繁，收益打折）。
     → 倾向方案 1（实现简单，且超卖已由 DB 守卫兜底，库存展示延迟可接受）。
- **优惠券组列表 `GET /api/coupon-groups`（`getAvailableCouponGroups`）**：列表本身变化慢，但响应含 `remainCount`，活动期高频变化。若缓存会出现"显示可领、点了已抢完"。**暂不缓存**，或仅缓存极短 TTL（30~60s）并接受该体验落差。待定。           不缓存
- **商品搜索 / 门店商品列表（`searchProducts`/`listStoreProducts`）**：含 keyword/分类/价格区间/分页等多维参数，**缓存键组合爆炸、命中率低**，且结果含 stock。**暂不缓存**；如需，仅对"无关键词的默认列表首页"缓存。待定。   不缓存

## ❌ 明确不缓存（个性化 / 高频变动 / 复用低）

| 对象                | 接口                                      | 原因                                                         |
| ------------------- | ----------------------------------------- | ------------------------------------------------------------ |
| 购物车              | `GET /api/cart`                         | 用户私有、频繁增删改，跨用户零复用                           |
| 我的订单 / 订单详情 | `GET /api/orders`、`/api/orders/{id}` | 用户私有、状态频繁流转，强一致需求                           |
| 我的优惠券          | `GET /api/coupons/mine`                 | 用户私有、领取/核销即变                                      |
| 收货地址            | `GET /api/addresses`                    | 用户私有、写后需立即可见                                     |
| Admin 商店列表      | `GET /api/admin/stores`                 | 后台低频访问，缓存收益小（含 creditCode 敏感字段，避免缓存） |

## 后续实现要点（任务 3 落地时）

- 现有 `RedisConfig` 是 `StringRedisTemplate`，Spring Cache 需另配一个 **`RedisCacheManager`**（JSON 序列化 value、统一 key 前缀、按 cacheName 配差异化 TTL）。
- `@EnableCaching`；读方法标 `@Cacheable`，对应写方法标 `@CacheEvict`（务必保证**写操作必清缓存**，否则脏读）。
- 缓存 value 为 DTO（Response 对象），注意可序列化。
- 防穿透/雪崩（空结果是否缓存、TTL 加随机抖动）按需在实现阶段评估。
