# 生产化部署与可观测性设计

> 日期：2026-07-06
> 范围：准生产部署版（Docker Compose + 可观测闭环），不包含云服务器上线、域名、HTTPS、Nginx 或前端项目编排。

## 1. 背景

BlueWhale 后端业务模块已完成，现有能力包括 MySQL、Redis、Qdrant、Actuator、Micrometer、Prometheus 指标、AI 语义搜索、RAG 与 Agent。当前缺口不是业务功能，而是缺少一套可重复启动、可演示、可排障的准生产运行形态。

本轮目标是把项目从“本机手动起依赖 + Maven 启动”推进到“Docker Compose 一键启动完整后端栈，并能通过 Prometheus/Grafana/日志完成基础观测”。

## 2. 目标

1. 一键启动后端依赖栈：MySQL、Redis、Qdrant、BlueWhale app、Prometheus、Grafana。
2. 应用配置可通过环境变量覆盖，避免把数据库密码、JWT 密钥、AI key、metrics token 写死。
3. Prometheus 可以稳定抓取 `/actuator/prometheus`，不依赖会过期的 ADMIN JWT。
4. Grafana 自动加载 BlueWhale 概览 dashboard，展示 JVM、HTTP、AI 关键指标。
5. 每个 HTTP 请求都有 `X-Request-Id`，日志中可按 requestId 定位请求链路。
6. 文档说明本地启动、验证、排障与常见环境问题。

## 3. 非目标

1. 不做云服务器上线、域名、HTTPS、Nginx、证书自动续期。
2. 不把另一个前端项目纳入本仓库 Compose 编排。
3. 不引入 ELK、Loki、Tempo、OpenTelemetry 等更重的观测栈。
4. 不改 AI 业务逻辑、不新增 Agent/RAG 功能。
5. 不开放 Actuator 敏感端点，仅继续暴露 `health` 与 `prometheus`。

## 4. 总体方案

采用“准生产本地编排 + 轻量后端观测增强”方案：

- 根目录新增多阶段 `Dockerfile`，构建阶段用 Maven 产出 jar，运行阶段用 JRE 镜像启动应用。
- 根目录新增 `docker-compose.yml` 和 `.env.example`，统一描述依赖服务、端口、持久化卷、健康检查与应用环境变量。
- `deploy/prometheus/prometheus.yml` 配置 Prometheus 抓取 BlueWhale app 的 `/actuator/prometheus`，请求头使用固定 `X-Metrics-Token`。
- `deploy/grafana/provisioning/**` 和 dashboard JSON 让 Grafana 首次启动自动加载 Prometheus 数据源和 BlueWhale 概览面板。
- 后端新增 `MetricsTokenFilter` 支持机器密钥访问 `/actuator/prometheus`，同时保留现有 ADMIN JWT 访问路径。
- 后端新增 `RequestTraceFilter` 生成或透传 `X-Request-Id`，写入 MDC 并回传响应头，日志 pattern 输出 requestId。

## 5. 部署编排设计

### 5.1 Compose 服务

`docker-compose.yml` 包含以下服务：

| 服务 | 镜像/来源 | 说明 |
|---|---|---|
| `mysql` | `mysql:8` | 主数据库，挂载命名卷，初始化库 `bluewhale` |
| `redis` | `redis:7-alpine` | 缓存、锁、refreshToken、在线状态、限流 |
| `qdrant` | `qdrant/qdrant` | 商品向量库，挂载命名卷 |
| `bluewhale-app` | 本仓库 `Dockerfile` | Spring Boot 应用 |
| `prometheus` | `prom/prometheus` | 抓取应用指标 |
| `grafana` | `grafana/grafana` | 指标看板 |

### 5.2 端口

默认端口：

| 服务 | 宿主机端口 |
|---|---|
| BlueWhale app | `8080` |
| MySQL | `3305` |
| Redis | `6379` |
| Qdrant REST | `6333` |
| Qdrant gRPC | `6334` |
| Prometheus | `9090` |
| Grafana | `3000` |

所有关键端口允许通过 `.env` 覆盖，避免与本机已有服务冲突。

### 5.3 健康检查

Compose healthcheck：

- app：`GET /actuator/health`
- MySQL：`mysqladmin ping`
- Redis：`redis-cli ping`
- Qdrant：REST health 或 collection endpoint 探测
- Prometheus/Grafana：各自 HTTP health endpoint

`bluewhale-app` 通过 `depends_on.condition: service_healthy` 等待 MySQL、Redis、Qdrant 基础服务就绪。应用仍要保留对 Qdrant 不可用的降级能力，不能把向量库健康检查设计成业务强依赖。

## 6. 配置设计

### 6.1 `.env.example`

提供示例变量：

- MySQL：`MYSQL_ROOT_PASSWORD`、`MYSQL_DATABASE`、`SPRING_DATASOURCE_URL`、`SPRING_DATASOURCE_USERNAME`、`SPRING_DATASOURCE_PASSWORD`
- Redis：`REDIS_HOST`、`REDIS_PORT`、`REDIS_PASSWORD`
- Qdrant：`QDRANT_URL`、`QDRANT_COLLECTION`
- AI：`DASHSCOPE_API_KEY`、`QWEN_MODEL`
- 安全：`JWT_SECRET`、`PAYMENT_MOCK_SECRET`、`MANAGEMENT_METRICS_TOKEN`
- Grafana：`GRAFANA_ADMIN_USER`、`GRAFANA_ADMIN_PASSWORD`

`.env.example` 不包含真实密钥。`.env` 应由用户本地复制生成，并在 `.gitignore` 中保持忽略。

### 6.2 `application.yml`

补齐 datasource 相关环境变量覆盖：

- `spring.datasource.url: ${SPRING_DATASOURCE_URL:jdbc:mysql://localhost:3305/bluewhale?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&useSSL=false&allowPublicKeyRetrieval=true}`
- `spring.datasource.username: ${SPRING_DATASOURCE_USERNAME:root}`
- `spring.datasource.password: ${SPRING_DATASOURCE_PASSWORD:123456}`

新增 metrics token 配置：

```yaml
management:
  metrics-token: ${MANAGEMENT_METRICS_TOKEN:}
```

当 `MANAGEMENT_METRICS_TOKEN` 为空时，metrics token 访问不生效，只保留现有 ADMIN JWT 鉴权。

## 7. Metrics 专用密钥设计

### 7.1 目标

Prometheus 需要长期稳定抓取 `/actuator/prometheus`。现有设计要求 `hasAuthority("ADMIN")`，如果直接使用 ADMIN JWT，token 会随 access token 过期而失效，不适合机器间抓取。

### 7.2 方案

新增 `MetricsTokenFilter`：

1. 仅匹配 `/actuator/prometheus`。
2. 读取请求头 `X-Metrics-Token`。
3. 如果配置的 `management.metrics-token` 非空，且请求头与配置值完全一致，则写入一个内部认证对象，authority 为 `ADMIN`。
4. 如果 token 缺失或不匹配，不直接放行，继续走后续 Spring Security 鉴权。

这样保留两条访问路径：

- Prometheus：`X-Metrics-Token: <固定机器密钥>`
- 管理员/人工调试：`Authorization: Bearer <ADMIN JWT>`

### 7.3 安全边界

- 只作用于 `/actuator/prometheus`，不影响 `/actuator/health` 或其他接口。
- token 为空时禁用该能力，避免默认开放。
- 不新增 `/actuator/env`、`/actuator/beans` 等敏感端点。
- token 作为机器密钥写在 `.env`，不提交真实值。

## 8. 请求追踪日志设计

新增 `RequestTraceFilter`：

1. 读取请求头 `X-Request-Id`。
2. 如果不存在或为空，生成 UUID。
3. 写入 MDC key：`requestId`。
4. 响应头返回 `X-Request-Id`。
5. 请求完成后清理 MDC，避免线程复用污染。

日志 pattern 增加 requestId，例如：

```yaml
logging:
  pattern:
    level: "%5p [requestId:%X{requestId:-}]"
```

该设计不改变业务响应结构，只增强日志可追踪性。

## 9. Grafana Dashboard

新增 BlueWhale Overview dashboard，第一版关注能稳定展示、容易讲解的指标：

- JVM：内存使用、线程数、GC pause。
- HTTP：请求量、耗时分位、错误率。
- AI：`ai.tool.invocations`、`ai.agent.rounds`、`ai.ratelimit.rejected`。
- 进程：CPU、uptime。

Dashboard 使用 Grafana provisioning 自动加载，数据源为 Compose 内的 Prometheus。

## 11. 测试策略

单元测试：

- `MetricsTokenFilterTest`
  - token 正确时写入 ADMIN authority。
  - token 缺失/错误时不伪造认证，交给现有鉴权。
  - 配置为空时禁用 metrics token。
- `RequestTraceFilterTest`
  - 无请求头时生成 requestId 并写回响应头。
  - 有请求头时透传原值。
  - filter 结束后清理 MDC。

配置/集成测试：

- 使用 MockMvc 验证 `/actuator/prometheus`：
  - `X-Metrics-Token` 正确可访问。
  - 无 token 且无 ADMIN JWT 仍拒绝。
  - `/actuator/health` 仍 permitAll。

命令验证：

- `mvn test`
- `docker compose config`
- Docker 可用时，可选执行 `docker compose up -d --build` 并检查 Prometheus targets 与 Grafana dashboard。

## 12. 验收标准

1. 从空环境复制 `.env.example` 后，可按文档启动完整后端栈。
2. 应用容器能连接 Compose 内的 MySQL、Redis、Qdrant。
3. `GET /actuator/health` 返回 UP。
4. Prometheus target 中 BlueWhale app 为 UP。
5. Grafana 自动出现 BlueWhale Overview dashboard。
6. 业务请求响应头包含 `X-Request-Id`，应用日志可看到同一 requestId。
7. `/actuator/prometheus` 支持 `X-Metrics-Token`，且无 token 时不被匿名开放。
8. 自动化测试通过。

## 13. 风险与取舍

| 风险 | 处理 |
|---|---|
| Docker 首次拉镜像/构建慢 | 文档提示首次启动耗时；实现不依赖镜像缓存 |
| MySQL 首次初始化慢导致 app 连接失败 | healthcheck + app 重启策略；Flyway 保持启动迁移 |
| metrics token 误配置为空 | token 访问禁用，Prometheus target 403；文档排障 |
| Grafana dashboard 过度复杂 | 第一版只放稳定核心指标，避免维护成本过高 |
| 本地已有端口冲突 | `.env` 支持端口覆盖，文档列出常用端口 |
