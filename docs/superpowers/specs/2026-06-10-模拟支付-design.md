## 1. 目标与范围

用「**可插拔的模拟支付网关**」复刻真实第三方支付的**异步回路**，不接真支付宝、不碰内网穿透；接口留好，将来加 `AlipayPaymentGateway` 即可平滑替换。

**核心学习点**（真接支付宝时业务回路几乎不变）：异步支付状态机、webhook 验签、幂等回调、支付流水建模、支付提供方抽象。

**不做**（YAGNI）：真支付宝 SDK / RSA / 内网穿透；网关「查单」对账接口（mock 下查表即可）；多渠道路由。

---

## 2. 关键决策（brainstorm 定稿）

| # | 决策 | 取舍 |
|---|---|---|
| D1 | **手动模拟收银台**（方案 A）：自写 `/mock-pay/{tradeNo}/success\|fail` 扮演「用户在支付宝付钱」 | 成功/失败/超时三态可主动演示；异步回路真实 |
| D2 | **真异步**回调：收银台立即返回，`TaskScheduler` 延迟 ~1.5s 再发回调 | 保住「异步状态机」精髓；前端轮询查单（真支付宝标准姿势） |
| D3 | 验签 **HMAC-SHA256**（模拟 RSA2）；幂等用**支付流水状态守卫 + 原子 UPDATE** | webhook 标准范式，复用乐观锁思路 |
| D4 | `payment` 表，**订单 1 : N 流水**；重复支付**每次新建流水** | 最简、可追溯；并发由订单侧幂等兜住 |
| D5 | `PaymentGateway` 接口（createPayment + verifyCallback）；异步走**in-process 方法调用**，`/notify` HTTP 端点作真支付宝接入缝 | 抽象可插拔；既有异步体验又留真接缝 |

## 3. 异步支付回路（成功路径全流程）

```
① 用户点「去支付」
   POST /api/orders/{id}/pay  (Customer)
   → 校验订单本人 + status=PENDING_PAYMENT
   → 生成 tradeNo，建 payment 流水(PENDING, amount=订单实付额)
   → gateway.createPayment(orderId, tradeNo, amount) 返回 payUrl
   → 返回 { tradeNo, payUrl:"/api/mock-pay/{tradeNo}", amount }
   订单仍 PENDING_PAYMENT（不在此刻置 PAID）

② 用户「在支付页付钱」（模拟）
   POST /api/mock-pay/{tradeNo}/success   (开放)
   → 立即返回「已受理」
   → TaskScheduler 延迟 ~1.5s 的任务：
       构造 PaymentNotifyRequest{tradeNo, status=SUCCESS, amount, sign=HMAC(...)}
       调 paymentService.handleNotify(notify)

③ 回调到账（与真支付宝回调同一入口）
   paymentService.handleNotify(notify)：
     1. gateway.verifyCallback(notify) 验签，不过 → 拒绝
     2. 按 tradeNo 查流水：不存在→拒绝；已终态→幂等返回
     3. 校验 amount 与流水一致（防篡改）
     4. 原子 UPDATE payment SET status=SUCCESS,paid_at=NOW() WHERE trade_no=? AND status='PENDING'
        影响 1 行 → 订单置 PAID（UPDATE ... WHERE id=? AND status='PENDING_PAYMENT'）
        影响 0 行 → 并发已处理，幂等返回

④ 前端轮询
   GET /api/payments/{tradeNo}  (Customer 本人)
   → 返回 { tradeNo, status, orderId, amount, paidAt }
   见 SUCCESS 跳成功页

失败路径：POST /mock-pay/{tradeNo}/fail → 回调 status=FAILED → 流水置 FAILED，订单保持 PENDING_PAYMENT（用户可再次发起支付）。
超时路径：用户不调收银台 → 流水保持 PENDING、订单保持 PENDING_PAYMENT → 由现有「未支付订单自动取消」定时任务收尾。

> `/api/payments/notify` HTTP 端点（开放）也调同一 `handleNotify`，供真支付宝接入或手动 curl/测试驱动。
```

## 4. 数据模型（Flyway `V6__payment.sql`）

```sql
CREATE TABLE payment (
    id          BIGINT       NOT NULL AUTO_INCREMENT,
    order_id    BIGINT       NOT NULL                COMMENT '关联订单',
    trade_no    VARCHAR(64)  NOT NULL                COMMENT '交易号（幂等键）',
    amount      DECIMAL(10,2) NOT NULL               COMMENT '支付金额（订单实付额快照）',
    status      VARCHAR(16)  NOT NULL                COMMENT 'PENDING / SUCCESS / FAILED',
    channel     VARCHAR(16)  NOT NULL                COMMENT '渠道：MOCK（未来 ALIPAY）',
    paid_at     DATETIME         NULL                COMMENT '支付成功时间',
    created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    deleted     TINYINT      NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    UNIQUE KEY uk_trade_no (trade_no),
    KEY idx_order_id (order_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='支付流水';
```

- **订单 1 : N 流水**：`order_id` 关联，一订单可多条流水。
- **`trade_no` 唯一**：幂等键，每次 `/pay` 生成（UUID 去横线）。
- `status` 三态单向 `PENDING → SUCCESS/FAILED`；`channel` 为未来渠道预留。

## 5. 接口

| 接口 | 方法/路径 | 鉴权 | 行为 |
|---|---|---|---|
| 发起支付 | `POST /api/orders/{orderId}/pay` | Customer（本人） | 建 PENDING 流水，返回 `{tradeNo, payUrl, amount}`。**⚠️破坏性变更**：不再返回 `{status:PAID}` |
| 模拟收银台-成功 | `POST /api/mock-pay/{tradeNo}/success` | 开放 | 触发延迟异步回调（SUCCESS）；立即返回已受理 |
| 模拟收银台-失败 | `POST /api/mock-pay/{tradeNo}/fail` | 开放 | 触发延迟异步回调（FAILED） |
| 支付回调 | `POST /api/payments/notify` | 开放（HMAC 验签） | webhook：验签 + 幂等 + 推进状态。真支付宝接入缝 |
| 查单 | `GET /api/payments/{tradeNo}` | Customer（本人订单） | 返回支付状态，供前端轮询 |

**安全**：`/api/payments/notify`、`/api/mock-pay/**` 加入 `SecurityConfig` 开放白名单——模拟外部网关流量，真支付宝回调不带 JWT，靠 HMAC 签名保证安全（webhook 标准）。查单与发起需登录 + 订单归属校验。

## 6. 组件结构

| 组件 | 职责 |
|---|---|
| `service/PaymentGateway`（接口） | `createPayment(orderId, tradeNo, amount)→payUrl`、`verifyCallback(notify)→bool` |
| `service/impl/MockPaymentGateway` | 实现：payUrl=`/api/mock-pay/{tradeNo}`；verify 用 HMAC |
| `util/PaymentSignUtil` | 纯函数：`sign(params)` / `verify(params, sign)`（HMAC-SHA256，密钥 `payment.mock.secret`） |
| `service/PaymentService(Impl)` | `initiatePayment` / `handleNotify`（验签+幂等+推进） / `queryPayment` / `triggerMockCallback`（延迟异步发回调） |
| `controller/PaymentController` | `POST /api/payments/notify`、`GET /api/payments/{tradeNo}` |
| `controller/MockCashierController` | `POST /api/mock-pay/{tradeNo}/success\|fail` |
| `entity/Payment` + `mapper/PaymentMapper` | 映射 `payment`；含原子推进 UPDATE 与按 tradeNo 查询 |
| `job` 复用 | 超时由现有 `OrderAutocancelJob` 收尾，无新增 |
| `config` 复用 | 异步延迟用现有/新增 `TaskScheduler`（可复用 WebSocket 心跳调度器或新建） |

**改动**：`OrderService.payOrder` 移除，`OrderController.payOrder` 改调 `paymentService.initiatePayment`；`SecurityConfig` 加开放白名单；`application.yml` 加 `payment.mock.secret` 与回调延迟配置。

**幂等关键 SQL**：
```sql
-- 流水推进（防并发重复回调）
UPDATE payment SET status=#{status}, paid_at=#{paidAt} WHERE trade_no=#{tradeNo} AND status='PENDING'
-- 订单置 PAID（仅待支付订单）
UPDATE orders SET status='PAID', paid_at=#{paidAt} WHERE id=#{orderId} AND status='PENDING_PAYMENT'
```

## 7. 错误与边界

- **验签失败** → 拒绝（400/业务码），不改任何状态。
- **未知 tradeNo** → 拒绝。
- **重复回调**（已终态）→ 幂等返回成功，不重复改单。
- **金额不一致** → 拒绝（防篡改）。
- **订单已非 PENDING_PAYMENT**（已取消/已支付）→ 订单侧原子 UPDATE 影响 0 行，流水可置 SUCCESS 但订单不动；记录日志。
- **失败回调**：流水 FAILED，订单保持 PENDING_PAYMENT，可重新发起（新流水）。
- **超时未付**：复用未支付自动取消任务。
- **异步线程无 SecurityContext**：`triggerMockCallback`/`handleNotify` 不读 SecurityContext（同 `rebuildAll`/B 教训）。

## 8. 测试策略

- **`PaymentSignUtil` 纯函数单测**：sign/verify 一致、篡改后验签失败。
- **`PaymentServiceImpl` 单测（Mockito）**：发起建流水、handleNotify 验签拒绝、幂等（终态重复回调不改单）、原子推进、金额校验、失败路径、订单已非待支付。
- **端到端集成测试**（`@SpringBootTest`，需 MySQL+Redis）：下单 → `/pay` → `/mock-pay/success` → 轮询 `/payments/{tradeNo}` 直到 SUCCESS 且订单 PAID；失败路径订单仍 PENDING_PAYMENT。
- 原 `OrderServiceTest` 的 PayOrder 用例迁移到 `PaymentServiceTest`（语义已变）。
