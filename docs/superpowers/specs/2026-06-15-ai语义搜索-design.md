# AI 语义商品搜索 — 设计文档

> 创建于 2026-06-15。本文档是「AI 应用落地」系列的**第一个**子项目设计。
> 第二个子项目 RAG 将复用此处建立的向量检索基座，另走独立 spec → plan → 实现循环。

## 目标

在现有 MySQL 关键词搜索之外，**新增一条独立的 AI 语义搜索链路**：把商品向量化存入专用向量库 Qdrant，用户查询经 embedding 后做向量相似检索（带分类/价格结构过滤下推），返回按相关性排序的商品。核心工程学习点是用 **transactional outbox** 实现「商品变更 → 向量索引」的可靠最终一致同步。

## 定位与范围

- **定位**：学习/作品展示 AI 应用范式（embedding 检索、专用向量库、可靠同步），先打通最小可演示链路，加固点列为后续可选。
- **本期范围（IN）**：
  - 通义 `text-embedding-v3`（1024 维）做 embedding。
  - Qdrant 专用向量库（Docker 单容器）存向量 + payload。
  - transactional outbox 同步商品变更到 Qdrant。
  - 新增独立接口 `GET /api/products/semantic`，语义检索 + 分类/价格 payload 过滤下推。
  - 查询失败优雅降级到现有关键词搜索。
  - Admin 全量回填 `POST /api/admin/products/reindex`。
- **明确不做（OUT，留作后续加固）**：
  - 混合检索（向量 + 关键词融合 / RRF）、rerank 重排序。
  - 替换现有 `GET /api/products` 关键词搜索（保持不动，便于对比）。
  - 深翻页（语义检索按 top-K，分页在 top-K 内切片）。
  - RAG 生成（第二个子项目，生成侧用 DeepSeek）。

## 关键技术决策

| # | 决策 | 取舍 |
|---|---|---|
| 1 | **方案 C：outbox 可靠同步**（非写穿透 / 非纯批量） | 用户指定，借此加深 outbox 学习；商品写与索引解耦，AI 基础设施不可用不影响商品写 |
| 2 | **专用向量库 Qdrant**（非 MySQL+Java cosine / 非 Redis 向量） | 学习真实向量库；单容器轻量、Java 客户端成熟、概念清爽 |
| 3 | **通义 `text-embedding-v3`（1024 维）做 embedding** | 用户熟悉通义；国内网络可达、含 embedding API |
| 4 | **生成侧 DeepSeek**（仅用于后续 RAG，本期不涉及） | 性价比高；embedding 与生成分属两家（DeepSeek 无官方 embedding） |
| 5 | **独立接口 + 结构过滤下推**（非混合 / 非替换） | 不动旧接口便于对比演示；展示 Qdrant payload 过滤能力 |
| 6 | **`EmbeddingClient` / `ProductVectorIndex` 接口抽象** | 可插拔、可测试；呼应项目既有 `PaymentGateway` 套路 |
| 7 | **查询失败降级关键词搜索** | 「AI 挂了搜索仍可用」；复用现有 `ProductService.searchProducts` |

## 架构与组件

整体形态：**MySQL 仍是商品真相源；Qdrant 是向量索引；两者用 transactional outbox 解耦。**

| 组件 | 职责 | 依赖 |
|---|---|---|
| `service/EmbeddingClient`（接口）+ `service/impl/TongyiEmbeddingClient` | 文本 → 向量（1024 维），可插拔 | 通义 DashScope API |
| `service/ProductVectorIndex`（接口）+ `service/impl/QdrantProductVectorIndex` | `upsert` / `delete` / `search`（带 payload 过滤），封装 Qdrant 客户端 | Qdrant |
| `entity/IndexOutbox` + `mapper/IndexOutboxMapper` + `db/migration/V7__index_outbox.sql` | 索引事件表（productId, op, status, retry_count, last_error） | MySQL |
| `service/impl/ProductServiceImpl`（改） | create/update/delete 时**在同一事务内**插 outbox 事件 | IndexOutboxMapper |
| `job/OutboxRelayJob`（`@Scheduled`） | 轮询 PENDING → embed + 同步 Qdrant → 标记 DONE / 重试 / FAILED | 三者 |
| `service/SemanticSearchService`（+ impl） | 查询 embed → Qdrant 检索 → 回 MySQL 批量取详情 → 复用 `ProductListItemResponse`；失败降级关键词搜索 | 上述 |
| `controller/SemanticSearchController` | `GET /api/products/semantic`（开放）；Admin `POST /api/admin/products/reindex` 全量回填 | SemanticSearchService |
| `config/QdrantConfig`、`application.yml` | Qdrant/通义/outbox 轮询参数；`SecurityConfig` 放行语义搜索 GET | — |

**呼应现有模式**：抽象接口 = `PaymentGateway`；全量回填 = `RecommendationRebuildJob`；查询降级 = 订单/缓存兜底思路。

## 数据流

### 写入路径（生产者，关键：同一事务）

```
ProductServiceImpl.createProduct / updateProduct / deleteProduct   @Transactional
  → 写 product 表（现有逻辑）
  → IndexOutboxMapper.insert({productId, op, status=PENDING})   ← 同一事务原子提交
```

- `op`：create/update → `UPSERT`；delete → `DELETE`。
- `updateStock` **不入队**（库存不影响 embedding 文本）。
- 商品写与 outbox 事件原子提交：通义/Qdrant 全挂时商品照样写成功，事件留表等补。

### 中继路径（消费者，`OutboxRelayJob` `@Scheduled(fixedDelay)`）

```
selectPending(limit N, status=PENDING ORDER BY id)
for each event:
  try:
    UPSERT → product = productMapper.selectById(productId)
             若不存在/已删 → 退化为 delete
             else: vec = embeddingClient.embed(buildText(product))   // 商品名 + 类目名（product 无描述字段，类目名经 categoryId 查 ProductCategory）
                   vectorIndex.upsert(productId, vec, payload{storeId, categoryId, price, name})
    DELETE → vectorIndex.delete(productId)
    → markDone(event.id)
  catch e:
    retry_count++ ; last_error = e.message
    若 retry_count ≥ MAX(默认 5) → markFailed   // 记日志，待人工 / reindex 修复
    否则保持 PENDING，下轮重试
```

### 状态机

```
          入队             中继成功
PENDING ───────▶ (处理中) ───────▶ DONE
   ▲                  │ 失败 & retry < MAX
   └──────────────────┘
                      │ 失败 & retry ≥ MAX
                      ▼
                   FAILED
```

### 幂等（至少一次投递下安全）

- Qdrant 以 `productId` 作 point id，`upsert` 天然幂等（重复覆盖同点，结果一致）。
- `delete` 重复无副作用。
- 中继「处理成功后、标记 DONE 前」崩溃 → 下轮重处理同一事件仍得一致结果。

### 查询路径

```
GET /api/products/semantic?q=...&categoryId=&minPrice=&maxPrice=&topK=&page=&size=   (开放)
  → SemanticSearchService.search:
      vec = embeddingClient.embed(q)
      hits = vectorIndex.search(vec, Filter{categoryId, price∈[min,max]}, topK)   // payload 过滤下推
      ids  = hits 按 score 降序的 productId
      products = productMapper.selectBatchIds(ids)，按 ids 顺序重排（保住相关性次序）
      → ProductListItemResponse（可附 score 字段，便于演示相关性）
  降级：embedding / Qdrant 抛异常 → 回退 ProductService.searchProducts（关键词），日志标记降级
```

- **过滤下推**：分类/价格作为 Qdrant payload 过滤，在向量库侧筛（非取回后过滤）。
- **分页**：语义检索按 top-K（`topK` 默认 50），分页在 top-K 内切片，不做深翻页。

### Admin 全量回填

`POST /api/admin/products/reindex`：给所有未删商品批量入队 `UPSERT` 事件，交同一中继消费。用于索引初始化 / 灾后重建，复用同一可靠通路，不走旁路。

## 错误处理

| 场景 | 处理 |
|---|---|
| 商品写时 AI/Qdrant 不可用 | 不受影响（outbox 解耦），事件留 PENDING 等补 |
| 中继处理失败 | 重试 ≤ MAX，超限置 FAILED + `last_error`，reindex 可恢复 |
| 查询时 embedding/Qdrant 失败 | 降级关键词搜索 |
| 通义返回维度/格式异常 | 校验返回维度 == collection 配置维度（1024），不符则该事件失败、记错 |

## 测试策略

- **单元（纯 Mockito）**：
  - `SemanticSearchService`：过滤条件构造、结果按 score 重排映射、异常时降级关键词搜索。
  - `OutboxRelayJob`：UPSERT/DELETE 分派、失败重试计数、超限置 FAILED、成功标记 DONE、UPSERT 遇已删商品退化为 delete。
  - `ProductServiceImpl`：create/update/delete 时确有对应 outbox 事件入队（同事务）；updateStock 不入队。
- **集成（需 Qdrant）**：Testcontainers 起 Qdrant，或不可用时 `assumeTrue` 优雅跳过（沿用支付集成测试套路）。端到端：建商品 → 跑一次中继 → 语义搜索召回该商品；删商品 → 中继 → 搜不到。
- 通义真实 API 不进自动化测试（测试中 mock `EmbeddingClient`）。

## 新增依赖与基础设施

- **Qdrant Java client**（向量库客户端）。
- **通义 DashScope**：SDK 或直接 HTTP 调 embedding 接口（实现期二选一）。
- **Qdrant 服务**：Docker 单容器，本地 `docker run` 启动。
- 配置项：Qdrant host/port/collection/dim(1024)/distance(Cosine)；通义 api-key/endpoint/model；outbox 轮询间隔、批量大小、重试上限；语义检索 topK 默认值。
