# 南鲸商城 — 下一阶段开发路线图

> 创建于 2026-06-04。来源：`requirements.md` 第 5 节「暂不实现的功能」。
> 全部业务模块（用户/商店/分类/商品/购物车/订单/地址/评论/优惠券/报表）已完成，
> 本路线图规划在此基础上逐步补齐 8 项暂缓功能，**按难度递增 + 价值**排序，不必照需求文档原顺序。

---

## 当前代码现状（影响排序的关键事实）

| 事实 | 影响 |
|---|---|
| 优惠券领取已有原子 `remain_count = remain_count - 1`，但缺 `WHERE remain_count > 0` 下限保护 | 并发下会超发（发成负数） |
| 订单库存扣减是「先读校验再 `updateById` 回写」（`OrderServiceImpl`），无并发保护 | 两单可同时通过校验导致**超卖** |
| Redis 已接入（`RedisUtil`，目前仅用于 refreshToken） | 加缓存成本低 |
| 调度器未启用（无 `@EnableScheduling`） | 定时任务需先开启 |

---

## 阶段一：低成本 / 高收益（优先）

### 任务 1 — 未支付订单自动取消（定时器）｜难度 ★☆☆☆☆
- **目标**：超时未支付订单自动置为 `CANCELLED` 并恢复库存。
- **方案**：开启 `@EnableScheduling`，新增定时任务扫描 `status=PENDING_PAYMENT` 且超时的订单，复用现有 `cancelOrder` / `restoreInventory`。超时阈值配置化（`order.auto-cancel.minutes`，演示可设短值，生产 14 天）。
- **关键文件**：`BluewhaleApplication`、新建 `task/OrderAutoCancelTask`、`OrderServiceImpl`（抽取可复用取消方法）、`application.yml`。
- **依赖**：订单模块（已完成）。自包含、风险低，适合热身。
- **文档义务**：`进度.md`；新调度模块在 `实现说明.md` 记执行流程。

### 任务 2 — 并发安全：库存 & 优惠券超发防护｜难度 ★★☆☆☆ ·【价值最高，修真实 bug】
- **目标**：堵住超卖 / 超发缺口。
- **方案**：
  - 库存：改条件更新 `UPDATE product SET stock = stock - #{q} WHERE id=#{id} AND stock >= #{q}`，按**影响行数=0**判失败抛异常。
  - 优惠券：领取原子减加 `.gt("remain_count", 0)`，影响行数 0 即「已领完」。
  - 可选升级：`product` 加 `version` 列（迁移 `V2__add_product_version.sql`）+ MyBatis Plus `OptimisticLockerInnerInterceptor` 作为通用乐观锁。
- **关键文件**：`OrderServiceImpl`、`CouponServiceImpl`、`ProductMapper`、`MybatisPlusConfig`、新迁移脚本。
- **依赖**：订单/优惠券模块（已完成）。建议紧跟任务 1。
- **文档义务**：`进度.md`；并发处理方案与（如引入）乐观锁选型 → `重要决策说明.md`；新迁移脚本遵循 `数据库迁移指南.md`。

### 任务 3 — 热点读 Redis 缓存｜难度 ★★☆☆☆
- **目标**：商品详情、分类树、商店列表等高频只读接口加缓存。
- **方案**：`@EnableCaching` + `RedisCacheManager`（现有 `RedisConfig` 为 `StringRedisTemplate`，需补 JSON 序列化的 CacheManager Bean）；`@Cacheable` 标读，`@CacheEvict` 在商品/分类写操作时失效。
- **关键文件**：`RedisConfig`、`ProductServiceImpl`、`ProductCategoryServiceImpl`、`StoreServiceImpl`。
- **依赖**：Redis（已接）。**注意缓存一致性**：写操作必须配套清缓存。
- **文档义务**：`进度.md`；缓存键设计与失效策略 → `实现说明.md`；引入 Spring Cache 抽象 → `重要决策说明.md`。

## 阶段二：中等业务复杂度

### 任务 4 — 报表导出 Excel｜难度 ★★★☆☆
- **目标**：在现有报表 JSON 接口上增加 `/reports/orders/export` 导出 xlsx。
- **方案**：引入 EasyExcel（比 Apache POI 轻），复用 `ReportService` 查询结果流式写出，权限沿用 Staff/Admin。
- **关键文件**：`pom.xml`、`ReportController` / `AdminController`、`ReportServiceImpl`。自包含。
- **文档义务**：`进度.md`；EasyExcel 选型与新依赖 → `重要决策说明.md`。

### 任务 5 — 多优惠券叠加策略｜难度 ★★★☆☆
- **目标**：下单支持多张券组合（如「满减 + 折扣」），定义叠加规则与计算顺序。
- **方案**：`CreateOrderRequest` 改收 `couponIds` 列表；订单计价处按规则校验互斥/门槛并依次计算。
- **⚠ 待拍板**：**叠加业务规则需先明确**（哪些类型可叠、计算先后、是否限张数）。
- **关键文件**：`OrderServiceImpl`（计价段）、`CreateOrderRequest`、`CouponService`。
- **依赖**：建议在任务 2 之后（涉及券核销并发）。
- **文档义务**：叠加规则 → `重要决策说明.md`；计价流程 → `实现说明.md`；接口变更 → `api-spec.md`。

## 阶段三：高复杂度 / 架构级（按需选做）

### 任务 6 — 第三方支付对接（支付宝沙箱）｜难度 ★★★★☆
- 用支付宝沙箱替换模拟支付：创建支付 → 扫码/跳转 → 异步回调 `notify` 验签后更新订单。需沙箱账号、回调验签、内网穿透。重但出彩。

### 任务 7 — 客服实时聊天｜难度 ★★★★☆
- WebSocket（STOMP）+ 消息持久化 + 在线状态。新模块、新实体，前后端都要动。

### 任务 8 — 推荐算法｜难度 ★★★★★
- 基于订单历史做 item-based 协同过滤。数据依赖强、最难，放最后。

## 推荐推进顺序

```
阶段一：任务 1 → 任务 2（最高价值）→ 任务 3
阶段二：任务 4 / 任务 5（需先定叠加规则）
阶段三：从 任务 6 / 7 / 8 中按兴趣挑一个深入
```
