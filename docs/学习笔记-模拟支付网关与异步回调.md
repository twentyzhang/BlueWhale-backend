# 学习笔记：模拟支付网关与异步回调

> 配合南鲸商城练手项目第二轮任务 D（模拟支付）的**知识沉淀**，便于复盘。
> 本文是**设计阶段**的概念梳理；最终方案见 `docs/superpowers/specs/`，实现细节后续补 `实现说明.md`。
> 核心思想：**不接真支付宝，用自己写的端点"扮演"支付宝，复刻真实的异步支付回路**——
> 学到的「异步状态机 / webhook 验签 / 幂等回调 / 支付流水建模 / 支付网关抽象」真接支付宝时几乎一行不用改。

---

## 1. 真支付宝长什么样：三个角色

```
用户浏览器  ←→  你的后端  ←→  支付宝服务器
```

买家付款的真实流程：

1. 用户点「去支付」→ 后端调**支付宝「创建支付」接口** → 支付宝返回**支付链接/二维码** + 交易号 `tradeNo`。
2. 后端把订单标记为「等待支付」（**不是已支付**），把支付链接给前端。
3. 用户跳到**支付宝的页面**扫码/输密码付钱。这一步**在支付宝那边，你的后端完全不参与**。
4. 支付成功后**支付宝主动回调你的后端**一个接口（`notify`），带「这笔 `tradeNo` 付成功了」+ **签名**（证明请求真来自支付宝、未被伪造）。
5. 后端收到回调 → **验签** → 确认是这笔单 → 订单「等待支付」→「已支付」。

> **关键点**：第 3 步（用户真正付钱）在支付宝那边、你无法控制；你只能被动等第 4 步的回调。
> 付款动作和你更新订单状态是**分离的两件事**——这就是「异步」。

---

## 2. 模拟方案（方案 A）：自己写端点「扮演」支付宝

项目里**缺的就是「支付宝服务器」这个角色**。方案 A 自己写端点来演它：

| 真支付宝的东西 | 模拟方案里对应 | 扮演谁 |
|---|---|---|
| 支付宝「创建支付」接口 | `MockPaymentGateway.createPayment()` | 支付宝 |
| 支付宝收银台页面（用户付钱处） | **模拟收银台端点** `POST /api/mock-pay/{tradeNo}/success`（或 `/fail`） | 支付宝（代替「用户在支付宝付钱」） |
| 支付宝回调你的 `notify` | `POST /api/payments/notify` | 你的后端（被回调方） |

---

## 3. 一笔成功支付完整走一遍

```
① 用户点「去支付」
   POST /api/orders/{id}/pay
   → 建支付流水(status=PENDING, tradeNo=xxx)，订单仍 PENDING_PAYMENT
   → 返回 { tradeNo:"xxx", payUrl:"/api/mock-pay/xxx" }   ← 模拟「支付链接」

② 用户「去支付页付钱」（真支付宝里是跳转支付宝；这里用端点模拟该动作）
   POST /api/mock-pay/xxx/success          ← 扮演「支付宝收银台」
   → 模拟支付宝那样，给我们自己的 notify 发一个带签名的回调

③ 回调到账（模拟「支付宝主动通知你」）
   POST /api/payments/notify { tradeNo:"xxx", status:"SUCCESS", sign:"<HMAC>" }
   → 验签 → 查幂等(这笔处理过没) → 支付流水置 SUCCESS + 订单 PENDING_PAYMENT→PAID

④ 前端怎么知道付好了？
   轮询 GET /api/payments/{tradeNo} 查状态（模拟支付宝「查单」接口），见 SUCCESS 跳成功页
```

失败演示：调 `/mock-pay/xxx/fail`。
超时演示：什么都不调，让现有「未支付订单自动取消」定时任务收尾。

---

## 4. 为什么分 `/mock-pay/.../success` 和 `/payments/notify` 两个端点？

- `/mock-pay/{tradeNo}/success` = **「用户在支付宝那边付钱」这个动作**（手动触发，代替真人付款）。
- `/payments/notify` = **「支付宝回调我们」这个接口**（真接支付宝时原样保留，由支付宝来调）。

把两者**分开**，是为了让 `/notify` 长得**和真支付宝回调一模一样**：以后换真支付宝，只需删掉 `/mock-pay`、让支付宝来调 `/notify`，而 `/notify` 里的**验签 + 幂等 + 改订单**逻辑一行不用动。这就是「**接口留好、未来可平滑替换**」——也是引入 `PaymentGateway` 接口（适配器模式 / 依赖倒置）的意义：现在 `MockPaymentGateway`，将来加个 `AlipayPaymentGateway` 替换即可，上层业务回路复用。

---

## 5. 一句话总结

> **`/pay` 只是下单意图（建流水、不付钱）；`/mock-pay/.../success` 扮演「用户在支付宝付钱」；
> `/notify` 扮演「支付宝回调我们」并真正把订单置为已支付。**

---

## 6. 这套回路真正要练的硬核点（后续设计逐个敲定）

- **异步支付状态机**：订单/流水不在 `/pay` 时同步置已支付，而是等回调确认。
- **webhook 验签**：回调验 HMAC（模拟 RSA），防伪造。
- **幂等回调**：`notify` 可能重复投递，必须靠 `tradeNo` 幂等，重复不重复扣/重复改单。
- **支付流水建模**：订单 ≠ 支付流水（一单可多次发起支付）。
- **对账兜底**：主动「查单」接口 + 超时处理（复用未支付自动取消）。
- **支付提供方抽象**：`PaymentGateway` 接口，Mock 与真实可插拔替换。

> 各点的具体取舍随 brainstorm 推进补充到本文（见下「设计决策」）。

## 7. 设计决策（brainstorm 逐步敲定）

### D1 触发方式：方案 A（手动模拟收银台端点）
自写 `/api/mock-pay/{tradeNo}/success|fail` 扮演「用户在支付宝付钱」，触发回调到 `/api/payments/notify`。详见第 2~4 节。

### D2 异步实现：真异步（延迟回调）
`/mock-pay/.../success` **立即返回「已受理」**，再**另起线程/延迟 1~2 秒**发 `/notify` 回调；前端调完后需**轮询查单**才看到 SUCCESS。
- **为什么不用同步直调**：D 的核心学习点就是「异步支付状态机」——`/pay` 后订单不立刻 PAID、要等回调。同步直调会把这个精髓抹掉，和原来的同步支付无本质区别。
- 用 Spring `@Async` + 小延迟（或 `TaskScheduler` 延迟任务）实现，不重。前端「轮询查单」也是真支付宝对接的标准姿势。

### D3 验签 + 幂等（`/notify` 处理器的两个核心）

**验签（防伪造）**：HMAC-SHA256 模拟 RSA2。
- 共享密钥 `payment.mock.secret`；对回调参数（`tradeNo` + `status` + `amount`）按固定规则拼串算 HMAC 得 `sign`。
- `/notify` 用同样规则与密钥**重算 HMAC 比对**，不一致直接拒绝（防伪造 notify 把订单刷成已支付）。
- 抽 `PaymentSignUtil.sign()/verify()` 纯函数，便于测试。

**幂等（回调重复不出错）**：真支付宝 `notify` 会重复投递，处理器必须幂等。用**支付流水状态做守卫**：
```
/notify 收到 (tradeNo, status, sign)：
  1. 验签，不过 → 拒绝
  2. 按 tradeNo 查支付流水
       不存在 → 拒绝（未知交易）
       已是终态(SUCCESS/FAILED) → 直接返回成功（幂等：已处理过，啥都不做）
  3. 流水仍 PENDING → 原子推进：
       UPDATE payment SET status=SUCCESS WHERE trade_no=? AND status='PENDING'
       影响 1 行 → 真正处理：订单置 PAID（订单侧也校验 status=PENDING_PAYMENT 才改）
       影响 0 行 → 并发回调已抢先处理，按幂等返回成功
```
- **幂等键 = `tradeNo`**（每次发起支付生成唯一交易号，`payment` 表 `trade_no` 唯一索引）。
- **状态机单向** `PENDING → SUCCESS/FAILED`，终态不可逆；重复回调命中终态即幂等返回。
- **原子 UPDATE + `WHERE status='PENDING'`** 兜并发重复回调（同库存乐观锁、会话认领套路）。

### D4 支付流水表（订单 1 : N 流水）
`payment(id, order_id, trade_no UNIQUE, amount, status[PENDING/SUCCESS/FAILED], channel='MOCK', paid_at, ...)`（迁移 V6）。
- **订单 ≠ 支付流水**：一个订单可多次发起支付（点了没付/超时再点）→ 多条流水；订单状态仍是权威，回调成功时流水 `SUCCESS` + 订单 `PAID`。
- `amount` 快照订单实付额（回调校验金额防篡改）；`channel` 为将来支付宝预留。
- **重复支付**：每次 `/pay` **新建一条流水**（方案 1），最简、可追溯；并发由订单侧「仅 PENDING_PAYMENT 才置 PAID」幂等兜住。

### D5 接口与抽象
- **端点**：`POST /orders/{id}/pay`（发起，破坏性：返回 `{tradeNo,payUrl,amount}` 而非 PAID）、`POST /mock-pay/{tradeNo}/success|fail`（模拟收银台，开放）、`POST /payments/notify`（webhook，开放靠验签）、`GET /payments/{tradeNo}`（查单，本人）。
- **`PaymentGateway` 接口**：`createPayment(orderId, tradeNo, amount)→payUrl` + `verifyCallback(notify)→bool`；`MockPaymentGateway` 实现（HMAC），将来 `AlipayPaymentGateway` 替换。查单直接读表（不进网关接口）。
- **异步落点（D2 的真异步）**：`/mock-pay/.../success` 立即返回 → `TaskScheduler` 延迟 ~1.5s → 构造签名回调 → 调 `paymentService.handleNotify(...)`；HTTP `/notify` 端点也调同一 `handleNotify`，作为真支付宝的接入缝。
- **服务划分**：新增 `PaymentService`（initiate/handleNotify/query/triggerMockCallback）；移除 `OrderService.payOrder`，`/pay` 改调 PaymentService。
