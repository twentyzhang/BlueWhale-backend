# 重要决策说明

本文件记录项目开发过程中的关键技术决策及其原因，供团队成员理解设计意图、避免反复讨论同一问题。

---

## 一、项目初始化

### 1. 添加 `mybatis-plus-jsqlparser` 依赖
**决策**：在 `pom.xml` 中除 `mybatis-plus-spring-boot3-starter` 外，额外显式声明 `mybatis-plus-jsqlparser`。

**原因**：从 MyBatis Plus **3.5.7** 起，JSqlParser 从核心包剥离为独立模块。`PaginationInnerInterceptor` 依赖 JSqlParser 做 SQL 改写，若不引入该模块，编译时会报"找不到符号 PaginationInnerInterceptor"。旧版本不需要单独引入，升级时容易踩坑。

---

### 2. 包路径统一使用全小写 `com.twentyzhang.bluewhale`
**决策**：所有包路径（entity、mapper、service 等）使用 `com.twentyzhang.bluewhale`，而非 `com.twentyzhang.BlueWhale`。

**原因**：Java 包名约定全小写（JLS 规范）；Windows 文件系统不区分大小写，但 Linux/macOS 区分，混用大小写会导致跨平台编译失败。项目初始化时目录已按全小写创建，后续所有类保持一致。

---

## 二、数据库设计

### 3. 订单表命名为 `orders` 而非 `order`
**决策**：订单表使用 `orders`，对应 Entity 类名为 `Order`，加 `@TableName("orders")`。

**原因**：`order` 是 MySQL 保留关键字（`ORDER BY` 语法），直接作为表名在部分 MySQL 版本或 SQL 模式下会报语法错误，需要反引号包裹。改名为 `orders` 可完全规避此风险，也是业界惯例。

---

### 4. 订单表冗余存储收货地址快照
**决策**：`orders` 表用 `addr_receiver_name / addr_phone / addr_province / addr_city / addr_district / addr_detail` 六个字段存下单时的地址，而非只存 `address_id` 外键。

**原因**：用户下单后可能修改或删除收货地址。如果只存外键，历史订单的地址会随用户操作而变化，导致订单信息失真。快照方案保证历史订单地址永远与下单时一致。

---

### 5. 订单条目（order_item）冗余存储商品名称和单价快照
**决策**：`order_item` 表保留 `product_name`、`unit_price`、`product_image` 字段，下单时写入当时的值。

**原因**：商品可能被修改价格、改名甚至逻辑删除，如果只存 `product_id` 并实时 JOIN 商品表，已完成订单的展示内容会随商品变更而改变。快照确保历史订单数据永远准确。

---

### 6. `product_category` 使用自关联 `parent_id` 支持嵌套分类
**决策**：分类表只有一张 `product_category`，通过 `parent_id` 指向同表父记录，`parent_id = NULL` 表示顶级分类。

**原因**：需求中明确要求"商品类型进行嵌套"（如食品 > 饮料 > 果汁）。自关联单表方案层级无限制，查询分类树只需一次 `selectList()` 后在 Service 递归组装，简单且无额外 JOIN。

---

### 7. `review` 使用自关联 `parent_id` 区分评价与回复
**决策**：评论表通过 `parent_id` 自关联：`parent_id = NULL` 为一级评价（有 `rating` 字段），`parent_id` 有值为回复（`rating` 为 NULL）。

**原因**：评价和回复共用同一张表可以减少关联查询复杂度。通过 `parent_id` 判断层级，`rating` 字段仅对一级评价有意义（只有购买后才能评分，回复无需评分），业务语义清晰。

---

### 8. `orders` 表冗余 `store_id` 字段
**决策**：`orders` 表直接包含 `store_id` 字段，而非通过 `order_item → product → store` 链路推导。

**原因**：API 中 Staff 高频查询"本店订单列表"，若每次都要 `JOIN order_item JOIN product` 才能过滤商店，性能差且查询复杂。冗余一个 `store_id` 可以直接走索引，代价是下单时额外写入一次，完全可接受。

---

### 9. `coupon_group.store_id` 为 NULL 表示全局优惠券
**决策**：优惠券组表不区分"店铺券"和"全局券"两张表，统一用 `coupon_group`，`store_id = NULL` 标识全局券。

**原因**：两类券的结构完全相同（名称、类型、面值、有效期等），只是作用域不同。用单表 + `store_id` 可空的设计，避免代码和查询的重复，Service 层按 `store_id IS NULL` 或 `store_id = ?` 过滤即可。

---

### 10. 逻辑删除统一使用 `deleted` 字段
**决策**：所有需要软删除的表都添加 `deleted TINYINT DEFAULT 0`，配合 MyBatis Plus 全局逻辑删除配置。

**原因**：`application.yml` 中已配置 `logic-delete-field: deleted`，MyBatis Plus 会自动在所有 `selectList / selectPage` 等查询中追加 `WHERE deleted = 0`，无需在每条 SQL 手动过滤。`cart` 和 `order_item` 不需要软删除（随主记录物理删除），故不加此字段。

---

## 三、Entity 类

### 11. `createTime` / `updateTime` 字段名配合显式 `@TableField(value=...)`
**决策**：Entity 字段统一命名为 `createTime` / `updateTime`，并用 `@TableField(value = "created_at", fill = FieldFill.INSERT)` 显式指定列名。

**原因**：`application.yml` 开启了 `map-underscore-to-camel-case: true`，`created_at` 会自动映射为 `createdAt`，而不是 `createTime`。字段名不符时必须显式声明 `value`，否则 MyBatis Plus 找不到对应列。选择 `createTime` 命名是按照团队约定统一风格。

---

### 12. `Coupon.createTime` 复用 `claimed_at` 列
**决策**：`Coupon` 实体的 `createTime` 字段用 `@TableField(value = "claimed_at", fill = FieldFill.INSERT)` 映射，不新增 `created_at` 列。

**原因**：`coupon` 表语义上"领取时间"就是"创建时间"，两者值完全相同。复用 `claimed_at` 避免表结构冗余，同时保持与其他实体 `createTime` 字段的命名一致性，Service 层无感知差异。

---

### 13. `Coupon.updateTime` 和 `Review.updateTime` 使用 `@TableField(exist = false)`
**决策**：`coupon` 和 `review` 表无 `updated_at` 列，对应实体的 `updateTime` 字段加 `@TableField(exist = false)`。

**原因**：要求所有 Entity 都有 `updateTime` 字段以保持接口一致性，但这两张表历史上未设计 `updated_at` 列。`exist = false` 让字段存在于 Java 对象中但不参与 DB 读写，不会报"列不存在"错误。如后续需要持久化，在 schema.sql 补列并去掉注解即可。

---

### 14. `product_category` 和 `order_item` 补充了时间戳列
**决策**：在 Entity 生成后，同步在 `docs/schema.sql` 中为 `product_category` 和 `order_item` 补充了 `created_at` / `updated_at` 列。

**原因**：这两张表最初建表时未包含时间戳，但 Entity 要求所有类都有 `createTime` / `updateTime`（映射到 `created_at` / `updated_at`）。若只改 Java 代码而不改 SQL，启动时 MyBatis Plus 自动填充会报"Unknown column"错误，必须保持 Schema 与 Entity 同步。

---

## 四、Mapper 接口

### 15. 只有 `UserMapper` 和 `OrderMapper` 添加自定义方法
**决策**：12 个 Mapper 中，只为 `UserMapper` 添加 `selectByPhone`，为 `OrderMapper` 添加 3 个报表聚合方法，其余 10 个均只继承 `BaseMapper`。

**原因**：判断标准是"QueryWrapper 无法表达"：
- `selectByPhone`：`phone` 是登录核心路径，高频调用，`@Select` 内联比每次写 `wrapper` 更明确；
- 报表方法（`GROUP BY`、`SUM`、跨表 `JOIN`）：MyBatis Plus 的 QueryWrapper 不支持聚合函数和 `GROUP BY`，必须写原生 SQL；
- 其他过滤/分页（商品搜索、订单列表、优惠券列表等）：Service 层用 `LambdaQueryWrapper` 动态拼条件完全可以覆盖，不需要额外的 Mapper 方法。

---

### 16. 购物车、优惠券、评论回复均采用"二次查询 + Service 组装"而非 JOIN
**决策**：
- 购物车详情：先查 `CartItem`，再 `productMapper.selectBatchIds()` 获取商品信息，Service 组装响应 VO；
- 我的优惠券：先查 `Coupon`，再 `couponGroupMapper.selectBatchIds()` 获取组信息；
- 评论回复：先查顶级评论，再 `LambdaQueryWrapper.in(Review::getParentId, ids)` 批量查回复。

**原因**：以上场景虽然需要多表数据，但主键都是已知的 ID 集合，`selectBatchIds()` 走主键索引效率极高，两次查询总耗时通常低于一次复杂 JOIN。同时避免了在 Mapper 层定义返回混合字段的 ResultMap，Service 层组装逻辑更清晰，VO 结构变更时只改 Service 无需动 Mapper 和 XML。

---

### 17. `OrderMapper` 报表方法用 `storeId = null` 兼容店铺和全局两个报表接口
**决策**：`selectStatusBreakdown` / `selectDailyRevenue` 两个方法的 `storeId` 参数可传 `null`，SQL 中用 `#{storeId} IS NULL OR store_id = #{storeId}` 做动态过滤。

**原因**：API 中门店报表（Staff）和全局报表（Admin）的数据结构几乎相同，差别只是是否限定商店。用同一个方法复用 SQL，`storeId` 传具体值时查某店数据，传 `null` 时查全局，避免重复维护两套 SQL 逻辑。`selectStoreBreakdown` 仅全局报表使用（需要按商店分组），单独保留。
