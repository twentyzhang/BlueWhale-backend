# 重要决策说明

本文件记录项目开发过程中的关键技术决策及其原因，供团队成员理解设计意图、避免反复讨论同一问题。

---

## 零、测试策略

### 0. 单元测试使用纯 Mockito，不启动 Spring 容器
**决策**：Service 层单元测试使用 `@ExtendWith(MockitoExtension.class)` + `@InjectMocks`，不使用 `@SpringBootTest`。
**原因**：Spring 容器启动需要完整数据库和 Redis 连接，在无外部依赖的环境（CI、本地快速验证）下无法运行。纯 Mockito 测试只验证业务逻辑，速度快且无外部依赖。副作用是 `@Transactional` 不生效，事务行为需单独集成测试覆盖（当前尚未编写）。

### 0b. `ServiceImpl.baseMapper` 用 `ReflectionTestUtils` 显式注入
**决策**：所有 `XxxServiceImpl` 测试在 `@BeforeEach` 中调用 `ReflectionTestUtils.setField(service, "baseMapper", mapper)` 手动注入父类字段。
**原因**：`ServiceImpl<M, T>` 的 `baseMapper` 字段因泛型擦除，Mockito 的 `@InjectMocks` 字段注入无法匹配，导致运行时 NPE。显式注入比依赖 Mockito 反射行为更可靠。详见 `docs/debug记录.md` 第 3 条。

## 一、项目初始化

### 1. 添加 `mybatis-plus-jsqlparser` 依赖
**决策**：在 `pom.xml` 中除 `mybatis-plus-spring-boot3-starter` 外，额外显式声明 `mybatis-plus-jsqlparser`。

**原因**：从 MyBatis Plus **3.5.7** 起，JSqlParser 从核心包剥离为独立模块。`PaginationInnerInterceptor` 依赖 JSqlParser 做 SQL 改写，若不引入该模块，编译时会报"找不到符号 PaginationInnerInterceptor"。旧版本不需要单独引入，升级时容易踩坑。

---

### 2. 包路径统一使用全小写 `com.twentyzhang.bluewhale`
**决策**：所有包路径（entity、mapper、service 等）使用 `com.twentyzhang.bluewhale`，而非 `com.twentyzhang.BlueWhale`。

**原因**：Java 包名约定全小写（JLS 规范）；Windows 文件系统不区分大小写，但 Linux/macOS 区分，混用大小写会导致跨平台编译失败。项目初始化时目录已按全小写创建，后续所有类保持一致。

---

## 二、数据库设计

### 3. 订单表命名为 `orders` 而非 `order`
**决策**：订单表使用 `orders`，对应 Entity 类名为 `Order`，加 `@TableName("orders")`。

**原因**：`order` 是 MySQL 保留关键字（`ORDER BY` 语法），直接作为表名在部分 MySQL 版本或 SQL 模式下会报语法错误，需要反引号包裹。改名为 `orders` 可完全规避此风险，也是业界惯例。

---

### 4. 订单表冗余存储收货地址快照
**决策**：`orders` 表用 `addr_receiver_name / addr_phone / addr_province / addr_city / addr_district / addr_detail` 六个字段存下单时的地址，而非只存 `address_id` 外键。

**原因**：用户下单后可能修改或删除收货地址。如果只存外键，历史订单的地址会随用户操作而变化，导致订单信息失真。快照方案保证历史订单地址永远与下单时一致。

---

### 5. 订单条目（order_item）冗余存储商品名称和单价快照
**决策**：`order_item` 表保留 `product_name`、`unit_price`、`product_image` 字段，下单时写入当时的值。

**原因**：商品可能被修改价格、改名甚至逻辑删除，如果只存 `product_id` 并实时 JOIN 商品表，已完成订单的展示内容会随商品变更而改变。快照确保历史订单数据永远准确。

---

### 6. `product_category` 使用自关联 `parent_id` 支持嵌套分类
**决策**：分类表只有一张 `product_category`，通过 `parent_id` 指向同表父记录，`parent_id = NULL` 表示顶级分类。

**原因**：需求中明确要求"商品类型进行嵌套"（如食品 > 饮料 > 果汁）。自关联单表方案层级无限制，查询分类树只需一次 `selectList()` 后在 Service 递归组装，简单且无额外 JOIN。

---

### 7. `review` 使用自关联 `parent_id` 区分评价与回复
**决策**：评论表通过 `parent_id` 自关联：`parent_id = NULL` 为一级评价（有 `rating` 字段），`parent_id` 有值为回复（`rating` 为 NULL）。

**原因**：评价和回复共用同一张表可以减少关联查询复杂度。通过 `parent_id` 判断层级，`rating` 字段仅对一级评价有意义（只有购买后才能评分，回复无需评分），业务语义清晰。

---

### 8. `orders` 表冗余 `store_id` 字段
**决策**：`orders` 表直接包含 `store_id` 字段，而非通过 `order_item → product → store` 链路推导。

**原因**：API 中 Staff 高频查询"本店订单列表"，若每次都要 `JOIN order_item JOIN product` 才能过滤商店，性能差且查询复杂。冗余一个 `store_id` 可以直接走索引，代价是下单时额外写入一次，完全可接受。

---

### 9. `coupon_group.store_id` 为 NULL 表示全局优惠券
**决策**：优惠券组表不区分"店铺券"和"全局券"两张表，统一用 `coupon_group`，`store_id = NULL` 标识全局券。

**原因**：两类券的结构完全相同（名称、类型、面值、有效期等），只是作用域不同。用单表 + `store_id` 可空的设计，避免代码和查询的重复，Service 层按 `store_id IS NULL` 或 `store_id = ?` 过滤即可。

---

### 10. 逻辑删除统一使用 `deleted` 字段
**决策**：所有需要软删除的表都添加 `deleted TINYINT DEFAULT 0`，配合 MyBatis Plus 全局逻辑删除配置。

**原因**：`application.yml` 中已配置 `logic-delete-field: deleted`，MyBatis Plus 会自动在所有 `selectList / selectPage` 等查询中追加 `WHERE deleted = 0`，无需在每条 SQL 手动过滤。`cart` 和 `order_item` 不需要软删除（随主记录物理删除），故不加此字段。

---

## 三、Entity 类

### 11. `createTime` / `updateTime` 字段名配合显式 `@TableField(value=...)`
**决策**：Entity 字段统一命名为 `createTime` / `updateTime`，并用 `@TableField(value = "created_at", fill = FieldFill.INSERT)` 显式指定列名。

**原因**：`application.yml` 开启了 `map-underscore-to-camel-case: true`，`created_at` 会自动映射为 `createdAt`，而不是 `createTime`。字段名不符时必须显式声明 `value`，否则 MyBatis Plus 找不到对应列。选择 `createTime` 命名是按照团队约定统一风格。

---

### 12. `Coupon.createTime` 复用 `claimed_at` 列
**决策**：`Coupon` 实体的 `createTime` 字段用 `@TableField(value = "claimed_at", fill = FieldFill.INSERT)` 映射，不新增 `created_at` 列。

**原因**：`coupon` 表语义上"领取时间"就是"创建时间"，两者值完全相同。复用 `claimed_at` 避免表结构冗余，同时保持与其他实体 `createTime` 字段的命名一致性，Service 层无感知差异。

---

### 13. `Coupon.updateTime` 和 `Review.updateTime` 使用 `@TableField(exist = false)`
**决策**：`coupon` 和 `review` 表无 `updated_at` 列，对应实体的 `updateTime` 字段加 `@TableField(exist = false)`。

**原因**：要求所有 Entity 都有 `updateTime` 字段以保持接口一致性，但这两张表历史上未设计 `updated_at` 列。`exist = false` 让字段存在于 Java 对象中但不参与 DB 读写，不会报"列不存在"错误。如后续需要持久化，在 schema.sql 补列并去掉注解即可。

---

### 14. `product_category` 和 `order_item` 补充了时间戳列
**决策**：在 Entity 生成后，同步在 `docs/schema.sql` 中为 `product_category` 和 `order_item` 补充了 `created_at` / `updated_at` 列。

**原因**：这两张表最初建表时未包含时间戳，但 Entity 要求所有类都有 `createTime` / `updateTime`（映射到 `created_at` / `updated_at`）。若只改 Java 代码而不改 SQL，启动时 MyBatis Plus 自动填充会报"Unknown column"错误，必须保持 Schema 与 Entity 同步。

---

## 四、Mapper 接口

### 15. 只有 `UserMapper` 和 `OrderMapper` 添加自定义方法
**决策**：12 个 Mapper 中，只为 `UserMapper` 添加 `selectByPhone`，为 `OrderMapper` 添加 3 个报表聚合方法，其余 10 个均只继承 `BaseMapper`。

**原因**：判断标准是"QueryWrapper 无法表达"：
- `selectByPhone`：`phone` 是登录核心路径，高频调用，`@Select` 内联比每次写 `wrapper` 更明确；
- 报表方法（`GROUP BY`、`SUM`、跨表 `JOIN`）：MyBatis Plus 的 QueryWrapper 不支持聚合函数和 `GROUP BY`，必须写原生 SQL；
- 其他过滤/分页（商品搜索、订单列表、优惠券列表等）：Service 层用 `LambdaQueryWrapper` 动态拼条件完全可以覆盖，不需要额外的 Mapper 方法。

---

### 16. 购物车、优惠券、评论回复均采用"二次查询 + Service 组装"而非 JOIN
**决策**：
- 购物车详情：先查 `CartItem`，再 `productMapper.selectBatchIds()` 获取商品信息，Service 组装响应 VO；
- 我的优惠券：先查 `Coupon`，再 `couponGroupMapper.selectBatchIds()` 获取组信息；
- 评论回复：先查顶级评论，再 `LambdaQueryWrapper.in(Review::getParentId, ids)` 批量查回复。

**原因**：以上场景虽然需要多表数据，但主键都是已知的 ID 集合，`selectBatchIds()` 走主键索引效率极高，两次查询总耗时通常低于一次复杂 JOIN。同时避免了在 Mapper 层定义返回混合字段的 ResultMap，Service 层组装逻辑更清晰，VO 结构变更时只改 Service 无需动 Mapper 和 XML。

---

### 17. `OrderMapper` 报表方法用 `storeId = null` 兼容店铺和全局两个报表接口
**决策**：`selectStatusBreakdown` / `selectDailyRevenue` 两个方法的 `storeId` 参数可传 `null`，SQL 中用 `#{storeId} IS NULL OR store_id = #{storeId}` 做动态过滤。

**原因**：API 中门店报表（Staff）和全局报表（Admin）的数据结构几乎相同，差别只是是否限定商店。用同一个方法复用 SQL，`storeId` 传具体值时查某店数据，传 `null` 时查全局，避免重复维护两套 SQL 逻辑。`selectStoreBreakdown` 仅全局报表使用（需要按商店分组），单独保留。

---

## 五、DTO 层设计

### 18. Request DTO 加 Validation 注解，Response DTO 不加
**决策**：所有 `XxxRequest` 类在字段上加 `@NotBlank` / `@NotNull` / `@Size` / `@Pattern` 等 Jakarta Bean Validation 注解；所有 `XxxResponse` 类只使用 `@Data @Builder @NoArgsConstructor @AllArgsConstructor`，不加校验注解。

**原因**：Validation 的职责是在系统边界（Controller 入口）校验外部输入的合法性。Response 是系统向外输出的数据，由代码逻辑保证其正确性，加校验注解无意义且有误导性。在 Controller 方法参数上加 `@Valid` 触发校验，与 `@RestControllerAdvice` 配合统一返回 400 错误。

---

### 19. 更新可选字段的 Request DTO 不加 `@NotNull`
**决策**：`UpdateProductRequest`、`UpdateStoreRequest`、`UpdateAddressRequest` 等"部分更新"类的字段均不加 `@NotNull`，允许传 `null` 表示"不修改该字段"。

**原因**：编辑接口通常只传需要改动的字段（PATCH 语义）。若加 `@NotNull`，调用方必须把所有字段都传，与 API 约定不符。Service 层实现时用"字段非 null 才 set"的策略合并更新。

---

### 20. `ProductDetailResponse` 中分类信息使用嵌套 VO `ProductCategoryInfo`
**决策**：商品详情响应中，分类信息不直接平铺（如 `categoryId / categoryName / parentId / parentName`），而是封装为独立的 `ProductCategoryInfo` 类作为嵌套对象返回。

**原因**：API spec 中 `category` 是一个对象而非多个平铺字段，嵌套 VO 与 JSON 结构一一对应，序列化时不需要额外处理，也利于复用（如果未来其他 VO 也需要展示分类信息）。

---

### 21. `OrderDetailResponse` 中地址和订单条目使用嵌套 VO
**决策**：订单详情响应将地址快照封装为 `OrderAddressResponse`，将每条商品明细封装为 `OrderItemDetailResponse`，均作为嵌套字段出现在 `OrderDetailResponse` 中。

**原因**：Orders 表存储的是地址字段快照（6 个 `addr_*` 列），与 `UserAddress` 实体结构有差异，需要专属 VO 而非复用地址 VO。嵌套结构与 API spec 的 JSON 格式完全一致，减少 Controller / Service 的手动字段映射。

---

### 22. `StoreOrderReportResponse.statusBreakdown` 使用 `Map<String, Integer>`
**决策**：门店订单报表中，各状态的订单数量用 `Map<String, Integer> statusBreakdown` 表示，key 为订单状态枚举字符串。

**原因**：状态数量不固定，用 Map 比固定字段（`completedCount / cancelledCount / ...`）更灵活。当状态枚举增减时，无需修改 VO 结构。Controller 从 Mapper 的 `List<Map<String, Object>>` 聚合结果中组装该 Map 即可。

---

## 六、Controller 层设计

### 23. Controller 分 15 个类，按资源路径归组
**决策**：生成 15 个 Controller 类，不以 HTTP 方法归组，而以资源路径归组：`AuthController`、`UserController`、`StoreController`、`StoreProductController`、`ProductController`、`CategoryController`、`CartController`、`OrderController`、`StoreOrderController`、`AddressController`、`ReviewController`、`CouponGroupController`、`CouponController`、`ReportController`、`AdminController`。

**原因**：路径归组符合 REST 设计直觉，便于通过路径快速定位处理逻辑。`/api/stores/{storeId}/products` 和 `/api/products` 是不同语义（前者针对某店，后者全局搜索），分到两个 Controller 避免一个类膨胀，也便于后续加权限拦截器时精准匹配。

---

### 24. `ReviewController` 和 `CouponGroupController` 不设 class-level `@RequestMapping`
**决策**：这两个 Controller 的 `@RequestMapping` 写在方法上（完整路径），不在类上定义公共前缀。

**原因**：`ReviewController` 的端点横跨 `/api/products/{productId}/reviews` 和 `/api/reviews/{reviewId}/replies` 两个不同根路径，无法提取公共前缀。`CouponGroupController` 同理，兼管 `/api/coupon-groups/**` 和 `/api/stores/{storeId}/coupon-groups`。强行设公共前缀反而会让路径更难读。

---

### 25. Controller 中 userId / role 通过 `getCurrentUserId()` 占位方法获取
**决策**：需要当前登录用户信息的 Controller 定义私有占位方法 `getCurrentUserId()` / `getCurrentUserRole()`，方法体内 `return null`，并附 `// TODO: 从 JWT Token 解析` 注释。

**原因**：JWT 过滤器尚未实现，SecurityContext 中目前没有用户信息。用占位方法统一封装获取逻辑，后续实现 JWT 时只需修改这一个方法（改为从 `SecurityContextHolder` 提取），不需要逐个修改 Controller 方法签名，降低改动范围。

---

### 26. `AdminController` 同时注入 `StoreService` 和 `ReportService`
**决策**：`/api/admin/**` 下两个端点（商店列表、全局报表）分属不同 Service，全部集中在 `AdminController` 中处理。

**原因**：这两个端点的路径前缀和权限（Admin Only）完全一致，集中在一个 Controller 便于权限拦截器统一拦截 `/api/admin/**`。如果拆分到 `StoreController` 和 `ReportController`，则这两个 Controller 就需要同时处理 Admin 和非 Admin 端点，权限边界不清晰。

---

## 七、公共工具类

### 27. 新增 `Result<T>` 与已有 `ApiResponse<T>` 并存
**决策**：在 `common` 包新建 `Result<T>`，已有的 `dto/ApiResponse<T>` 暂时保留不删除。

**原因**：`Result<T>` 包含按场景区分的错误码常量（400/401/403/404/500）和语义化快捷方法（`badRequest` / `unauthorized` / `forbidden` / `notFound`），并通过私有构造器 + 静态工厂方法禁止外部直接实例化，设计更完整。`ApiResponse<T>` 是早期为 DTO 层生成的简化版，待全面切换 `Result<T>` 后可删除。

---

### 28. `Result<T>` 字段声明为 `final`，使用 `@Getter` 而非 `@Data`
**决策**：`Result<T>` 的三个字段 `code / message / data` 均声明为 `final`，只用 `@Getter`，不用 `@Data` / `@Setter`。

**原因**：`@Data` 会通过 `@RequiredArgsConstructor` 生成公共无参构造器（当字段无 `@NonNull` / `final` 时退化为无参），破坏"只能通过静态工厂方法创建实例"的设计意图。`final` 字段 + 私有全参构造器 + `@Getter` 保证对象不可变，是值对象（Value Object）的标准写法。

---

## 八、异常处理

### 29. `BusinessException` 默认 code 为 400 而非 500
**决策**：`BusinessException(String message)` 单参构造器将 `code` 默认设为 `Result.CODE_BAD_REQUEST`（400）。

**原因**：Service 层抛出的业务异常通常表示"请求在业务规则上无法执行"（库存不足、优惠券已用、状态不对等），是客户端请求的前置条件未满足，语义上属于 4xx。500 表示服务端内部故障（数据库异常、第三方服务超时等），此类情况不应由 `BusinessException` 承载，而由 `RuntimeException` 兜底处理。

---

### 30. `GlobalExceptionHandler` 将所有字段错误拼接后返回，而非只取第一条
**决策**：`MethodArgumentNotValidException` 处理器将所有 `FieldError` 的 `defaultMessage` 用 `"; "` 拼接后放入 `Result.message` 返回给前端。

**原因**：用户提交的表单可能同时有多个字段不合法（如手机号格式错误 + 密码太短），若只返回第一条错误，用户修正后提交还会看到第二条错误，体验差。一次性返回所有错误让用户可以批量修正。单字段校验失败时行为与只取第一条完全一致。

---

## 九、Redis 集成

### 32. Redis 客户端选用 Lettuce（Spring Boot 默认），显式引入 `commons-pool2` 激活连接池
**决策**：Redis 依赖只添加 `spring-boot-starter-data-redis`（内置 Lettuce）和 `commons-pool2`，不引入 Jedis。

**原因**：Spring Boot 2.x 起默认使用 Lettuce 替代 Jedis 作为 Redis 客户端。Lettuce 基于 Netty 实现，单连接支持多线程复用，适合高并发场景。连接池配置（`spring.data.redis.lettuce.pool.*`）需要 `commons-pool2` 在 classpath 中才会生效，否则即使写了配置也不会启用池化，故显式声明依赖。

> 注：Spring Boot 3.x 已移除 `spring.redis.*` 命名空间，Redis 配置须置于 `spring.data.redis.*` 下，否则 `application.yml` 中的 host/port/password 等不会被绑定（会静默回退到 localhost:6379 默认值）。本项目曾误用 `spring.redis.*`，已修正。

---

### 33. Redis 连接参数使用环境变量占位符
**决策**：`application.yml` 中 Redis 的 `host / port / password / database` 均使用 `${ENV_VAR:defaultValue}` 形式，如 `${REDIS_HOST:localhost}`。

**原因**：不同环境（本地开发、测试、生产）的 Redis 地址不同，硬编码会导致提交的配置文件在其他环境不可用。使用环境变量占位符后，本地不设置环境变量时自动使用默认值（localhost:6379），CI/生产环境通过注入环境变量覆盖，不需要修改代码或配置文件。

---

### 34. 使用 `StringRedisTemplate` + `StringRedisSerializer`，不使用 `RedisTemplate<Object, Object>`
**决策**：`RedisConfig` 中创建 `StringRedisTemplate` Bean，key/value/hashKey/hashValue 序列化器全部设为 `StringRedisSerializer`。

**原因**：默认的 `RedisTemplate<Object, Object>` 使用 JDK 序列化，存入 Redis 的数据是二进制乱码，无法在 Redis CLI 或可视化工具中直接阅读，也无法跨语言共享。`StringRedisTemplate` 强制 key 和 value 都是 String，存入的是可读文本。对于需要存对象的场景，在调用层手动序列化为 JSON 字符串（如 `Jackson ObjectMapper`），保持 Redis 中数据格式统一可控。

### 35. `RedisUtil` 额外封装 `expire` 和 `getExpire`
**决策**：工具类在用户要求的 5 个方法基础上，额外提供 `expire`（补设过期时间）和 `getExpire`（查剩余秒数）两个方法。

### 41. 新增 `POST /api/auth/refresh` 刷新接口，refreshToken 轮换

### 43. 引入 Flyway 做数据库版本化迁移，迁移脚本成为 schema/种子的唯一可执行来源
**决策**：引入 Flyway（`flyway-core` + `flyway-mysql`，版本由 Spring Boot 3.4 BOM 管理，实际 10.20.1），应用启动时自动执行 `src/main/resources/db/migration/` 下脚本。原 `docs/schema.sql` → `V1__init_schema.sql`（版本化迁移，DDL），原 `docs/data.sql` → `R__seed_data.sql`（可重复迁移，种子）。`docs/` 下的两个 SQL 文件已删除，相关文档引用改指向迁移目录。

**原因**：此前 schema 与代码脱节引发连环问题——实体加了 `created_at/updated_at` 列但运行库未同步，报 `Unknown column`；`schema.sql` 与 `data.sql` 两份种子主键冲突（`Duplicate entry '1'`）。根因是「全量脚本只描述最终结构、不记录增量，旧库无法安全升级」且存在多份打架的种子来源。Flyway 用带版本号、不可变、按序累加的迁移脚本，让任何环境启动即自动对齐到最新结构，并以 `flyway_schema_history` 表记录已应用版本。

- **`R__` 可重复迁移而非 `V2__` 版本化**承载种子：可重复迁移在所有版本化迁移后执行，且仅当内容 checksum 变化时重跑。配合脚本开头的「清空 + 重置自增」，改种子后重启即自动重灌，契合开发期频繁调整测试数据的需求。代价：会清空相关表，仅限开发/测试库。
- **`baseline-on-migrate: true` + `baseline-version: 1`**：兼容「已建表但无 flyway 历史」的存量库——基线到 V1（跳过建表），只补跑 `R__`；空库则正常从 V1 执行。
- **已发布的 `V1` 不可再改**，后续任何结构变更新增 `V2__xxx.sql` 只写增量 DDL（Flyway 会校验已应用脚本的 checksum）。

### 44. 未支付订单自动取消用 Spring `@Scheduled`，逐条独立事务并恢复库存/优惠券
**决策**：用 Spring 内置定时任务实现未支付订单自动取消：`config/SchedulingConfig` 上 `@EnableScheduling`，`job/OrderAutocancelJob` 用 `@Scheduled(fixedDelay = 60000)` 每分钟执行；`OrderMapper` 加 `selectExpiredUnpaidOrders(LocalDateTime)` 查询；`OrderService` 加系统级方法 `cancelExpiredUnpaidOrder(Order)`（独立 `@Transactional`），由 Job 逐条 try-catch 调用。保留天数读配置 `bluewhale.order.auto-cancel-days`（默认 14）。

**原因**：
- **自动取消必须恢复库存**：本项目 `createOrder` 是「下单即扣库存」（`OrderServiceImpl` Phase 2 扣减），未支付订单已占用库存，若取消不恢复会造成**库存永久泄漏**。最初需求设想「未支付未扣库存、无需恢复」与实际代码不符，经确认采用「与现状一致、恢复库存」方案（未改动 createOrder 的扣减时机，避免引入下单到支付间的超卖窗口）。
- **同时恢复优惠券**：`createOrder` 下单即把券标记 `USED`，取消需还原 `UNUSED`，复用 `restoreCoupon`。
- **不复用 `cancelOrder`**：它内部 `requireCustomerOrder` 读 `SecurityContext` 校验 Customer 归属，定时任务无鉴权上下文，强行复用会失败。新增不鉴权、不暴露接口的系统级方法，库存/优惠券恢复逻辑（`restoreInventory`/`restoreCoupon`）仍复用。
- **逐条独立事务 + Job 内 try-catch**：每条订单各自 `@Transactional`，单条失败只回滚该条；Job 循环内捕获异常，保证「单条失败不影响其他订单」。优于「整批一个事务」（一条坏数据回滚整批）。
- **幂等防御**：`cancelExpiredUnpaidOrder` 执行前 `getById` 重查状态，非 PENDING_PAYMENT 则跳过，避免与手动支付/取消竞态导致重复处理。
- **用 Spring `@Scheduled` 而非 Quartz/XXL-Job**：单机单任务，内置调度零额外依赖即可；分布式调度属后续扩展。
- **包名全小写**：按决策第 2 条，类放在 `com.twentyzhang.bluewhale.job` / `.config`（需求中 `BlueWhale` 大小写仅为非正式写法）。
- 实现细节见 `docs/实现说明.md`「定时任务：未支付订单自动取消」。

### 45. 商品库存用乐观锁（自定义 SQL）防超卖，不注册全局乐观锁拦截器
**决策**：`Product` 加 `@Version version` 字段（迁移 `V2__add_product_version.sql`）；`ProductMapper` 加自定义 `@Update` 方法 `updateStockWithVersion`（相对扣减，含 `stock >= quantity` 守卫）与 `updateStockTo`（绝对设置）；`createOrder` 扣减与 `updateStock` 调整均改为「重读 → 带版本号条件更新 → 影响行数 0 则重试，最多 3 次，仍失败抛『库存更新失败，请重试』」。**不注册** MyBatis-Plus `OptimisticLockerInnerInterceptor`。

**原因**：
- **防超卖的核心是条件 UPDATE 的 `stock >= #{quantity}`**：DB 层原子的"检查并扣减"，影响行数 0 即库存不足/被抢占，杜绝并发超卖；version 提供并发冲突检测与重试依据。

- **为什么不只用 `stock >= quantity`、还要叠版本号？**（两者职责不同）
  - `stock >= quantity` 是**业务护栏**——只针对"库存单调递减且有天然下限 0"的特例，恰好既是业务规则又能当冲突信号。**纯扣减场景它单独就够防超卖，version 在这条路径上并非必需。**
  - `version = #{version}` 是**并发护栏**——检测"本行自我读取后是否被他人改过"，防的是**丢失更新（lost update）**，对任意字段通用、不依赖天然下限。
  - **真正离不开 version 的是 `updateStockTo`（Staff 绝对值写入）**：它是"读 100 → 应用算出新绝对值 → 写回"，写绝对值**没有 `stock >= q` 这类护栏**；若只 `WHERE id=?`，两个并发调整会互相覆盖（丢失更新），只有 `WHERE version=#{read}` 能检测冲突并重试。
  - **代价（诚实记录）**：给纯扣减路径也加 version，会让"影响 0 行"二义化——既可能是库存不足、也可能是版本冲突，因此才需要重试循环 + 进入循环前的库存再校验来区分；只用 `stock >= q` 时 0 行含义唯一（库存不足），可直接拒绝、无需重试。即在扣减路径上 version 不增加安全性、反增复杂度。
  - **仍两条路径都用 version 的理由**：① 需求规格明确要求 `@Version` + 带版本号 SQL；② 与 `updateStockTo` 统一为一套"乐观锁 + 重试"心智；③ 为库存逻辑未来变复杂（预占/释放、多字段联动，`stock >= q` 特例护栏失效）预留通用机制。**结论：扣减路径的安全性由 `stock >= quantity` 兜底，version 主要为绝对值写入、规格一致性与扩展性服务，未夸大其作用。**

- **为何不注册全局 `OptimisticLockerInnerInterceptor`**：注册后所有 `updateById(product)` 都会被自动加版本校验。但 `restoreInventory`/`updateProduct` 等调用**未检查返回值**，冲突时会静默不更新，引入隐蔽 bug（如取消订单库存未恢复）。改用显式自定义 SQL 只保护指定路径，爆炸半径最小；version 仅由这两个自定义 SQL 推进，`@Version` 注解保留以表意并为将来启用拦截器留口。
- **加列走 Flyway 新迁移 `V2`**：已发布的 `V1` 不可改（决策 #43），结构变更一律新增版本化迁移。
- **重试 3 次**：按需求规格。注意 `createOrder` 处于 `@Transactional` + MySQL 默认 REPEATABLE READ，事务内重读未必见到他事务最新提交的 version，重试常无效；但安全性由条件 UPDATE 保证，重试耗尽即抛错、由客户端整单重试（新事务新快照），不会超卖。`updateStock` 无事务，重试有效。
- **遗留**：`restoreInventory` 仍为读-改-写 `updateById`（只加库存、不致超卖）。
- 实现细节见 `docs/实现说明.md`「商品库存乐观锁（防并发超卖）」。

### 46. 优惠券领取用 Redis 分布式锁（组级粒度）+ DB 守卫双保险防超发
**决策**：新增 `util/RedisLockUtil`（`tryLock` 用 `SET NX EX`，`unlock` 用 Lua「value 一致才 del」）；`claimCoupon` 方法开始处按 `coupon_lock:groupId:{groupId}` 加锁（lockValue=UUID，5s 过期），失败抛「系统繁忙，请稍后重试」，`finally` 释放；持锁后双重检查 `remainCount > 0`；扣减改为带 `remain_count > 0` 守卫的条件 UPDATE；方法保留 `@Transactional`。

**原因**：
- **为什么用分布式锁而非乐观锁（与库存 #45 的关键区别）**：领取是一个**多步复合业务流程**，四步必须作为整体保证原子——① 查 `remainCount` → ② 查"用户是否已领取过" → ③ `remainCount - 1` → ④ 创建 `coupon` 记录。乐观锁（version / 条件 UPDATE）**只能保证单条 SQL 的原子性，保护不了跨多步的业务不变量**。
  - 最致命的是第②步「**防重复领取**」：它是"先查再插"的检查-动作组合，乐观锁无从下手。高并发下两个请求可能**同时通过"未领取"检查**，各自插入一条，导致**同一用户领两张**。库存那种 `stock >= #{q}` 单条原子守卫，在"是否已领取"上根本写不出对应的单 SQL 条件。
  - 库存扣减（#45）之所以乐观锁够用，是因为它本质是**单步**操作、且有天然的单条原子守卫（`stock >= q`）；而领取是**多步、含查重**的流程，只能用锁把整段临界区串行化。
  - 故区分原则：**单步且可表达为单条原子条件 → 乐观锁（#45 库存）；多步业务流程、含"检查后动作"的不变量 → 分布式锁串行化整段（#46 领取）。**
- **锁粒度为优惠券组**：key 含 `groupId`，同组并发领取互斥、不同组互不影响，避免全局串行化损失吞吐。
- **解锁用 Lua 脚本**：`tryLock` 的 value 用 UUID 唯一标识持有者，`unlock` 判断 value 一致才删除，防止「锁过期→他线程持锁→本线程误删他人锁」。判断与删除必须原子，故用 Lua。
- **`SET NX EX` 而非分两步**：`NX` 互斥 + `EX` 过期一条命令完成，避免「set 后还没设过期就宕机」导致死锁。
- **DB 守卫 `remain_count > 0` 作为最终防线（关键）**：锁在 `@Transactional` 方法体 finally 释放，而事务由 Spring 代理在方法返回后才提交——存在「释放锁→他线程拿锁→读到本事务尚未提交的旧 remainCount（双重检查放行）→扣减」的窗口，**单靠锁仍可能超发 1 个**。给扣减加 `WHERE remain_count > 0` 并判影响行数，保证即便读到旧值也减不成负数。即超发的最终保证是 DB 守卫，分布式锁主要降低无效竞争与重复领取冲突。彻底消除该窗口的正解是「锁包事务」（锁移到事务外），属后续优化，当前用 DB 守卫兜底已不会超发。
- **未引入 Redisson**：临界区短、可容忍偶发重试，轻量实现（不可重入、无看门狗）足够；需要可重入/自动续期再升级。
- **包名全小写**：`com.twentyzhang.bluewhale.util`（决策第 2 条）。
- 实现细节见 `docs/实现说明.md`「优惠券领取 Redis 分布式锁（防并发超发）」。

### 47. 热点读缓存用手写 CacheUtil（getOrLoad）而非 Spring Cache 注解
**决策**：路线图任务 3。新增 `util/CacheUtil`（`getOrLoad` 两个重载：`Class<T>` 单实体 / `TypeReference<T>` 集合分页）+ `util/CacheKeys`（key 与 TTL 集中）+ `RedisUtil.deleteByPrefix`（SCAN）。缓存对象：分类树、商店详情/列表、商品详情、商品评论分页、订单报表（依识别文档，含三个待定项的拍板：商品详情库存取**方案 1 短 TTL**、优惠券组列表与商品搜索**不缓存**）。写操作主动失效对应缓存。

**原因**：
- **手写 CacheUtil 而非 `@Cacheable`/`@CacheEvict`**：需要精确控制「空值占位防穿透 + 命中占位抛 404」「TTL 随机抖动防雪崩」「反序列化失败回源容错」这些定制逻辑，Spring Cache 注解表达起来绕；手写 getOrLoad 一处封装、各 Service 复用，且不必引入 `@EnableCaching` 改全局行为。
- **不注册 `RedisCacheManager`**：复用现有 `StringRedisTemplate` + 注入 Spring 的 `ObjectMapper`（已含 JavaTimeModule，能序列化 `LocalDateTime`；`FAIL_ON_UNKNOWN_PROPERTIES=false`）做 JSON 存取。`IPage` 缓存为具体 `Page<T>`，用 `TypeReference` 携带泛型反序列化（已单测验证 `Page<Dto>` 可往返）。
- **穿透防护**：DB 查询为 null → 写空值占位 `CACHE_NULL`（固定 60s）并抛 `BusinessException(404)`；后续命中占位直接抛 404，避免不存在的 key 反复打库。代价：单实体未找到的 404 消息统一为通用「资源不存在」（占位命中时无法还原实体专属文案）。
- **雪崩防护**：实际 TTL = `baseTtl + random(randomRange)`，打散过期时刻。
- **失效用 SCAN 不用 KEYS**：`deleteByPrefix` 以 SCAN 游标分批删除（如清某商品全部分页评论 `product:reviews:{id}:*`），KEYS 会全库遍历阻塞生产。
- **失效触发**：增删分类→清 `category:tree`；商店增改→清 `store:detail:{id}` + `store:list:*`；商品改/删/调库存→清 `product:detail:{id}`；发表评论/回复→清 `product:reviews:{id}:*`；报表纯 TTL 不主动清。
- **一致性边界（方案 1 取舍）**：商品详情含 `stock`，订单下单/取消改库存**不**主动清该缓存（只有 Staff `updateStock`/改删商品才清），靠 5 分钟短 TTL 容忍展示延迟；下单有 `stock >= q` 实时守卫兜底，不会超卖（详见 #45）。
- 识别与定级见 `docs/缓存热点数据识别.md`；实现见 `docs/实现说明.md`「热点读缓存」。

### 48. 报表导出用 EasyExcel + 多 Sheet，Controller 复用 JSON 查询方法
**决策**：路线图任务 4。引入 `com.alibaba:easyexcel:3.3.4`；新增两个导出接口 `GET /api/stores/{storeId}/reports/orders/export`（Staff）与 `GET /api/admin/reports/orders/export`（Admin）。Controller **直接复用** `ReportService.getStoreOrderReport`/`getGlobalOrderReport` 拿数据，再把 DTO 交给 `util/ReportExcelExporter` 写成**多 Sheet** xlsx（门店：汇总/状态分布/每日收入；全局：汇总/门店分布/每日收入），`util/ExcelDownloadUtil` 设下载响应头。新增 `dto/excel/*` 行模型（`@ExcelProperty`）。

**原因**：
- **选 EasyExcel 而非 Apache POI**：POI 全量加载到内存、API 繁琐；EasyExcel 在其上做了 SAX 流式封装，内存占用低、注解式表头（`@ExcelProperty`）声明即用，报表数据量虽不大但写法更省。EasyExcel 仍以 POI 为底层依赖，故 POI 类（`WorkbookFactory`）在测试里可直接用来回读校验。
- **版本取 3.3.4**：与 Spring Boot 3.4 / Java 17 兼容的稳定版（底层 POI 5.2.x）。未选更激进的 4.x / 改名后的 `fastexcel`，优先稳定。
- **Controller 复用 Service 的 JSON 查询方法，而非给 Service 加导出方法**：导出与 JSON 接口的数据完全一致，复用即自动获得**相同的鉴权（`requireRole`/`requireStoreAccess`）与缓存（`getOrLoad`）**，零重复。导出逻辑（DTO→xlsx）是纯展示转换，放 `util` 不进 Service，保持 Service 只产数据。
- **鉴权异常先于响应体写出**：Controller 先调 Service 查数据（可能抛 401/403/404），**再**调 `prepareResponse` 设响应头并写字节。顺序保证鉴权失败时异常能正常落到 `GlobalExceptionHandler` 返回 JSON 错误，而不是写了一半的损坏 xlsx。
- **多 Sheet 而非单表**：报表是「汇总指标 + 明细分布 + 按日趋势」三段异构数据，塞进一张表需要合并/留白很别扭；EasyExcel 的 `ExcelWriter` + 多个 `WriteSheet` 每段一张、各用各的表头类，结构清晰。
- **汇总值统一转 String**：汇总 Sheet 同列既有整数（总订单数）又有金额（总收入），用 `ReportSummaryRow{metric, value:String}` 键值对避免类型混排。
- **下载文件名走 RFC 5987**：`ExcelDownloadUtil` 同时给 `filename`（URL 编码）与 `filename*=UTF-8''`，兼容含非 ASCII 字符的文件名（当前文件名为纯 ASCII，但留好通用编码）。
- **安全放行**：两个 export 路径不在 `SecurityConfig` 的游客白名单内（`/api/stores/*` 只匹配单段、`/api/stores/*/products` 为精确串），自动落入 `anyRequest().authenticated()`，再由 Service 内的角色校验细化。
- **包名全小写**：`com.twentyzhang.bluewhale.util` / `.dto.excel`（决策第 2 条）。
- 实现细节见 `docs/实现说明.md`「报表导出 Excel」。

### 49. 多优惠券叠加：券类型拆 3 类 + 穷举最优顺序计价 + order_coupon 关联表 + 试算接口
**决策**：路线图任务 5。①券类型由 `DISCOUNT/AMOUNT_OFF` 拆为 **`DISCOUNT`(折扣) / `FULL_REDUCTION`(满减,有门槛) / `DIRECT_OFF`(直减,无门槛)**（迁移 V3 把旧 `AMOUNT_OFF` 按 `min_order_amount>0` 拆到两类）；②`CreateOrderRequest.couponId` 改为 `couponIds` 列表；③新增纯函数 `util/CouponCalculator` 穷举券应用顺序取最大折扣；④新增 `order_coupon` 关联表（`OrderCoupon`/`OrderCouponMapper`）记录一单多券，取消/退款据此恢复；⑤新增试算接口 `POST /api/orders/coupon-preview`；⑥`OrderServiceImpl.resolveCoupons` 统一校验+计价，被 `createOrder` 与 `previewCoupon` 复用。

**原因**：
- **为何拆成 3 个 type（而非沿用 AMOUNT_OFF 靠门槛区分）**：叠加规则是「同类型至多一张、不同类型无限叠加」。若满减/直减同属一个 type，用户就无法「满减 + 直减」同时用。拆成独立 type 后，按 `type` 即可判定「同类型限一张」，规则表达直接。代价是新增一次数据迁移（V3）与创建校验分支。
- **门槛按原始订单总额判定（不按运行金额）**：券是否可用在计价前一次性按购物车原价判定，达标后只优化「先后顺序」。好处是可预测——不会因为先用了折扣券把金额压低、导致满减券被悄悄踢掉；与历史单券逻辑一致。任一选中券不达标即整单报错（带券名），不静默丢弃。
- **顺序为何影响结果、为何穷举**：链式计价中，乘性折扣会把「其后」的减免一并打折，故「先乘后减」removes 全额减免、折扣最大——这是可证明的最优贪心（先所有折扣、再所有减免）。但仍选择**穷举全排列取最大**：券数 ≤3（每类至多一张）⇒ 至多 6 种排列，开销可忽略；穷举「显然正确」、且对未来规则变化（新增券型、改门槛语义）天然鲁棒，无需重证贪心。用户提及的并发计算在此规模下无必要。
- **CouponCalculator 设计为纯函数**：只接收 `totalAmount + 已通过资格校验的 specs`，不碰 DB/Spring，便于单测（`CouponCalculatorTest` 覆盖单券/叠加/下限/空券）。资格校验（归属、状态、过期、店铺范围、同类型限一张、门槛）留在 Service 层（持 DB 与券名，错误信息友好）。
- **计价以「实付」为中心，保证不漏分**：每步运行金额四舍五入到分、并以 0 兜底（券额超额不产生负数），最终实付不低于 `0.01`；`discount = total − payable` 反推，保证 `折扣 + 实付 = 总额`精确无舍入泄漏（旧单券「先算 discount 再减」在极端舍入下二者可能差 1 分，新写法更严谨）。
- **新增 order_coupon 关联表而非在 orders 存多列/CSV**：一单多券是一对多，关联表是范式做法；取消/退款恢复以本表为准，并**兼容**历史单券订单的 `orders.coupon_id`（恢复时取两者并集）。新订单不再写 `coupon_id`（保留列以兼容旧数据），核销时逐张标记 USED 并插 `order_coupon`。
- **店铺范围校验（新增收紧）**：店铺券仅适用于本店订单，全局券（storeId=null）不限。单券时代此校验缺失（潜在 bug）；多券叠加下若不校验，可叠加多张无关店铺的券，故在 `resolveCoupons` 补上。属对既有行为的收紧，记录在此。
- **试算接口复用计价、不落库**：`previewCoupon` 走与下单相同的 `resolveCoupons`（同样的校验与最优计价），但只读购物车/商品、不校验库存、不写任何表，返回最优折扣、实付与券应用顺序，供前端选券时实时展示。下单时后台**重新计算**，不信任前端试算结果。
- **DIRECT_OFF 必须无门槛、FULL_REDUCTION 必须有门槛**：创建券组时校验，使两个 type 语义清晰、与「满减/直减」名实相符。
- 实现细节见 `docs/实现说明.md`「多优惠券叠加（任务 5）」。

### 50. 会话归属采用「认领制（claim/pull）」，而非共享收件箱、哈希分配或自动路由
**决策**：v1 客服会话归属模型选 **认领制**——新会话先进店铺公共池（全店客服可见），客服**手动「接入」**某个会话后该会话归属此客服（`chat_session.assignee_staff_id`），之后买家消息精准投递给该客服、其他客服看到「已被 X 接待」。不做哈希分配、不做自动路由引擎。

**原因**：
- **目标是「一客户对接一个固定客服、客服间不撞车」**，这是成熟客服系统（Zendesk / Intercom / 网易七鱼等）的标配能力，叫**会话归属（assignment）**。
- **为什么不用哈希分配（`customerId % 客服数`）**——这是最初的直觉方案，但有三个现实硬伤：
  1. **哈希按「人数」均衡，聊天负载看的是「强度」**：哈希能让每个客服分到差不多数量的客户，但有人狂聊、有人发一句就走，导致负载严重失衡。
  2. **哈希无状态，看不到「谁在线」**：客服下班/午休时，哈希到他名下的客户发消息无人接，买家干等。
  3. **客服数一变全体重算**：增减一个客服，`% N` 的 N 变了，几乎所有客户被重新分配、正聊的对话串线（需一致性哈希才能缓解，复杂度陡增）。
  - 根因：**哈希是「无状态、反复算」的，而「在线状态、当前负载」是动态的**，无状态算法看不到。成熟系统都改为「**算一次、把归属持久化**」（`assignee_staff_id` 落库），而非反复哈希。
- **三种成熟模型对比与取舍**：
  | 模型 | 运作方式 | 复杂度 | v1 是否采用 |
  |---|---|---|---|
  | ① 共享收件箱(pool) | 不分配，全员看到全部，谁有空谁回 | 最低 | 否 |
  | ② **认领制(claim/pull)** | 新会话进公共池，客服手动「接入」，接入后归他 | 中 | **是** |
  | ③ 自动路由(auto-route) | 路由引擎按在线+负载+技能自动派单，粘性保持 | 高 | 否（留待后续） |
  - **选 ② 的理由**：精确命中「专人对接、不撞车、对话期不广播刷屏」的需求，又**没有哈希的全部坑**（看得见在线状态、不会负载失衡、增减客服不串线）；只比 ① 多一个 `assignee_staff_id` 字段 + 一个「接入」动作，成本可控。
  - **不选 ③**：自动路由本质是一套**派单子系统**（路由决策 + 掉线转交 + 无人在线排队），v1 偏重；且可从 ② **平滑升级**——把「人点接入」换成「引擎自动接入」即可，数据模型不变。
  - **不选 ①**：共享收件箱下客服互相看不到归属，容易两个客服重复回复同一买家；且与「专人对接」的产品诉求不符。
- **对数据模型/拓扑的影响**：`chat_session` 增 `assignee_staff_id`（可空，未接入为 null）；需「接入」接口 + 「已被谁接待」状态展示；消息路由从「广播店铺主题」调整为「未接入→店铺池可见、已接入→投递给归属客服」（STOMP 拓扑细节随设计推进在 spec 中定稿）。

### 51. 实时客服（任务 7，实现细节）——传输、鉴权、路由、在线状态与关键修复

> 本条记录 **实现阶段** 的架构细节与取舍。设计阶段选型见第 50 条；测试策略见第 0 条（纯 Mockito 单测 + 集成测试两套）。

**传输与 Broker**：引入 `spring-boot-starter-websocket`，`@EnableWebSocketMessageBroker` 开启消息路由。WebSocket 握手端点 `/ws`（纯 WebSocket，无 SockJS，降低复杂度）。内存 `SimpleBroker`（单实例，无需 RabbitMQ/Redis 外部 Broker），广播前缀 `/topic`、私信前缀 `/queue`、应用发送前缀 `/app`、用户定向前缀 `/user`。

**STOMP 鉴权**：复用现有 JWT，方案为「CONNECT 帧 Header 鉴权」——客户端在 STOMP CONNECT 帧的 `Authorization` header 携带 `Bearer <jwt>`，`StompAuthChannelInterceptor`（注册在 client inbound channel）解析并验证 token，通过后绑定 `ChatPrincipal`（`getName()` 返回 userId String）作为会话 principal。非法/缺失 token 抛异常拒绝连接。`SecurityConfig` 放行 `/ws/**`（WebSocket 握手走 HTTP Upgrade，真正鉴权在 STOMP CONNECT 帧，不依赖 servlet 安全链）。

**关键修复——WS 线程无 SecurityContext**：STOMP 消息处理在专用线程池，`JwtAuthenticationFilter` 只在 servlet 请求线程填充 `SecurityContextHolder`，WS 处理线程上 SecurityContext 为空。直接在 WS 处理器里调 `AuthUtil.requireRole()`（读 SecurityContext）会误判 401。

修复方案：新增 `AuthUtil.requireRole(AuthUser authUser, String... roles)` 重载，对**显式传入的 AuthUser 做角色校验**，不读 SecurityContext。WS 路径：`@MessageMapping` 方法签名带 `Principal principal`，从 `ChatPrincipal` 取出 `AuthUser`，传入 `requireRole` 重载。REST 路径不变（仍用 `AuthUtil.getCurrentUser()` 读 SecurityContext）。两条路径均传入 `AuthUser`，代码路径统一、无全局副作用。

**会话认领（原子写）**：接入用 `UPDATE chat_session SET assignee_staff_id=#{staffId} WHERE id=#{id} AND assignee_staff_id IS NULL`，影响 0 行表示已被他人接待（并发安全）。释放用 `UPDATE ... WHERE assignee_staff_id=#{me}`，影响 0 行表示非本人持有（403）。接入/释放走 REST（需写库并返回结果），成功后 STOMP 广播 `StoreTopicEvent{type:"CLAIMED"/"RELEASED"}` 通知全店客服更新待接入列表。

**消息路由（StoreTopicEvent 信封）**：所有推送到店铺主题的事件统一使用信封对象 `StoreTopicEvent{type, sessionId, message/...}`，`type` 枚举：`MESSAGE`（新消息）、`CLAIMED`（已被接入）、`RELEASED`（已释放）。路由规则：
- 买家发 `/app/chat.customer.send {storeId, content}` → 落库 → 未接入则广播 `StoreTopicEvent{MESSAGE}` 到 `/topic/store.{storeId}`；已接入则 `convertAndSendToUser(归属客服userId, /queue/messages, ChatMessageResponse)`。
- 客服发 `/app/chat.staff.send {sessionId, content}`（须为 assignee，否则 403）→ 落库 → 投递买家 `/user/queue/messages`。

**推送在事务提交后执行（避免 REST-then-WS 竞态）**：发消息方法为 `@Transactional`（落库消息 + 更新会话冗余），STOMP 推送必须延迟到事务**提交之后**再发。否则买家首条消息（同一事务里新建会话 + 广播 `MESSAGE` 携带 `sessionId`）被客服收到后，客服立刻用该 `sessionId` 调 REST `claim`/`getMessages`（独立事务、MySQL 默认 REPEATABLE READ），可能因会话行尚未提交而读不到 → 偶发 404。实现用私有 `afterCommit(Runnable)`：有活动事务时 `TransactionSynchronizationManager.registerSynchronization(...afterCommit)`，无事务时立即执行（兼顾纯 Mockito 单测）。

**订阅权限**：`SUBSCRIBE /topic/store.{id}` 在拦截器中校验订阅者为该店 STAFF，防止买家越权订阅他店店铺主题；`/user/queue/**` 由 Spring 按 principal（userId）自动隔离。

**在线状态**：`WebSocketPresenceListener` 监听 Spring 内置的 `SessionConnectedEvent`/`SessionDisconnectEvent`，维护两个 Redis Set——买家 `cs:online:customers`（成员为 userId）、客服 `cs:online:store:{storeId}`（成员为 userId）。会话列表接口内联返回对端在线状态：买家视角=本店 `SCARD > 0` 有客服在线；客服视角=买家 `SISMEMBER` 是否在线。

**错误处理**：WS 侧用 `@MessageExceptionHandler` + `@SendToUser("/queue/errors")`，`BusinessException` 回友好信息，未预期异常记日志回通用文案。REST 侧越权走 `GlobalExceptionHandler`（403/404）。

**离线粘性**：接待客服掉线时 `assignee_staff_id` 保持不变（粘性）；掉线期间买家消息正常落库；客服重连后通过历史接口（`GET /api/chat/sessions/{id}/messages?before=...`）拉取补齐。

**🔴 后续必做 / 已知限制**（第二轮 B 已全部收尾，见决策 #55）：
1. ~~**接待会话超时自动释放**~~ ✅：`ChatSessionTimeoutJob` 每 5 分钟扫描，归属客服离线者自动释放回公共池（B1）。
2. ~~**STOMP 拒绝未发 ERROR 帧**~~ ✅：注册 `ChatStompErrorHandler`（`StompSubProtocolErrorHandler`），失败回结构化 ERROR 帧（B2）。
3. ~~**在线状态脏数据**~~ ✅：SimpleBroker 启用 STOMP 心跳，死连接被探测关闭 → DISCONNECT 触发清理（B3）。

**实现细节**见 `docs/实现说明.md`「实时客服：消息路由与在线状态」。

### 52. 推荐算法（任务 8）——item-based 协同过滤、加权余弦、多级缓存

> 设计过程见 `docs/superpowers/specs/2026-06-10-推荐算法-design.md`；知识背景见 `docs/学习笔记-推荐算法与实时客服.md` 第一部分；实现细节见 `实现说明.md`「推荐算法」。

**决策**：基于订单历史做 **item-based 协同过滤**，离线预计算相似度、线上查表，提供「商品相关推荐(A)」与「个性化猜你喜欢(B)」两接口。

**原因与取舍**：

- **选 item-based，不选 user-based / 矩阵分解 / 深度模型**：物品相似度是慢变量、可离线算好查表（亚马逊经典论文论点）；用户相似度变化快、线上算不动；MF / 深度模型工程偏重，对本项目数据量属杀鸡用牛刀。

- **加权余弦，不选 Jaccard**：二元数据下两者结果接近，但余弦基于向量点积，**为后续加权留口**（次数/评分加权只需改权重值）；Jaccard 基于集合交并，加权要换公式。v1 即用上该口子（状态加权）。

- **共现口径=同一用户跨订单**（非同一购物篮）：贴合「相关推荐/猜你喜欢」语义；订单量不大时数据更密、相似度更稳。

- **状态全纳入但加权（取最大）**：下单本身即被行为证明的兴趣，故 `CANCELLED`/`PENDING_PAYMENT` 也纳入；但不与真实成交等价——`PAID/SHIPPED/COMPLETED`=1.0、`PENDING_PAYMENT`=0.5、`CANCELLED`=0.3（含任务1的自动弃单，弱信号）。同用户同商品多次购买**取最大权重**而非累加，避免刷单/重复下单放大。订单状态经核对仅五种，退款复用 `CANCELLED`。

- **离线预计算 + 多级缓存**：`@Scheduled` 每日 03:00 全量重建 + Admin 手动接口（本地调试免等 cron）。`product_similarity` 表为**真相来源**（关机不丢，派生数据可随时从订单重算）；Redis ZSET（`rec:sim:{id}`）作**热读缓存**，read-through 未命中回表回填、重建时清缓存懒重建。把贵的计算挪出请求路径。

- **热销榜按需 SQL，不预计算建表**（对 spec §4.2 的实现期细化）：兜底路径触发频率低、`SUM(quantity)` 聚合便宜，故不单独建表/缓存，简化设计；多级缓存的学习点集中在相似度路径。

- **Admin 鉴权放 Controller 层**：`rebuildAll()` 同时被定时任务调用（线程无 SecurityContext），故鉴权不能放服务层 `AuthUtil.requireRole`（读 SecurityContext 会 NPE/误判）——与任务7「WS 线程无 SecurityContext」同源教训。

- **冷启动兜底分层**：CF 结果 → 同类目热销 → 全站热销，逐层补足，保证推荐位不空白；接口 B 排除已购，接口 A 不排除。

**对数据模型的影响**：新增 `product_similarity(product_id, similar_product_id, score)`（迁移 V5，唯一键 `(product_id, similar_product_id)` + 索引 `(product_id, score)`，无逻辑删除列）。`RedisUtil` 新增 ZSet 操作（`zAdd`/`zRevRange`）。

**第二轮 C 增补**：① **空结果哨兵**——冷门商品无相似时写 `rec:sim:empty:{id}`（5min）占位，避免反复回表；前缀含 `rec:sim:` 故重建清缓存时一并清除。② **评分加权**——`review.rating` 经 `ratingMultiplier`（5→1.5…1→0.5，无评分 1.0）在重建时乘到状态权重上，兑现「选余弦留的加权口子」；仅作用于相似度重建路径。③ **C2 增量重建暂缓**：当前全量重建，本项目数据量小、收益有限，按规划列为可选未做。

### 53. 缓存增强（第二轮 F）——Caffeine L1 三级缓存 + single-flight 防击穿

> 实现细节见 `实现说明.md`「三级缓存：Caffeine L1 + single-flight」。来源参考见 `技术参考-可迁移优化点.md` #6（Feed 三级缓存）。

**决策**：在 `CacheUtil`（原 Redis L2 + DB）之上引入 **Caffeine 本地 L1**，补 **single-flight 防击穿**，并将四处缓存写点的失效统一收口到 `CacheUtil`（同时清 L1+L2）。

**原因与取舍**：

- **引入 Caffeine 做 L1**：L1 命中省去 Redis 网络往返与反序列化前的取值开销；与已有「Redis+DB」叠成经典三级缓存。版本由 Spring Boot BOM 管理，零额外配置。

- **single-flight 用条带锁，非每 key 建锁**：原 `getOrLoad` 未命中时并发请求会一起打 DB（缓存击穿是当时的缺口，雪崩/穿透已有保护）。改为按 key 哈希落 64 条固定条带锁 + 双重检查，同 key 并发只放一个回源。条带锁内存有上限，避免「每 key 一锁」无限增长（参考 Guava Striped 思路）。单机本地锁即可；跨实例可换 `RedisLockUtil`，本项目单实例无需。

- **失效统一走 CacheUtil（L1+L2 一致）**：L1 是本地缓存，写操作只清 Redis 会让 L1 残留脏数据。故新增 `invalidate`/`invalidateByPrefix` 同时清两级，四处写点（分类树/商品详情/商店详情·列表/商品评论）由 `redisUtil.delete*` 改用之，并移除各 Service 中不再使用的 `RedisUtil` 注入。

- **L1 短 TTL 兜底**：`expireAfterWrite 5s` 作为显式失效之外的安全网，限制任何漏失效场景的脏数据窗口（牺牲至多 5s 强一致换性能，对分类树/商店/商品详情等热点读可接受）。`invalidateByPrefix` 因 L1 不便前缀匹配而整体清空 L1，属有意取舍（条目少、重建快）。

- **不影响推荐 ZSet 缓存**：`rec:sim:*` 非 `CacheUtil` 托管，其失效仍走 `RedisUtil.deleteByPrefix`。

**对依赖的影响**：`pom.xml` 新增 `com.github.ben-manes.caffeine:caffeine`（版本随 Spring Boot BOM）。

### 54. 认证增强（第二轮 E）——令牌版本即时撤销 + 短 access token

> 实现细节见 `实现说明.md`「认证增强：令牌版本与即时撤销」。来源参考见 `技术参考-可迁移优化点.md` #1。

**决策**：在已有双令牌基础上，用**用户级令牌版本（token version / epoch）**实现 access token 即时撤销，access 有效期缩至 15min，退出登录 / 改密时撤销该用户全部令牌。RS256 暂缓。

**原因与取舍**：

- **撤销机制选「令牌版本」而非「jti 黑名单」**：token 带 `ver` 声明，Redis 存 `auth:tokenver:{userId}`，撤销即 `INCR`（旧 token `ver < current` → 失效）。一个 key、一条 `INCR` 即撤销该用户**全部**令牌，契合项目「每用户一个 refreshToken」的单会话模型；jti 黑名单需在 token 里加 jti、按已撤销 token 累积 key（虽有 TTL），且「撤销全部」需逐个拉黑。代价：过滤器每请求多一次 Redis `GET`（读当前版本），可接受。

- **版本键无 TTL、比较用 `>=`**：键持久（按用户数量有界）；`>=` 比较保证即便键缺失（默认 0）也不会误杀有效 token。real-scale 可加「TTL > 最大令牌寿命」自清，本项目从简持久。

- **access 缩至 15min**：缩小令牌暴露窗口，配合 refresh 轮换（7d）。前端刷新更频繁，机制已具备。属非破坏性变更。

- **登出/改密统一撤销**：二者成功后均 `bump 版本 + 删 refreshToken`（既杀 access 又杀 refresh）。新增 `POST /api/auth/logout`（从 access token 解析用户）。改密强制全端重新登录，符合安全直觉。

- **撤销校验放过滤器、不读业务 SecurityContext**：`JwtAuthenticationFilter` 验签后即查版本，未通过则不写认证上下文 → 受保护接口经 A1 的 `RestAuthenticationEntryPoint` 返回 401。

- **RS256 暂缓（E3 可选）**：HS256→RS256 是签名算法 + 密钥管理的替换，学习增量小于「撤销」这一核心安全点；后续只需改 `JwtUtil` 签名/验签与密钥，不影响版本撤销逻辑。

**对依赖/接口的影响**：`RedisUtil` 新增 `increment`；新增 `POST /api/auth/logout`；`jwt.expiration` 默认值 24h → 15min。

### 55. 实时客服收尾（第二轮 B）——超时释放、ERROR 帧、心跳兜底

> 实现细节见 `实现说明.md`「实时客服收尾」。收尾任务 7 决策 #51 记录的三项遗留。

**决策**：补齐实时客服三项遗留——接待会话超时自动释放、STOMP 结构化 ERROR 帧、在线状态心跳兜底。

**原因与取舍**：

- **B1 超时释放用「扫描时在线判定」而非新增掉线时间列**：定时任务（每 5min）扫已接入会话，归属客服当前不在 `cs:online:store:{storeId}` 即释放。复用现有在线 Set + 原子 `release`，**无需新增 `assigned_at`/掉线时间戳列**。5min 扫描间隔本身作宽限期，短暂刷新重连的客服扫描时已在线、不误释放。代价：极端情况下（客服恰在扫描瞬间断线）可能误释放，但会话回公共池可被重新接入，可接受。系统级调用不读 SecurityContext（同 `rebuildAll`/E 的教训）。

- **B2 注册自定义 `StompSubProtocolErrorHandler` Bean**：此前未注册任何错误处理器，`StompSubProtocolHandler` 的 errorHandler 为 null → 失败时不回 ERROR 帧。声明一个 Bean 即被 `WebSocketMessageBrokerConfigurationSupport` 自动织入，失败回结构化 ERROR 帧（带友好原因），提升前端可诊断性。

- **B3 启用 STOMP 心跳而非改造在线状态为 TTL 键**：原方案设想"心跳 TTL 键"需把在线 Set 改为带 TTL 的 per-member 键、改动 `SCARD`/`SISMEMBER` 查询，较重。改为**给 SimpleBroker 启用心跳**（需配 `TaskScheduler`）：死连接被服务端探测关闭 → 触发 `DISCONNECT` → 现有监听器 SREM 清理。**不改在线状态模型**，且覆盖客户端异常掉线这一脏数据主因；不支持心跳的客户端协商为 0、不受影响。残留：服务端自身崩溃的 Set 残留未处理（重连 re-SADD 可自愈），属可接受边界。

**对依赖/接口的影响**：新增 `ChatSessionTimeoutJob`、`ChatStompErrorHandler`、`WebSocketHeartbeatScheduler` Bean；`ChatService` 增 `autoReleaseOfflineAssignees`、`ChatSessionMapper` 增 `selectClaimedSessions`；无数据库变更。

### 56. 模拟支付网关（第二轮 D）——异步回路、HMAC 验签、幂等流水

> 实现细节见 `实现说明.md`「模拟支付：异步回路与幂等」。设计取舍见 `docs/superpowers/specs/2026-06-10-模拟支付-design.md`。

**决策**：用「可插拔的模拟支付网关」复刻真实第三方支付的**异步回路**，不接真支付宝、不碰内网穿透；接口留好供未来平滑替换真沙箱（任务 6）。

**原因与取舍**：

- **D1 方案 A「独立模拟收银台端点」而非前端假按钮**：`/api/mock-pay/{tradeNo}/success|fail` 扮演「用户在支付宝付钱」，触发真实回调链路，保住「外部网关回调」这一架构精髓。真接支付宝时删除 `MockCashierController`，由支付宝来调 `/api/payments/notify`（同一 `handleNotify`），是清晰的接入缝。

- **D2 真异步回调而非同步置 PAID**：收银台立即返回，`TaskScheduler`（`paymentCallbackScheduler`）延迟 ~1.5s 再发回调，前端轮询查单。保住「异步状态机 + 轮询」这一真支付宝标准姿势，也暴露幂等/并发问题供解决。**破坏性变更**：`POST /api/orders/{orderId}/pay` 不再直接返回 PAID，改返回 `{tradeNo, payUrl}`。

- **D3 幂等用「流水状态守卫 + 原子 UPDATE」而非分布式锁**：`advanceStatus`（`WHERE status='PENDING'`）与 `markPaid`（`WHERE status='PENDING_PAYMENT'`）两道原子条件更新，天然挡住重复/并发回调，无需额外锁。自定义 `@Update` SQL 显式 `deleted=0`。

- **D4 订单 1:N 流水分离**：订单状态与支付流水分表（`payment`，`trade_no` 唯一幂等键），一笔订单可多次发起支付（失败重试）各自留痕，金额取下单时实付额快照。

- **D5 网关抽象 `PaymentGateway`**：`createPayment` / `verifyCallback` 两方法，`MockPaymentGateway`（HMAC-SHA256）现实现，未来 `AlipayPaymentGateway`（RSA2）替换实现即可，`PaymentService` 与控制器不变。

- **回调路径不读 SecurityContext**：`handleNotify`/`triggerMockCallback` 跑在异步线程与开放端点；鉴权放 REST 路径（`initiatePayment`/`queryPayment`）。

**对依赖/接口的影响**：新增 `payment` 表（迁移 `V6`）、`Payment`/`PaymentMapper`、`PaymentService(Impl)`、`PaymentGateway`/`MockPaymentGateway`、`PaymentController`/`MockCashierController`、`PaymentSchedulerConfig`、`PaymentSignUtil`、`dto/payment/*`；`OrderMapper` 增 `markPaid`；`SecurityConfig` 放行 `/api/payments/notify`、`/api/mock-pay/**`；`application.yml` 增 `payment.mock.*`。**移除** `OrderService.payOrder` 与 `dto/PayOrderResponse`（破坏性）。

**实现期两处基础设施修复（落地任务 D 时发现并解决）**：

- **新增 `lombok.config`（`copyableAnnotations += @Qualifier`）**：`PaymentServiceImpl` 用 `@RequiredArgsConstructor` + 字段 `@Qualifier("paymentCallbackScheduler")` 注入。本项目 Lombok 版本默认**不**把 `@Qualifier` 复制到生成的构造器参数，运行期存在 3 个 `TaskScheduler` Bean（payment / messageBroker / webSocketHeartbeat）→ `NoUniqueBeanDefinitionException`，应用上下文无法启动。加全局 `lombok.config` 让 `@Qualifier` 随构造器参数保留，按名消歧（保留计划原写法，未改用显式构造器）。

- **JDBC URL 增 `allowPublicKeyRetrieval=true`**：MySQL 8 默认 `caching_sha2_password` over 非 SSL 连接，握手报「Public Key Retrieval is not allowed」导致所有 `@SpringBootTest` 无法连库。加该参数（已有 `useSSL=false`）放通公钥获取；属环境兼容性改进，对原可用环境无副作用。

### 57. AI 语义商品搜索（AI-1）——transactional outbox 同步 + Qdrant 向量库 + 通义 embedding

> 实现细节见 `实现说明.md`「AI 语义搜索：outbox 同步与向量检索」。设计取舍见 `docs/superpowers/specs/2026-06-15-ai语义搜索-design.md`，计划见 `plans/2026-06-15-ai语义搜索.md`。

**决策**：在现有 MySQL 关键词搜索之外，**新增一条独立的 AI 语义搜索链路**——商品向量化存入专用向量库 Qdrant，查询经通义 embedding 后做向量相似检索（带分类/价格过滤下推）；商品变更经 transactional outbox 可靠最终一致地同步到向量库。

**原因与取舍**：

- **方案 C「transactional outbox」而非写穿透或纯批量**：用户指定，借此加深 outbox 学习。商品写与 outbox 事件在**同一事务**原子提交，AI 基础设施（通义/Qdrant）全挂时商品照样写成功、事件留 `PENDING` 等补；商品写永不被索引链路拖垮。中继 `OutboxRelayJob`（`@Scheduled`）轮询消费 → embed → 同步 Qdrant → 标记 `DONE`/重试/`FAILED`。

- **专用向量库 Qdrant（Docker 单容器）而非 MySQL+Java cosine / Redis 向量**：学习真实向量库；以 `productId` 作 point id，`upsert`/`delete` 天然幂等，配合「至少一次投递」的中继安全。collection 启动时 `ensureCollection` 幂等创建（应用启动**不依赖** Qdrant 在跑）。

- **通义 `text-embedding-v3`（1024 维）做 embedding**：用户熟悉、国内网络可达、含 embedding API。生成侧 DeepSeek 留给 AI-2 RAG（本期不涉及）。

- **独立接口 + 结构过滤下推而非混合/替换**：新增 `GET /api/products/semantic`（开放），不动旧 `GET /api/products` 便于对比演示；分类/价格作为 Qdrant payload 过滤在向量库侧下推（非取回后过滤）。`POST /api/admin/products/reindex`（仅 Admin）给所有未删商品批量入队 UPSERT 全量回填，复用同一可靠通路。

### 58. AI 导购问答（AI-2，RAG）——检索增强生成 + SSE 流式 + qwen

> 实现细节见 `实现说明.md`「AI 导购问答（RAG）」。设计取舍见 `docs/superpowers/specs/2026-06-27-rag-design.md`，计划见 `plans/2026-06-27-rag导购问答.md`。

**决策**：在 AI-1 检索基座上叠加 LLM 生成，做**单轮、SSE 流式的商品导购问答**：用户自然语言提问 → 复用 `SemanticSearchService` 检索 top-K 商品 → 通义千问 `qwen-plus` 流式生成带推荐理由的回答 → SSE 推「商品卡事件 + 流式回答 token + done」。

**原因与取舍**：

- **生成侧 qwen 而非 DeepSeek**：路线图原计划 DeepSeek，但其账户余额不足（402）；改用通义千问 `qwen-plus`（DashScope OpenAI 兼容端点），**复用 embedding 同一个 `DASHSCOPE_API_KEY`/百炼账号**，联调零额外成本。`ChatCompletionClient` 抽象 + OpenAI 兼容，切回 DeepSeek 仅改 `base-url`/`model`/`key` 配置。

- **SSE 流式（方案 A：`SseEmitter` + `RestClient` 读流）而非 WebFlux / 假流式**：打字机效果、作品展示价值高，又贴合现有 servlet MVC + RestClient 栈，**零新增依赖**；代价是手写 SSE chunk 解析（`QwenChatClient.consumeStream`，`data: [DONE]` 终止）。否决引入响应式栈的 WebFlux，否决「整段生成完再切块」的假流式。

- **检索复用 `SemanticSearchService`，一份数据两用**：检索结果 `List<ProductListItemResponse>` 既作 `products` 事件的商品卡，又作 LLM 上下文，不重写检索。

- **严格 grounding + 空结果短路**：system 提示约束「只能从候选商品推荐、不得编造」防幻觉；检索为空时不调 qwen，短路推一句提示 + done，省 token。

- **专用 `ragStreamExecutor` 跑后台流**：`SseEmitter` 主线程秒返回、流在后台线程推，不阻塞容器请求线程；开放接口、后台线程均不读 SecurityContext。

- **接口开放**：`GET /api/products/qa`（SSE）。`EventSource` 只能 GET、不便带 token，开放正合适；现有 `/api/products/*` GET 规则已覆盖，`SecurityConfig` 显式标注。

**对依赖/接口的影响**：新增 `RagProperties`/`RagExecutorConfig`、`service/llm/ChatMessage`、`ChatCompletionClient`/`QwenChatClient`、`RagPromptBuilder`、`RagService(Impl)`、`RagController`；`SecurityConfig` 放行 `GET /api/products/qa`；`application.yml` 增 `rag.*`（qwen key 复用 `DASHSCOPE_API_KEY`）。**零新增 Maven 依赖、无数据库迁移**。SSE 事件协议：`products`→`answer`*→`done`，异常→`error`。

## 十一、AI 导购 Agent + 生产化护栏（AI-3，模块十六）

### 59. 手写 Agent 循环而非 Spring AI / LangChain4j

**决策**：`AssistantAgentService` 完全手写非流式工具轮（LLM → `tool_calls` → `ToolRegistry.execute` → 回填结果）与流式最终轮（`streamFinal`），不引入 Spring AI 或 LangChain4j 框架。最大轮数 `maxRounds=5`，超出推 SSE `error`；客户端断开（`SseEmitter.onCompletion`）通过每请求局部 `AtomicBoolean` 标志短路剩余轮次。

**原因**：① Spring AI / LangChain4j 抽象层不稳定（API 仍频繁变动），本项目以「学会自己实现 Agent 循环」为核心学习目标，手写比框架更透明可控。② 既有 `QwenAgentChatClient`（OpenAI 兼容 tools API）和 `SseEmitter` 体系完全足够，引框架徒增依赖与 Spring 版本兼容风险。③ 可插拔设计（`AgentChatClient` 抽象）与框架等价，未来如需切框架阻力更小。

### 60. 工具集 spec 7 个 → 实现 6 个（移除 `preview_coupon`）

**决策**：实现 6 个工具——4 个公开只读（`search_products`/`get_product_detail`/`check_stock`/`list_claimable_coupons`）+ 2 个个人数据工具（`get_my_orders`/`list_my_coupons`）；**移除** spec 原计划的 `preview_coupon`（下单前优惠试算）。个人数据工具在工具执行层强制 `ctx.userId()` 过滤，LLM 无法传入他人 userId，从根本上防越权。

**原因**：① `preview_coupon` 要求同时传购物车商品列表与券 ID 列表，参数结构复杂，LLM 在自然语言导购场景中几乎不会产生这一精确调用，工具价值低；移除后剩余 6 个工具已覆盖「商品查询→库存确认→查券→查历史订单→查我的券」完整导购链路。② 6 个工具的 `AgentMessage` JSON 更短，减少 token 消耗并降低工具选择幻觉概率。

### 61. 限流选 Redis Lua 固定窗口，不引入 Bucket4j

**决策**：`RateLimitUtil` 用 `StringRedisTemplate.execute(RedisScript)` 跑 Lua 脚本（INCR + 首次设 EXPIRE，原子）实现固定窗口令牌桶；`RateLimitInterceptor` 拦截三个 AI 端点（`/api/assistant/chat`、`/api/products/qa`、`/api/products/semantic`）；登录用户按 `userId`、游客按 `X-Forwarded-For`/`remoteAddr`；超限抛 `BusinessException(429, …)` → `GlobalExceptionHandler` 转 `{code:429}`（HTTP 200，项目既有约定）；阈值 `ratelimit.ai.limit:20`/`window-seconds:60`。

**原因**：① Lua + Redis 既有栈（`StringRedisTemplate` 已在项目中），零新增依赖，INCR+EXPIRE 两步原子即实现固定窗口。② Bucket4j 滑动窗口精度更高，但需额外引入 `bucket4j-core` 或 `bucket4j-redis`，且学习曲线更陡；固定窗口对导购场景已足够（20 req/min 是防滥用而非精细流量整形）。③ 与既有 `RedisLockUtil`（`SET NX EX`）同思路、同风格，保持项目一致性。

### 62. Resilience4j 熔断/重试串联关键词搜索降级

**决策**：给 `TongyiEmbeddingClient.embed` 加 `@CircuitBreaker(name="aiEmbedding")+@Retry(name="aiEmbedding",maxAttempts=2)`，fallback 方法返 `float[0]`；`SemanticSearchServiceImpl` 收到空向量时 Qdrant 返 HTTP 400 → catch → 降级调 `productService.searchProducts` 关键词搜索。给 `QwenAgentChatClient` 三个方法（`chat`/`streamFinal`/`streamChat`）加 `@CircuitBreaker(name="aiLlm")`，fallback 抛 `IllegalStateException`，上层 `AssistantAgentService` catch 后推 SSE `error`。**不给 LLM 加 `@Retry`**，避免应用启动时报 `NoSuchRetryConfigException`（未配 `aiLlm` retry instance）。

**原因**：① embedding 短暂失败值得重试（`maxAttempts=2`），重试后仍失败才触发降级，降级链保留（不会完全不可用）。② LLM 超时/失败重试代价高（每次调用耗时大、token 费用高），加上 SSE 已打开，重试会让前端长时间无响应，故 LLM 路径只熔断不重试，快速失败推 error 更合适。③ embedding fallback 返 `float[0]` 而非直接 throw 的选择：`SemanticSearchServiceImpl` 已有 try/catch 全包含 Qdrant 调用，`float[0]` → Qdrant 400 → catch → 关键词降级，无需改动降级链；代价是降级触发依赖 Qdrant 行为（见 Task 9 Minor M1）。

### 63. Actuator 暴露面收窄 + `hasAuthority` 鉴权（非 `hasRole`）

**决策**：`management.endpoints.web.exposure.include=health,prometheus`（仅暴露这两个端点，health show-details=never）；`SecurityConfig` 中 `/actuator/health` 用 `permitAll()`，`/actuator/**` 用 `hasAuthority("ADMIN")`（**不是** `hasRole("ADMIN")`），令 `/actuator/prometheus` 仅 ADMIN 可访问。

**原因**：① 只暴露必需端点（health 给 Kubernetes/负载均衡就绪探针、prometheus 给 Prometheus 抓取），其余端点（env/beans/mappings 等）含敏感配置，默认关闭。② `hasAuthority("ADMIN")` 而非 `hasRole("ADMIN")`：`JwtAuthenticationFilter`（`JwtAuthenticationFilter.java:59`）以 `new SimpleGrantedAuthority(role)` 存储裸角色串（如 `"ADMIN"`，无 `"ROLE_"` 前缀），`hasRole("ADMIN")` 内部会查 `"ROLE_ADMIN"` 导致鉴权恒拒；`hasAuthority("ADMIN")` 按原始串比较，与 JWT payload 一致。此决策与全项目其他角色校验方式（Service 层 `AuthUtil.requireRole` 用字符串比较）保持一致，风格统一。
