# 第一部分：推荐算法

## 1. 推荐系统在解决什么问题

商城商品成千上万，用户不可能逐页翻。推荐系统的目标：**在合适的位置，把用户最可能感兴趣的少量商品挑出来呈现**。常见展示位：

- 商品详情页「相关推荐 / 买了又买」——给定一个商品，推相似商品
- 首页「猜你喜欢」——给定一个用户，推个性化商品
- 购物车页「凑单推荐」、下单后「搭配购买」等

衡量好坏的核心不是"算得准"这种感觉，而是能不能提升**点击率、转化率、客单价**。但作为练手，我们先把"能产出合理推荐"作为目标。

---

## 2. 主要流派一览

| 流派 | 核心思想 | 依赖的数据 | 适合本项目？ |
|---|---|---|---|
| **协同过滤 CF**（item-based / user-based） | 只看"谁和什么发生过交互"，靠群体行为找规律 | 用户-商品交互（订单） | ✅ 路线图选的方向 |
| **基于内容 Content-based** | 看商品自身属性，推同类目/同标签 | 商品元数据（类目、店铺） | ⭐ 适合做冷启动兜底 |
| **矩阵分解 MF**（SVD/ALS） | 把"用户×商品"稀疏矩阵分解成隐向量做预测 | 大量评分数据 | ❌ 工程偏重，杀鸡用牛刀 |
| **深度学习 / 召回-排序** | 多级流水线（召回→粗排→精排→重排） | 海量数据 + 算力 | ❌ 超出本项目范围 |

下面只深入和我们相关的两类。

### 2.1 协同过滤 CF —— 经典主力

核心特征：**不关心商品"是什么"，只关心"谁买过它"**。

**(a) 基于物品 Item-based CF**（我们要做的）
- 一句话："买了 A 的人也常买 B" ⟹ A 和 B 相似 ⟹ 给买过 A 的人推 B。
- 把每个商品表示成"买过它的用户集合"，两个集合重叠越多越相似。

**(b) 基于用户 User-based CF**
- 一句话："和你口味相似的人买了 X" ⟹ 推 X 给你。
- 先找"邻居用户"，再推他们买过而你没买的。

> **为什么电商几乎都用 item-based 而不是 user-based？**（亚马逊那篇经典论文的核心论点）
> 1. **物品相似度变化慢**：商品集合稳定，相似度可以**离线预计算**存好，线上查表即可，极快。
> 2. **用户相似度变化快**：用户多、行为天天变，线上算不动。
> 3. 所以工业界的范式是「**离线算好物品相似度矩阵 → 线上查表**」。
>
> 这正是路线图选 item-based、以及我们"先做物品相似度引擎、再叠加个性化"的原因。

### 2.2 基于内容 Content-based —— 冷启动救星

- 看商品属性：你买过"科幻小说" → 推同类目其他书。本项目对应 `categoryId` / `storeId`。
- **优点**：新商品只要有类目就能被推，解决"物品冷启动"（新品没人买过，CF 无能为力）。
- **缺点**：推荐单调，永远在一个类目打转，发现不了"啤酒+尿布"式跨类目惊喜。
- 实战常把它作为 **CF 结果不足时的兜底**，而非主力。

---

## 3. Item-based CF 的三步拆解（核心）

```
① 建共现：扫订单，统计"商品 A 与商品 B 被同一用户买过几次"（共现次数）
② 算相似度：把共现次数归一化，得到 0~1 的相似度（压制热门商品偏差）
③ 存与查：每个商品的 Top-N 相似商品离线算好存起来，线上直接查表
```

### 3.1 相似度公式：为什么不能只看"共现次数"

直接用共现次数有个致命问题：**热门商品（如可乐）几乎和所有东西共现**，于是它和谁都"相似"，污染所有推荐结果。解决办法是**归一化**——除以两个商品各自的热度。常用两个公式：

**余弦相似度（Cosine）**

把商品看成"用户向量"（买过=1，没买=0）：

```
sim(A,B) = 共同买过A和B的人数 / ( √买过A的人数 × √买过B的人数 )
```

**Jaccard 相似度**（更直观，适合只有"买/没买"的隐式数据）：

```
sim(A,B) = 同时买过A和B的人数 / 买过A或B的人数（并集）
```

两者都把"热门"放到分母里压制：可乐买的人多，分母大，相似度自然被拉低。

### 3.2 手算一遍（建立直觉）

假设 4 个用户买了 4 个商品（✓ = 买过）：

| 用户 \ 商品 | 手机 | 手机壳 | 数据线 | 咖啡 |
|---|---|---|---|---|
| 张三 | ✓ | ✓ | ✓ | |
| 李四 | ✓ | ✓ | | ✓ |
| 王五 | ✓ | | ✓ | |
| 赵六 | | | | ✓ |

**问：和"手机"最相似的是谁？** 用 Jaccard 算：

- 买过手机的人：{张三, 李四, 王五}（3 人）
- **手机 vs 手机壳**：都买的 {张三,李四}=2；买过其一的 {张三,李四,王五}=3 ⟹ 2/3 ≈ **0.67**
- **手机 vs 数据线**：都买的 {张三,王五}=2；并集 {张三,李四,王五}=3 ⟹ 2/3 ≈ **0.67**
- **手机 vs 咖啡**：都买的 {李四}=1；并集 {张三,李四,王五,赵六}=4 ⟹ 1/4 = **0.25**

**结论**：手机的相似商品排序 = 手机壳 / 数据线（并列 0.67）> 咖啡（0.25）。
所以用户看"手机"详情页时，推「手机壳、数据线」，符合直觉。咖啡虽然和手机共现过 1 次（李四），但因为咖啡总体买的人也多（赵六也买），被归一化压低了 —— **这就是分母在起作用**。

### 3.3 第③步：存哪儿、怎么查

- **离线计算**：定时任务（如每天凌晨）扫全量订单，算出每个商品的 Top-N（如 Top 10）相似商品，结果是一张"商品 → 相似商品列表"的表。
- **存储选项**：①写一张数据库表 `product_similarity(product_id, similar_product_id, score)`；②或写进 Redis（`ZSET`，天然按 score 排序）。本项目 Redis 已接入，查表成本低。
- **线上查询**：用户请求"商品 X 的相关推荐" → 直接读预存结果，O(1)~O(logN)，不做实时计算。

## 4. 一定会遇到的四个真实问题

| 问题 | 说明 | 常见对策 |
|---|---|---|
| **冷启动（新商品）** | 新品没人买过，没有共现数据，CF 推不出来 | 用 content-based 兜底：推同类目热销 |
| **冷启动（新用户）** | 新用户没历史，个性化"猜你喜欢"无从下手 | 兜底推全站/类目热销榜 |
| **热门商品偏差** | 爆款和谁都共现，污染结果 | 相似度公式的归一化（见 3.1） |
| **在线 vs 离线** | 实时算相似度数据量大时算不动 | 离线预计算 + 线上查表（推荐） |

还有一个选型问题：**用什么交互信号？**（本项目最终方案见第 7 节）

- 候选信号：订单（最强，真金白银）、购物车（加了不一定买）、评分（`review.rating`，数据量小先不用）。
- 本项目最终决定**用订单**，且**全部下单状态都纳入但按状态加权**（详见第 7 节），而非简单地"只留已完成、过滤掉取消"。

| 信号 | 来源 | 用途 |
|---|---|---|
| 用户-商品交互 | `orders`(userId, status) + `order_item`(productId) | **CF 共现矩阵的原料**（核心） |
| 商品类目 | `product.categoryId` | content-based 兜底、同类目补位 |

**最小可用方案雏形**（待 brainstorm 定稿）：
1. 离线 `@Scheduled` 任务扫 `order_item` join `orders`(status 有效) → 算商品两两 Jaccard/余弦 → 存 Top-N。
2. 接口 A `GET /api/products/{id}/recommendations` → 查表返回；不足则同类目热销补位。
3. 接口 B `GET /api/recommendations`（个性化）→ 取用户买过的商品 → 对每个查 A 的相似集 → 加权聚合去重（排除已买）→ 返回；新用户兜底热销。

## 6. 在线 vs 离线，以及结果存哪里（架构决策）

### 6.1 离线预计算 + 线上查表

相似度计算放**离线**（定时任务算好存起来），线上只**查表**。

- 为什么不在线实时算：商品两两比较是 O(商品数²) 级，放在请求路径上数据稍多就超时。
- 物品相似度是**慢变量**（今天几笔新订单几乎不改变整体相似度），所以"有延迟"完全可接受——这正是 item-based CF 成为电商主力的根本原因：**把贵的计算挪到请求路径之外**。

### 6.2 关键概念：派生数据（derived data）与真相来源（source of truth）

相似度矩阵不是原始数据，它是**从订单算出来的派生数据**。订单在 MySQL 里本就持久化，所以：

> **相似度结果丢了也无所谓——随时能从订单重算。** 真正要决定的不是"怎么持久化 ZSET"，而是"**把哪一层当作持久的真相来源**"。

这个视角能避免一个常见误区：以为缓存里的数据需要"备份保存"。其实**只要原始数据还在，任何派生/缓存数据都能重建**，不必单独备份。

### 6.3 三种存储方案对比

| 方案 | 真相来源 | 关机后 | 评价 |
|---|---|---|---|
| A. 只用 Redis ZSET | Redis | ❌ 丢失需重算 | 关机即没 |
| B. 只用 MySQL 表 | MySQL 表 | ✅ 自然持久 | 加索引查 Top-N 也快，最简单 |
| **C. MySQL 表（真相）+ Redis ZSET（缓存）** | MySQL 表 | ✅ 表持久，ZSET 可重建 | **本项目选用**，多级缓存 |

**本项目选 C**：MySQL 表 `product_similarity` 作持久真相来源，Redis ZSET 作热读缓存。这就是大厂常见的**多级缓存（multi-level cache）**思路——慢但持久的底层（DB）+ 快但易失的上层（Redis）。

### 6.4 多级缓存的读写套路（避免踩坑）

- **写**：离线任务**直接把结果写进 MySQL 表**——这一步本身就是"持久化"，**不需要再开一个"把 ZSET 另存"的任务**（那等于绕一圈还要处理两任务时序）。写表后可顺手刷新 ZSET。
- **读（read-through / 缓存未命中回源）**：先查 Redis ZSET；未命中（如刚重启、Redis 被清）→ 回 MySQL 表查 → 回填 ZSET → 返回。这样关机清空 Redis 后，第一次请求自动从表重建缓存，无需手动预热。
- **数据量小时 B 也够用**：`SELECT ... WHERE product_id=? ORDER BY score DESC LIMIT N` 配 `INDEX(product_id, score)` 毫秒级。上 Redis 是为了练多级缓存 / 应对未来热点，属于**可平滑升级**的优化，不是必需。

> 补充：Redis 自身**能**持久化（RDB/AOF 落盘），但依赖 Redis 配置、且开发机会主动关它——**把 MySQL 表当真相来源比依赖 Redis 持久化更可靠、更简单**。

### 6.5 ZSET 为什么适合存相似度

Redis 的 `ZSET`（有序集合）每个成员带一个 score，**天然按 score 排序**。把"商品 X 的相似商品"存成一个 ZSET（成员=相似商品 id，score=相似度），查 Top-N 就是一条 `ZREVRANGE key 0 N-1`，O(logN)，不用自己排序。键设计形如 `rec:sim:{productId}`。

## 7. 信号定义：共现口径与状态加权（本项目决策）

### 7.1 共现口径：同一用户跨订单（口径一）

"共同买过 A 和 B"有两种定义：

| 口径 | 定义 | 语义 | 数据密度 |
|---|---|---|---|
| **① 同一用户跨订单**（本项目选） | 同一用户在**任何时候**买过 A 也买过 B | "买了又买 / 相关推荐" | 较密（全部历史参与） |
| ② 同一订单/购物篮 | 必须在**同一笔订单**里同时出现 | "搭配购买 / 凑单"（啤酒+尿布） | 较稀疏 |

**本项目选口径①**：更贴合"相关推荐/猜你喜欢"语义；且订单量不大时口径①数据更密、相似度更稳。
SQL 实现 = `order_item` 按 `userId` 自连接，拿到"同一用户买过的商品对"再 `GROUP BY` 聚合。

### 7.2 状态加权：兴趣信号 ≠ 满意信号

一个关键辨析：**"下单"本身就是被行为证明过的兴趣**（走完了购物车→结算），比单纯浏览强得多。所以下过单的都该纳入。

但**不能一视同仁**——`CANCELLED` 是个"混合袋"：有"买错了/重复了/改主意了"的**后悔（负信号）**，尤其本项目**任务 1 会把未付款超 14 天的单自动置为 `CANCELLED`**，那其实是"弃单"，是最弱的信号。若把弃单和真实购买都按 1 次共现算，会稀释相似度质量。

**解决办法——按状态加权**（恰好用上了"选余弦而非 Jaccard"留下的加权口子）：

| 状态 | 含义 | 权重 |
|---|---|---|
| `COMPLETED` / `SHIPPED` / `PAID` | 真金白银买了 | **1.0** |
| `PENDING_PAYMENT` | 下单未付（有意图，未承诺） | **0.5** |
| `CANCELLED` | 下单后取消（兴趣存在但被反转/弃单） | **0.3** |

> 这就是为什么前面**选余弦而不选 Jaccard**——Jaccard 基于集合的交并，天然只认"买/没买"二元，要加权就得换公式；余弦基于向量点积，把"次数=1"换成"权重=0.x"即可平滑支持。**v1 就把这个口子用上了**，是个完整闭环。

### 7.3 加权后的余弦怎么算

原来余弦分子是"共同买的人数"，现在每个用户对某商品的贡献不再是 1，而是**该用户在该商品上所有相关订单的状态权重之和**（或取最大值，二选一，实现时定）。分子 = 两商品共同用户的权重乘积之和，分母 = 各自权重平方和的根。本质就是把"0/1 向量"换成"加权向量"，余弦公式形式不变。

## 8. 冷启动兜底与热销榜

CF 在"没数据"时无能为力，必须有兜底，保证任何情况下推荐位都不空白。核心原则：**先 CF，不足用规则补位**。

### 8.1 两类冷启动各自的兜底

| 接口 | 冷启动场景 | 兜底 |
|---|---|---|
| A 相关推荐 | 新商品没人买过 / 相似结果不足 N 个 | **同类目热销**（`categoryId` 相同，按销量排序）补位 |
| A 相关推荐 | 商品连类目数据都没有 | 退到**全站热销榜** |
| B 个性化 | 新用户无购买历史 / 聚合不足 | **全站热销榜** |

兜底分层：`CF 结果 → 同类目热销 → 全站热销`，逐层补足到 N 个。这就是 content-based（同类目）+ 热销榜作为 CF 兜底的典型用法。

### 8.2 热销榜也是派生数据

"热销榜"同样从订单算出，可由**同一个离线任务顺带产出并存好**（全站一份 + 每类目一份）。

- **口径**：用**成交件数 `SUM(quantity)`** 排序，比"下单次数 `COUNT`"更反映真实热度（一单买 10 件 ≠ 一单买 1 件）。
- 同样遵循多级缓存：写 MySQL（或复用商品表统计）+ Redis 缓存。

### 8.3 排除已购

- **接口 B（个性化）排除用户已购**：给用户推他已买过的通常无意义。聚合候选后，用用户的订单历史商品集合做差集。
- **接口 A（相关推荐）不排除**：A 是逛某商品时的相关展示，不针对个人，"看手机推手机壳"即使用户买过手机壳也合理。
- （快消品复购场景是例外，v1 不特殊处理。）

## 9. 接口形态与离线任务（本项目决策）

### 9.1 两个推荐接口

| | A：商品相关推荐 | B：个性化猜你喜欢 |
|---|---|---|
| 路径 | `GET /api/products/{productId}/recommendations` | `GET /api/recommendations` |
| 入参 | `productId` + `limit`(默认 10) | `limit`(默认 10)，userId 从 JWT 取 |
| 鉴权 | **开放**（同商品浏览，进 `SecurityConfig` 开放 GET 白名单） | **需登录** |
| 排除已购 | 否 | 是 |
| 返回 | 复用现有商品摘要 DTO（id/名称/价格/图片） | 同左 |

> v1 单商品入参；"购物车搭配推荐（多 productId）"按 YAGNI 暂不做。
> B 的逻辑 = 取用户买过的商品 → 对每个查 A 的相似集 → **加权聚合去重**（按相似度累加）→ 排除已购 → 取 Top-N，不足热销补位。

### 9.2 离线任务

- **定时**：`@Scheduled(cron)` **每天凌晨 3:00** 跑一次（低峰期、相似度慢变量一天内几乎不变）。复用任务 1 已启用的 `@EnableScheduling`。
- **手动触发**：额外加 Admin 接口 `POST /api/admin/recommendations/rebuild`，方便本地调试/演示时立即重算，不必改系统时间等到凌晨。
- 任务职责：扫订单 → 算加权余弦相似度 → 写 `product_similarity` 表 + 刷 Redis ZSET；顺带算全站/分类目热销榜。

### 9.3 一个通用工程经验

推荐这类**离线批处理**任务，**务必同时提供"手动触发"入口**（接口或命令）。否则开发期想看效果只能干等定时器、或被迫改系统时间，调试体验极差。这条经验对任何 cron 驱动的功能都适用。

# 第二部分：实时客服（WebSocket / STOMP）

> 本部分对应已实现的任务 7。先讲通用原理，再对应到本项目实际代码与踩过的坑。

## 1. 为什么普通 HTTP 不够用

HTTP 是**请求-响应**模型：客户端问一次，服务端答一次，然后连接就完了。**服务端无法主动推送**。聊天要求"对方发消息时我立刻收到"，用 HTTP 只能：

- **轮询（polling）**：每隔 N 秒问一次"有新消息吗"——浪费、有延迟。
- **长轮询（long polling）**：请求挂住直到有消息才返回——勉强能用但笨重。

根本矛盾：**HTTP 是半双工、服务端被动**。聊天需要**全双工、服务端能主动推**。这就是 WebSocket 的用武之地。

## 2. WebSocket：建立一条双向常连接

- WebSocket 是一个**独立协议**（`ws://` / `wss://`），但**借用 HTTP 完成握手**：
  - 客户端发一个带 `Upgrade: websocket` 头的 HTTP 请求（"协议升级"）。
  - 服务端同意后，这条 TCP 连接**从 HTTP 切换成 WebSocket**，之后双方都能随时发帧。
- 握手之后就是一条**长期保持、双向**的管道，服务端可主动 push。

> 本项目握手端点 `/ws`（`WebSocketConfig`）。`SecurityConfig` 放行 `/ws/**` 握手，因为真正的鉴权在后面的 STOMP CONNECT 帧做，不走 servlet 安全链。

## 3. STOMP：在 WebSocket 之上加"信封格式"

裸 WebSocket 只能传字节流，**没有"这条消息发给谁、是什么类型"的概念**——这些都得自己定义。STOMP（Simple Text Oriented Messaging Protocol）是一个轻量文本协议，给消息加了**类似 HTTP 的帧结构**：

```
SEND                       ← 命令（CONNECT / SUBSCRIBE / SEND / MESSAGE ...）
destination:/app/chat...   ← 头（发往哪个目的地）
Authorization:Bearer xxx   ← 头（可带鉴权）

{"content":"你好"}          ← 消息体
```

有了 STOMP，就能用**"目的地（destination）"+"订阅（subscribe）"**这套发布-订阅模型，而不用自己造轮子。Spring 原生支持 STOMP over WebSocket。

### Spring 的四个前缀（消息路由的关键）

| 前缀 | 方向 | 含义 | 本项目用法 |
|---|---|---|---|
| `/app` | 客户端→服务端 | 发给 `@MessageMapping` 处理方法 | `/app/chat.customer.send`、`/app/chat.staff.send` |
| `/topic` | 服务端→多客户端 | **广播**，所有订阅者都收到 | `/topic/store.{storeId}` 全店客服 |
| `/queue` + `/user` | 服务端→单客户端 | **点对点**，按 principal 隔离 | `/user/queue/messages` 私信、`/user/queue/errors` 错误 |
| broker | — | 内存 `SimpleBroker`（单实例，无需 RabbitMQ） | — |

`convertAndSend("/topic/...")` = 广播；`convertAndSendToUser(userId, "/queue/...")` = 定向投递给某人（Spring 按 principal 自动隔离，A 收不到 B 的）。

## 4. WebSocket 上怎么做鉴权（和普通接口不一样）

普通 REST 接口：`JwtAuthenticationFilter` 在 **servlet 请求线程**解析 JWT，填进 `SecurityContextHolder`。

WebSocket 不一样：握手是一次性的，之后是长连接，**消息处理在专用线程池**，`SecurityContextHolder` 是空的。本项目的方案：

- **在 STOMP CONNECT 帧鉴权**：客户端 CONNECT 时带 `Authorization: Bearer <jwt>` 头。
- `StompAuthChannelInterceptor`（注册在 client inbound channel）拦截 CONNECT 帧，验 JWT，通过后绑定 `ChatPrincipal`（`getName()` 返回 userId）作为这条连接的"身份"。
- 之后每条消息处理方法签名带 `Principal principal`，就能拿到当前用户身份。

> **🔴 踩过的坑（决策 #51）：WS 线程无 SecurityContext**
> 一开始在 WS 处理器里直接调 `AuthUtil.requireRole()`（它读 `SecurityContextHolder`），结果 WS 线程里 SecurityContext 是空的 → 误判 401。
> **修复**：新增 `AuthUtil.requireRole(AuthUser, roles...)` 重载，对**显式传入的 AuthUser**校验角色，不读 SecurityContext。WS 路径从 `ChatPrincipal` 取出 `AuthUser` 传进去；REST 路径仍走读 SecurityContext 的老方法。两条路统一传 `AuthUser`，无全局副作用。

## 5. 会话归属：认领制（claim/pull）

> 决策 #50 的核心，值得单独理解，因为这是"客服系统"区别于"群聊"的地方。

需求：**一个买家固定对接一个客服，客服之间不撞单**。三种成熟模型：

| 模型 | 运作 | 取舍 |
|---|---|---|
| ① 共享收件箱 | 全员看到全部，谁有空谁回 | 简单，但易重复回复、无专属感 |
| ② **认领制**（本项目选） | 新会话进店铺公共池，客服手动"接入"后归他 | 平衡之选 |
| ③ 自动路由 | 引擎按在线+负载自动派单 | 强大但是个派单子系统，v1 偏重 |

**为什么不用最直觉的"哈希分配"（`customerId % 客服数`）？** 三个硬伤：
1. 哈希按"人数"均衡，但聊天负载看的是"强度"——有人狂聊有人发一句就走，负载失衡。
2. 哈希无状态，**看不到谁在线**——客服下班，分到他名下的客户无人接。
3. 客服数一变，`% N` 的 N 变，几乎所有会话重新分配、正聊的串线。

根因：**哈希是"无状态反复算"的，而在线状态/负载是动态的**。成熟做法是"**算一次、把归属持久化**"——本项目用 `chat_session.assignee_staff_id` 落库。

**认领的并发安全**（决策 #51）：用一条**原子 UPDATE** 防两个客服同时接入：

```sql
-- 接入：影响 0 行 = 已被他人接待
UPDATE chat_session SET assignee_staff_id=#{me} WHERE id=? AND assignee_staff_id IS NULL
-- 释放：影响 0 行 = 非本人持有（403）
UPDATE chat_session SET assignee_staff_id=NULL WHERE id=? AND assignee_staff_id=#{me}
```

## 6. 消息怎么路由（按归属决定广播还是点对点）

```
买家发消息 /app/chat.customer.send
  → 落库 chat_message
  → 会话未接入(assignee 为 null)：广播到 /topic/store.{storeId}，全店客服可见（StoreTopicEvent{MESSAGE}）
  → 会话已接入：convertAndSendToUser(归属客服, /queue/messages) 点对点投递

客服发消息 /app/chat.staff.send（须为 assignee，否则 403）
  → 落库 → convertAndSendToUser(买家, /queue/messages)
```

推送到店铺主题的事件统一用**信封对象** `StoreTopicEvent{type, sessionId, ...}`，`type` 区分 `MESSAGE`（新消息）/`CLAIMED`（已被接入）/`RELEASED`（已释放），让前端待接入列表能实时更新。

> **🔴 踩过的坑（决策 #51）：推送必须在事务提交后**
> 发消息方法是 `@Transactional`（落库消息 + 更新会话）。如果在事务**提交前**就 STOMP 推送，会出现竞态：买家首条消息会**在同一事务里新建会话**并广播携带 `sessionId`；客服收到后立刻用该 `sessionId` 调 REST `claim`/`getMessages`（独立事务、MySQL 默认 REPEATABLE READ），此时会话行**还没提交**，读不到 → 偶发 404。
> **修复**：用 `TransactionSynchronizationManager` 把推送注册成 `afterCommit` 回调，事务提交后才发；无事务时（纯单测）立即执行。

## 7. 在线状态：Redis Set

- `WebSocketPresenceListener` 监听 Spring 内置的 `SessionConnectedEvent` / `SessionDisconnectEvent`。
- 连接成功 → `SADD` 到对应 Set；断开 → `SREM`。两个 Set：
  - 买家：`cs:online:customers`（成员 = userId）
  - 客服：`cs:online:store:{storeId}`（成员 = userId）
- 会话列表接口**内联**返回对端是否在线：
  - 买家视角：`SCARD cs:online:store:{storeId} > 0`（本店有无客服在线）
  - 客服视角：`SISMEMBER cs:online:customers {customerId}`（该买家是否在线）

## 8. 已知限制（决策 #51 记录的技术债）

1. **接待会话超时自动释放**：客服掉线是"粘性"（assignee 不变），目前只支持手动 release，须补计划任务避免买家长期挂在失联客服名下。
2. **STOMP 拒绝未发 ERROR 帧**：鉴权失败时拦截器抛异常拒绝（安全成立），但未注册 `StompSubProtocolErrorHandler`，客户端收不到结构化 ERROR 帧，可诊断性弱。
3. **在线状态脏数据**：进程异常退出可能漏发 DISCONNECT，留少量"显示在线实际已断"的脏数据，后续用心跳 TTL 兜底。

## 附：两块知识的共同点

虽然推荐和客服八竿子打不着，但都体现了同一类工程权衡：

- **离线预计算 vs 线上实时**：推荐把相似度离线算好查表；客服把在线状态用 Redis 维护好查表。都是"**把贵的计算挪到请求路径之外**"。
- **状态持久化优于反复计算**：客服归属落库而非反复哈希；推荐结果存表而非每次重算。
- **兜底很重要**：推荐有冷启动兜底；客服有离线粘性 + 重连补历史。
