# 数据库迁移指南（Flyway）

本项目使用 **Flyway** 管理数据库结构与种子数据。应用启动时自动执行迁移，**不再手动跑 SQL**。

---

## 目录与文件

```
src/main/resources/db/migration/
├── V1__init_schema.sql    # 版本化迁移：建 12 张表（DDL）
└── R__seed_data.sql       # 可重复迁移：测试商店/账号/分类/商品（种子）
```

- **版本化迁移 `V{n}__描述.sql`**：按版本号从小到大、每个**只执行一次**，执行记录写入 `flyway_schema_history` 表。
- **可重复迁移 `R__描述.sql`**：无版本号，在所有版本化迁移**之后**执行，仅当文件内容（checksum）变化时重跑。本项目用它承载种子数据，脚本开头会先清空相关表再插入，因此可安全重复执行（**仅限开发/测试库**）。

---

## 配置（application.yml）

```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: true   # 兼容「已建表但无 flyway 历史」的存量库
    baseline-version: 1         # 基线到 V1：存量库跳过建表、只补跑 R__；空库正常从 V1 跑
    encoding: UTF-8
```

## 首次启用 / 推荐重建流程

存量库（手动建过表、没有 `flyway_schema_history`）虽可借 `baseline-on-migrate` 兼容，但**最干净的是用空库让 Flyway 从头接管**：

```sql
DROP DATABASE IF EXISTS bluewhale;
CREATE DATABASE bluewhale DEFAULT CHARSET utf8mb4;
```

然后启动应用，Flyway 自动执行 `V1` 建表 + `R__` 灌种子。完成后用 `13000000000 / Admin@123456` 即可登录管理员。

## 日常操作

### 1. 改了表结构（加字段 / 改表）

**不要改已发布的 `V1`**（Flyway 会校验 checksum，改动已应用脚本会导致启动报错 `Migration checksum mismatch`）。

新增一个版本号更大的脚本，只写**增量 DDL**：

```sql
-- src/main/resources/db/migration/V2__add_xxx_column.sql
ALTER TABLE product ADD COLUMN brand VARCHAR(50) NULL COMMENT '品牌';
```

下次启动，Flyway 只执行尚未应用的 `V2`，已有数据不丢。

> 同步规则：实体（Entity）加了映射列，就要配一条对应的 `V{n}` 迁移，否则运行库会缺列报 `Unknown column`。这正是引入 Flyway 要根除的问题。

### 2. 改种子数据

直接编辑 `R__seed_data.sql` 并重启应用。checksum 变化后 Flyway 会重新执行它（先清空相关表再插入）。

### 3. 查看迁移状态

库里 `flyway_schema_history` 表记录了每条迁移的版本、checksum、执行时间、是否成功。

## 常见报错

| 报错 | 原因 | 解决 |
|---|---|---|
| `Migration checksum mismatch for migration version 1` | 改动了已应用的 `V1` | 还原 `V1`，把变更挪到新的 `V2`；或开发库 `flyway clean` 后重来 |
| `Found non-empty schema(s) ... without schema history table` | 存量库无 flyway 历史且未开基线 | 已配 `baseline-on-migrate: true` 应不再出现；否则手动建库重来 |
| 启动时 `Table 'xxx' already exists` | 非空库被当成空库重跑 `V1` | 确认 `baseline-version: 1`，或改用空库 |
