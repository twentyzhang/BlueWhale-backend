# Claude Code 上手指南

每次新会话开始时，按以下顺序阅读文件，5 分钟内掌握项目全貌。

---

## 第一步：必读文件（按顺序）

| 顺序 | 文件 | 目的 |
|---|---|---|
| 1 | `CLAUDE.md` | 技术栈、包结构、常用命令 |
| 2 | `docs/进度.md` | **当前开发进度**，哪些模块已实现、哪些是 stub |
| 3 | `docs/重要决策说明.md` | 历史技术决策（**为什么**这样做），避免重复讨论 |
| 4 | `docs/实现说明.md` | 已实现模块的业务逻辑细节和关键算法（**怎么做**的） |
| 5 | `docs/debug记录.md` | 已踩过的坑与解决方案（**编写测试前必读**） |

> 以上五个文件读完即可开始工作。需求和接口细节按需查阅：
> - `docs/requirements.md` — 功能需求
> - `docs/api-spec.md` — 完整接口规范
> - `docs/下一阶段路线图.md` — 后续开发的分阶段任务与推进顺序（开发新功能前先看）
> - `docs/数据库迁移指南.md` — Flyway 迁移机制（改表结构 / 种子前必看）
> - `docs/项目学习手册.md` — 面向初学者的深度导读（架构 + 关键代码 + PlantUML 流程图）。**讲解了核心功能的实现，改动核心功能后需同步对应小节，见下方文档义务。**
> - `docs/项目说明.md` — 一页纸的项目概览（对外介绍 / README 性质）

## 第二步：快速定位代码

```
src/main/java/com/twentyzhang/bluewhale/
├── controller/       # 路由入口，找接口从这里开始
├── service/          # 接口定义
├── service/impl/     # 业务实现（未完成的方法抛 UnsupportedOperationException）
├── entity/           # 数据库实体
├── mapper/           # MyBatis Plus Mapper
├── dto/              # 请求/响应 DTO
├── common/Result.java         # 统一响应封装（用这个，不用 dto/ApiResponse）
├── exception/                 # 全局异常处理
├── config/                    # Spring 配置
└── util/RedisUtil.java        # Redis 工具类
```

## 工作规范

### 修改代码后必须做的事

**每次完成一个方法或模块的实现后，同步更新 `docs/进度.md`：**
- 将对应行的"未实现"改为"完成"
- 更新文件顶部的"最后更新"日期

### 实现业务模块后必须做的事

**每次完成一个 Service 方法或模块的完整实现后，在 `docs/实现说明.md` 对应章节追加内容：**
- 执行流程（有顺序依赖的先后步骤）
- 关键算法或复杂查询逻辑
- 边界处理和错误场景（抛什么异常、为什么）

> 此文件记录"怎么做"，与 `重要决策说明.md`（记录"为什么"）互不重叠。
> 纯 bug 修复、代码格式调整无需更新。

---

### 改动核心功能后必须做的事（项目学习手册 / 项目说明）

`docs/项目学习手册.md` 与 `docs/项目说明.md` 是**面向人阅读的导读/概览**，不像 `实现说明.md` 那样事无巨细，因此**只在改动触及它们已写到的内容时才需同步**：

- **改了手册「五、核心实现」已讲解的功能**（如下单流程、库存乐观锁、优惠券锁、支付回调、缓存、JWT 鉴权、客服路由、推荐、定时任务）——若**架构、关键代码片段或流程图所示的步骤**发生变化，更新 `项目学习手册.md` 的对应小节（含其中的代码片段与 PlantUML 图）。
- **新增了一个值得初学者了解的核心功能/模块**——在手册「三、功能地图」补一个节点，并酌情新增一节「五、X」讲解（保持「问题 → 流程图 → 关键代码 → 提醒」结构）。
- **改动影响概览级事实**（模块数、接口数、技术栈、数据表、角色权限、暂未实现项）——同步 `项目说明.md` 对应表格。
- 手册中引用的是**真实代码片段**：若被引用的方法签名/逻辑改了，记得让片段与源码一致（手册顶部已声明个别片段为"简化/核心思想"，这类无需逐字对齐）。

> 判断标准：**问自己"初学者照着这份文档理解，会不会被我的改动带偏？"** 会，就更新；不会（纯内部重构、bug 修复、措辞调整），就跳过。

---

### 做出技术决策后必须做的事

**凡涉及以下情况，必须在 `docs/重要决策说明.md` 末尾追加新条目：**
- 选择了某个技术方案而非另一个（如选了 A 库而不是 B 库）
- 数据库表结构新增字段或修改设计
- 接口行为与 `docs/api-spec.md` 存在差异或做了补充约定
- 引入新依赖
- 绕过了某个约定或做了特殊处理

**条目格式（参考文件内已有格式）：**
```markdown
### N. 决策标题
**决策**：做了什么。
**原因**：为什么这样做。
```

### 不需要更新文档的情况
- 纯 bug 修复，行为与设计一致
- 代码重构，没有改变对外行为
- 测试代码变更
