## 一、JWT 认证基础设施

### JwtUtil
- `generateToken(userId, role, storeId)`：将三个字段写入 JWT Payload，使用 HMAC-SHA256 签名
- `getUserId / getRole / getStoreId`：从 Claims 中读取对应字段
- Staff 的 `storeId` 直接写在 Token 里，Filter 一次解析即可全程使用，避免每次请求重查数据库

### JwtAuthenticationFilter
执行流程：
```
请求 → 读取 Authorization Header
     → 不以 "Bearer " 开头 → 放行（Security 后续处理）
     → jwtUtil.isValid(token) 为 false → 放行
     → 解析出 userId / role / storeId
     → 构造 AuthUser record 作为 principal
     → 写入 SecurityContextHolder
     → 放行
```
Filter 只做解析，不做授权；授权逻辑由 `AuthUtil.requireRole / requireStoreAccess` 在 Service 层完成。

### AuthUtil
四个静态方法，均从 `SecurityContextHolder` 读取：

| 方法 | 行为 | 异常 |
|---|---|---|
| `getCurrentUser()` | 返回 AuthUser | 未登录 → 401 |
| `getCurrentUserId()` | 返回 userId | 未登录 → 401 |
| `requireRole(roles...)` | 校验角色在白名单中 | 不匹配 → 403 |
| `requireStoreAccess(storeId)` | 校验 Staff 的 storeId 与路径参数一致 | 不一致 → 403 |

角色常量（`ROLE_CUSTOMER / ROLE_STAFF / ROLE_ADMIN`）定义在 AuthUtil 内，避免引入 Enum 导致现有 String 字段需要大范围改动。

## 二、用户模块（UserServiceImpl）

### register
1. `selectByPhone` 查重 → 重复抛 400
2. `passwordEncoder.encode` 加密密码
3. `save` 写库（自增 ID 回写到 entity）

### login
1. `selectByPhone` 查用户 → 不存在或密码不匹配统一抛同一条消息（"手机号或密码不正确"，防枚举攻击）
2. `jwtUtil.generateToken` 生成 accessToken
3. `UUID.randomUUID()` 生成 refreshToken，存入 Redis（key: `refresh_token:{userId}`，TTL 7天）
4. 返回两个 token + 用户基本信息

### refreshToken
1. `redisUtil.get("refresh_token:" + userId)` 取 Redis 中保存的 refreshToken
2. 为 null（已过期/登出）或与请求体不一致 → 抛 401「refreshToken 无效或已过期」
3. `getById(userId)` 加载用户（取 role / storeId 以重建 JWT）；用户不存在 → 抛 401
4. `jwtUtil.generateToken` 签发新 accessToken；`UUID` 生成新 refreshToken
5. **轮换**：新 refreshToken 写回 Redis 并重置 7 天 TTL（旧值被覆盖即失效），返回 `{ token, refreshToken }`

> 失败一律 401（而非 400/404），让前端用同一套「跳登录」逻辑处理。轮换设计见决策第 41 条。

### getUserInfo
- 手机号脱敏规则：`phone.substring(0,3) + "****" + phone.substring(7)` → `138****8000`

### changePassword
执行顺序：**两次新密码一致校验 → 查用户 → 旧密码校验 → encode 新密码 → updateById**  
两次密码不一致是最早可以判断的错误，提前抛出避免多余的数据库查询。

## 三、商店模块（StoreServiceImpl）

### listStores / listAllStoresForAdmin
- 分页：`this.page(new Page<>(page, size))`
- `productCount`：对分页结果中的每条 Store，单独执行一次 `productMapper.selectCount(eq storeId)`
- 采用"二次查询"而非 JOIN，与决策文档第 16 条一致
- `listAllStoresForAdmin` 和 `listStores` 共用 `toListItem(store, includeCreditCode)` 辅助方法，布尔参数控制是否填充 `creditCode`

### createStore（Admin）
执行顺序：
1. `AuthUtil.requireRole(ROLE_ADMIN)`
2. `userMapper.selectByPhone(staffPhone)` → 不存在或角色不是 STAFF 抛 400
3. `save(store)` 写库（自增 ID 回写）
4. `staff.setStoreId(store.getId())` + `userMapper.updateById(staff)` 关联 Staff

整个方法加 `@Transactional`，store 写入和 staff 更新保证原子性。

### updateStore（Admin）
- 只更新请求体中非 null 的字段（`name / logo`），未传字段保持原值
- 先 `getById` 确认存在再 `updateById`，避免静默忽略不存在的 storeId

## 五、商品查询模块（ProductServiceImpl — 只读方法）

### createProduct — 鉴权 + 分类校验 + 写库

执行顺序：
1. `AuthUtil.requireRole(ROLE_STAFF)` → 确认角色
2. `AuthUtil.requireStoreAccess(storeId)` → 确认操作的是自己的店
3. `productCategoryMapper.selectById(categoryId)` → null 则抛 404
4. `save(product)` → 自增 ID 回写到实体，返回 `product.getId()`

### updateProduct — 局部更新，分类存在性按需校验

执行顺序：
1. 鉴权（同 createProduct）
2. `getById(productId)` → null 或 `product.storeId ≠ storeId` 均抛 404（防止越权操作他店商品）
3. `categoryId != null` 时才查分类是否存在（避免无谓的 DB 查询）
4. 只更新请求体中非 null 的字段，`updateById`

### deleteProduct — 两道守卫 + 二次查询检查活跃订单

执行顺序：
1. 鉴权 + 商品存在校验
2. 查 `order_item` 中 `product_id = productId` 的所有 orderId（select 只取 orderId 列）
3. 若 orderId 列表非空，查 `orders` 表中 status IN ('PENDING_PAYMENT','PAID','SHIPPED') 的数量
4. count > 0 → 抛 400，消息含具体数量和状态说明

活跃状态常量：`ACTIVE_ORDER_STATUSES = ["PENDING_PAYMENT", "PAID", "SHIPPED"]`

为什么不直接 JOIN：`BaseMapper` 不支持跨表 JOIN，二次查询（selectList + selectCount）走主键索引，性能等价，代码更清晰。整个方法加 `@Transactional` 确保删除前的状态检查与 `removeById` 在同一事务内不被并发修改干扰。

### updateStock — IN/OUT 分支 + 库存下限校验

```
type = IN  → newStock = currentStock + delta
type = OUT → if currentStock < delta: 抛 400（提示当前库存和出库数量）
             else: newStock = currentStock - delta
updateById → 返回 UpdateStockResponse(currentStock = newStock)
```

注意：当前实现不做乐观锁，高并发场景下存在超卖风险。如需处理，可在 `product` 表加 `@Version` 字段，或改为 `UPDATE product SET stock = stock - delta WHERE id = ? AND stock >= delta`（原子操作）。

---

### listStoreProducts / searchProducts — 共用过滤器 + 二次批量查分类

两个方法共用 `buildProductFilter(keyword, categoryId, minPrice, maxPrice)` 构建 `LambdaQueryWrapper`：
- 所有筛选条件均为可选；MyBatis Plus 的条件方法第一个参数为 `boolean condition`，传 `keyword != null && !keyword.isBlank()` 时自动跳过该条件
- `listStoreProducts` 在此基础上额外加 `.eq(Product::getStoreId, storeId)` 并前置商店存在校验

分页结果转 VO 时，`categoryName` 用"二次批量查询"而非 N+1（决策文档第 16 条）：
```
1. 收集本页所有 categoryId（distinct + filter null）
2. productCategoryMapper.selectBatchIds(categoryIds) → 一次查库
3. 构建 Map<id, name>
4. IPage.convert(p → VO) 时从 Map 取名称
```
若本页商品没有 categoryId（全为 null），直接返回空 Map，跳过查库。

### getProductDetail — 最多 5 次查库

执行顺序：
1. `getById(productId)` → 商品不存在抛 404
2. `storeMapper.selectById` → 取商店名
3. `productCategoryMapper.selectById(categoryId)` → 取分类
4. `productCategoryMapper.selectById(category.parentId)`（有 parentId 时）→ 取父分类名
5. `reviewMapper.selectList(eq productId, isNull parentId, select rating)` → 一次查出所有一级评论

评论统计在 Java 侧计算：
- `reviewCount = topReviews.size()`（含未评分的回复已被 `isNull(parentId)` 排除）
- `averageRating`：对 `rating != null` 的评论求 `mapToInt.average()`，无评论时返回 `null`（而非 0.0），语义更清晰

> **为什么不用 SQL AVG()**：
> 需要同时获取 count 和 average，一次 `selectList` 两用，避免两条单独的聚合 SQL。
> 商品详情是低频单条查询，全量拉 rating 列（数据量小）在性能上完全可接受。

## 四、商品分类模块（ProductCategoryServiceImpl）

### getCategoryTree — 两步建树算法

**问题**：数据库存的是扁平列表（每条记录只知道自己的 parentId），需要组装成嵌套树。

**算法（O(n) 时间，O(n) 空间）**：

```
第一步：list() 拉取全量分类，遍历一次建立 Map<Long, CategoryNodeResponse>
        key = id，value = 已初始化 children=[] 的 VO

第二步：再遍历一次，按 parentId 分拣
        parentId == null → 加入 roots 列表
        parentId != null → 从 Map 取出父节点，将当前节点加入 parent.children
        （父节点不在 Map 里 → 降级为根节点，容错处理）

返回 roots，树结构已在内存中就位
```

**为什么不递归查询**：递归方案需要对每个根节点深度优先查询子节点，复杂度 O(n × depth)，且需要多次查库或多次遍历全量数据。分类数量通常在几十到几百条，一次全量 + 两次线性遍历是最优解。

**为什么不用 Stream.groupingBy**：`groupingBy(parentId)` 方案同样 O(n)，但对于递归深度不固定的树，还需额外的递归函数组装根节点的子树，代码可读性不如显式 Map 方案清晰。

### createCategory（Staff 或 Admin）

执行顺序：
1. `AuthUtil.requireRole(ROLE_STAFF, ROLE_ADMIN)`
2. `parentId != null` → `getById(parentId)` 为 null 则抛 404
3. 同名校验：
   ```
   parentId == null → WHERE name=? AND parent_id IS NULL   (用 isNull，不能用 eq(null))
   parentId != null → WHERE name=? AND parent_id=?
   ```
   count > 0 → 抛 400（"该父级下已存在同名分类"）
4. `save` 写库，返回自增 ID

> **注意**：`parentId` 为 null 时必须用 `isNull()` 而非 `eq(field, null)`，后者会被 MyBatis Plus 自动忽略，导致查出所有同名分类（误报重复）。

### deleteCategory（Admin）

执行顺序（三道守卫）：
1. `AuthUtil.requireRole(ROLE_ADMIN)`
2. `getById(categoryId)` 为 null → 抛 404（"分类不存在"）
3. `count(eq parentId=categoryId) > 0` → 抛 400，消息含数量："该分类下存在 N 个子分类，请先删除子分类"
4. `productMapper.selectCount(eq categoryId=categoryId) > 0` → 抛 400，消息含数量："该分类下存在 N 件商品，请先移除或更换商品分类"
5. `removeById` 逻辑删除（MyBatis Plus 自动 `SET deleted=1`）

错误消息带具体数量，便于前端直接展示给用户，不需要再查一次数量。  
逻辑删除不影响历史订单中已关联的 `category_id`（订单条目有商品快照，不依赖实时分类）。

## 六、购物车模块（CartServiceImpl）

### 辅助方法：getOrCreateCart

`getOne(userId)` 查购物车，不存在则 `save` 新建。
购物车对每个用户懒创建（首次查看/加购时自动生成），无需注册时预先创建。

### 辅助方法：getItemForUser

统一封装条目存在性和归属校验，`updateItemQuantity` 和 `removeItem` 复用：
1. `cartItemMapper.selectById(itemId)` → null → 抛 404
2. `getOne(userId)` 查用户购物车 → 购物车不存在或 `cart.id ≠ item.cartId` → 抛 403

### getCart

执行流程：
1. `AuthUtil.requireRole(ROLE_CUSTOMER)`
2. `getOrCreateCart(userId)` 取（或创建）购物车
3. `cartItemMapper.selectList(eq cartId)` 拉取所有条目
4. `productMapper.selectBatchIds(productIds)` 批量查商品（决策文档第 16 条）
5. 构建 `id→Product` Map；不在 Map 中的商品视为已删除：stock=0、price=0、subtotal=0、name="（商品已下架）"
6. 对存在的商品：`subtotal = price × quantity`
7. `total = Σ subtotal`（已删除商品 subtotal 为 0，不计入总价）

MyBatis Plus 的逻辑删除会自动过滤 `deleted=1` 的商品，故 `selectBatchIds` 天然排除已删除商品，无需手动过滤。

### addItem

执行流程：
1. `AuthUtil.requireRole(ROLE_CUSTOMER)`
2. `productMapper.selectById(productId)` → null → 抛 404
3. `getOrCreateCart(userId)` 取（或创建）购物车
4. `cartItemMapper.selectOne(eq cartId + eq productId)` 查是否已有该商品的条目
   - 已存在：`newQuantity = existing.quantity + request.quantity`；超过库存 → 抛 400；否则 `updateById`
   - 不存在：`request.quantity` 超过库存 → 抛 400；否则 `insert` 新条目

### updateItemQuantity

执行流程：
1. `AuthUtil.requireRole(ROLE_CUSTOMER)`
2. `getItemForUser(userId, itemId)` → 404 / 403 守卫
3. `request.quantity == 0` → `cartItemMapper.deleteById(itemId)` 直接删除，提前返回
4. `productMapper.selectById(productId)` 查商品（已删除时 maxStock=0）；超出库存 → 抛 400
5. `item.setQuantity` + `cartItemMapper.updateById`

`UpdateCartItemRequest.quantity` 的 `@Min` 已从 1 改为 0，使 quantity=0 能通过 Bean Validation 到达 Service。

### removeItem

执行流程：
1. `AuthUtil.requireRole(ROLE_CUSTOMER)`
2. `getItemForUser(userId, itemId)` → 404 / 403 守卫
3. `cartItemMapper.deleteById(itemId)` 物理删除（`CartItem` 无 `@TableLogic`，与决策文档第 10 条一致）

## 七、收货地址模块（AddressServiceImpl）

### 辅助方法：clearDefaultForUser(userId, excludeId)

`LambdaUpdateWrapper` 一条 SQL 把该用户所有 `is_default=1` 的地址改为 0，排除 `excludeId`（传 null 时不排除任何地址）。用 MyBatis Plus 的条件方法 `.ne(excludeId != null, ...)` 做动态条件，避免重复写两个分支。

### 辅助方法：toResponse(UserAddress)

`isDefault` 字段在 Entity 中是 `Integer`（0/1），在 Response 中是 `Boolean`。用 `Integer.valueOf(1).equals(a.getIsDefault())` 而非 `a.getIsDefault() == 1`，安全处理 null 值。

### getAddresses

```
list(eq userId, orderByDesc isDefault, orderByDesc createTime)
```

两级排序：`isDefault DESC`（1 排在 0 前面）→ `createTime DESC`（同优先级内最新在前）。一次查库，无需后处理。

### addAddress

执行流程：
1. `count(eq userId)` 统计现有地址数
2. `existingCount == 0` → 强制 `willBeDefault = true`（首条地址自动成默认）
3. `willBeDefault = true` 且 `existingCount > 0` → `clearDefaultForUser(userId, null)` 清除旧默认
4. `save(address)`，自增 ID 回写

### updateAddress

执行流程：
1. `getById(addressId)` → null → 抛 404；`userId ≠ address.userId` → 抛 403
2. 只更新请求体中非 null 的字段
3. `updateById(address)`
4. `request.isDefault == true` → `clearDefaultForUser(userId, addressId)` 清除其他地址的默认标记

`clearDefaultForUser` 排除 addressId 自身，避免在步骤 4 把刚设好的默认又清掉。

### deleteAddress

执行流程：
1. `getById` → 404 守卫；userId 校验 → 403 守卫
2. 记录 `wasDefault = address.isDefault == 1`
3. `removeById(addressId)`（逻辑删除，MyBatis Plus 自动 `SET deleted=1`）
4. `wasDefault == true` → 查该用户剩余地址（`orderByDesc createTime`），取第一条，`setIsDefault(1)` + `updateById`
5. 删除后无地址 → 不处理

为什么选最新创建的而非其他策略：删除默认地址时用户通常想继续使用最近添加的地址，且无需业务决策，简单清晰。整个方法加 `@Transactional`，删除和新默认的设置原子完成。

## 八、订单模块（OrderServiceImpl — createOrder）

### 整体结构：两阶段设计

```
Phase 1（只读，全部校验）
  1. 购物车条目存在性 + 归属校验
  2. 收货地址存在性 + 归属校验
  3. 商品批量加载 + 库存充足性校验
  4. 优惠券存在性 + 归属 + UNUSED 状态 + 未过期校验
  5. 金额计算（totalAmount / discountAmount / payableAmount）

Phase 2（写库，全部通过后统一执行）
  6. 统一扣减库存（updateById × N）
  7. 创建 Order 记录
  8. 创建 OrderItem 记录（商品名称/价格快照）
  9. 核销优惠券（status=USED, usedAt=now, orderId=...）
  10. 物理删除购物车条目
```

整个方法加 `@Transactional`，任何写操作失败均回滚。

### Phase 1 细节

**购物车条目校验**：`cartItemMapper.selectBatchIds(cartItemIds)` 批量加载，用返回数量与请求数量比较判断是否有条目不存在。再查用户的 Cart，验证所有 item.cartId == cart.id。

**收货地址校验**：`userAddressMapper.selectById` + `address.userId == userId`。

**商品库存校验**：`productMapper.selectBatchIds(productIds)` 一次批量查，构建 `Map<Long, Product>`。逐一检查存在性和 `product.stock >= item.quantity`，库存不足时消息包含商品名称，便于前端展示。

**优惠券校验**（3 层守卫）：
1. coupon 存在 + 属于当前用户
2. `coupon.status == "UNUSED"`
3. `couponGroup.expireAt > now`（group 层面的过期校验）

### 金额计算

```
totalAmount = Σ(product.price × item.quantity)

AMOUNT_OFF:
  检查 totalAmount >= minOrderAmount（minOrderAmount > 0 时）
  discountAmount = couponGroup.value（固定减免）

DISCOUNT:
  discountAmount = totalAmount × (1 - value)（保留 2 位，HALF_UP）

payableAmount = max(0.01, totalAmount - discountAmount)
```

### storeId 来源

`Order.storeId` 取自商品 map 中任意一条商品的 `storeId`。业务前提：同一购物车中的商品属于同一店铺（与 `orders` 表设计决策第 8 条一致）。

### OrderItem 快照

下单时将 `product.name`、`product.price`（unitPrice）、`product.imageUrl` 写入 `order_item`，与决策文档第 5 条一致。商品信息事后变更不影响历史订单展示。

### 优惠券核销

在 Phase 2 中更新 `coupon.status=USED`、`coupon.usedAt=now`、`coupon.orderId=order.id`。`couponMapper.updateById` 只更新非 null 字段（MyBatis Plus 默认策略），`updateTime` 字段标注了 `@TableField(exist=false)`，不写库。

## 九、评论模块（ReviewServiceImpl）

评论与回复共用 `review` 单表，靠 `parentId` 区分层级（决策文档第 7 条）：`parentId = null` 为顶级评价（有 `rating`、`orderId`），`parentId` 有值为回复（`rating`、`orderId` 均为 null）。

### getProductReviews（无需登录）

执行流程：
1. `productMapper.selectById(productId)` → null 抛 404
2. 分页查顶级评论：`eq productId + isNull parentId + orderByDesc createTime`
3. 本页为空时直接返回空分页（`topPage.convert` over 空 records），跳过后续查库
4. 收集本页顶级评论 ID，`in(parentId, topIds) + orderByAsc createTime` 一次批量查出所有回复（决策文档第 16 条），按 `parentId` 用 `groupingBy` 分组
5. 收集评论者 + 回复者全部 userId，`userMapper.selectBatchIds` 一次查出昵称，构建 `Map<id, nickname>`
6. `topPage.convert` 组装 VO，每条顶级评论挂上其回复列表（无回复时为 `List.of()`）

回复列表**不分页**、按 `createdAt` 升序，与 api-spec 的 JSON 结构一一对应。

### createReview（仅 Customer）

执行顺序（多道校验，全部通过才写库）：
1. `requireRole(ROLE_CUSTOMER)`
2. `productMapper.selectById` → 商品不存在抛 404
3. 购买资格：`orderMapper.selectById(orderId)`，订单为 null 或 `userId` 不匹配 → 抛 400；`status != "COMPLETED"` → 抛 400（消息含当前状态）
4. 订单含该商品：`orderItemMapper.selectCount(eq orderId + eq productId) == 0` → 抛 400
5. 重复评论：`count(eq userId + eq productId + eq orderId + isNull parentId) > 0` → 抛 400
6. `save(review)`，返回自增 ID

rating 1–5 由 `CreateReviewRequest` 的 `@Min(1)/@Max(5)` 在 Controller 入口校验，Service 不重复校验。去重维度是 **user + product + order**：同一商品在不同已完成订单中可分别评论一次。

### replyToReview（仅 Customer）

执行顺序：
1. `requireRole(ROLE_CUSTOMER)`
2. `getById(reviewId)` → null 抛 404
3. `parent.parentId != null` → 抛 400「不支持多级回复」（只允许对顶级评论回复，禁止多级嵌套）
4. 构造回复：`productId` 继承自父评论，`parentId = reviewId`，不写 `orderId` / `rating`
5. `save(reply)`，返回自增 ID

回复无购买限制，任意 Customer 均可回复。

## 十、报表模块（ReportServiceImpl）

两个报表方法共用聚合逻辑，差别仅在鉴权与是否限定商店。底层依赖 `OrderMapper` 的三个原生聚合 SQL（QueryWrapper 不支持 `GROUP BY`/`SUM`，决策文档第 15、17 条）。

### 辅助方法：normalizeAndValidate(startDate, endDate)

- `endDate` 缺省取 `LocalDate.now()`；`startDate` 缺省取 `effectiveEnd.minusDays(30)`（最近 30 天）
- `effectiveStart.isAfter(effectiveEnd)` → 抛 400「起始日期不能晚于截止日期」
- 返回 `LocalDate[]{start, end}`

### 辅助方法：toBigDecimal(Object)

`SUM()` 在无匹配行时返回 null，统一转 `BigDecimal.ZERO`；已是 `BigDecimal` 直接返回，否则走 `new BigDecimal(toString())`，安全处理各种 JDBC 数值类型。

### getStoreOrderReport（仅 Staff 本店）

1. `requireRole(ROLE_STAFF)` + `requireStoreAccess(storeId)`
2. `selectStatusBreakdown(storeId, start, end)` 遍历组装 `statusBreakdown`（`LinkedHashMap` 保序），同时累加得 `totalOrders`（**含所有状态**）
3. `selectDailyRevenue(storeId, start, end)`（SQL 内已过滤 `status='COMPLETED'`）组装 `dailyRevenue`，累加得 `totalRevenue`
4. `averageOrderAmount`：`totalOrders > 0` 时 `totalRevenue / totalOrders`（2 位 HALF_UP），否则 `BigDecimal.ZERO`

> totalOrders 来自全状态统计，totalRevenue 仅 COMPLETED，二者口径不同是刻意设计：均单价反映"每笔订单平均贡献的实收收入"。

### getGlobalOrderReport（仅 Admin）

1. `requireRole(ROLE_ADMIN)`
2. `selectStatusBreakdown(null, ...)` 累加得全局 `totalOrders`（`storeId` 传 null，SQL 中 `#{storeId} IS NULL` 分支放开商店限定，决策文档第 17 条）
3. `selectDailyRevenue(null, ...)` 组装全局 `dailyRevenue` 并累加 `totalRevenue`
4. `selectStoreBreakdown(start, end)`（JOIN `store` 取店名，按 `store_id` 分组）组装 `storeBreakdown`

## 定时任务：未支付订单自动取消（OrderAutocancelJob）

> 路线图任务 1。复用订单手动取消的库存/优惠券恢复逻辑，无鉴权上下文。

### 触发与配置

- `config/SchedulingConfig` 加 `@EnableScheduling` 集中开启调度支持。
- `job/OrderAutocancelJob`（`@Component`）用 `@Scheduled(fixedDelay = 60000)` 每分钟执行一次（上次结束后再隔 60 秒）。
- 保留天数 `bluewhale.order.auto-cancel-days`（默认 14）经 `@Value` 注入，**不硬编码**；演示可调小（如 1）。

### 执行流程

1. **Job**：`expireTime = now - autoCancelDays 天`；调 `OrderMapper.selectExpiredUnpaidOrders(expireTime)` 查出所有 `status='PENDING_PAYMENT'` 且 `created_at < expireTime` 的订单（自定义 SQL，手写 `deleted=0`，`created_at AS createTime` 对齐实体字段）。
2. **逐条处理**：对每条订单 `try { orderService.cancelExpiredUnpaidOrder(order); count++ } catch { log.error }`，单条失败仅记日志、不中断其余。
3. 全部处理完打印 `自动取消过期订单完成，本次取消 X 条`。
4. **每条取消（`OrderServiceImpl.cancelExpiredUnpaidOrder`，独立 `@Transactional`）**：`getById` 重载并校验仍为 PENDING_PAYMENT（幂等防御）→ `restoreInventory` 恢复库存 → `restoreCoupon` 恢复券为 UNUSED → 置 `CANCELLED` + 记 `cancelledAt` → `updateById`。

### 关键设计 / 边界

- **为什么恢复库存**：`createOrder` 是「下单即扣库存」（Phase 2 扣减），故未支付订单已占用库存，自动取消必须恢复，否则库存泄漏（详见决策第 44 条）。
- **为什么恢复优惠券**：`createOrder` 下单时即把券标记为 `USED`，取消需还原为 `UNUSED`。
- **为什么不复用 `cancelOrder`**：它内部 `requireCustomerOrder` 读 SecurityContext 校验 Customer 归属，定时任务无鉴权上下文，故新增系统级方法 `cancelExpiredUnpaidOrder`（不鉴权、不暴露接口）。
- **每条独立事务 + Job 内逐条 try/catch**：单条失败只回滚该条、不影响其余；`@Scheduled` 方法内捕获异常避免中断调度。
- **幂等**：执行前重查状态，非 PENDING_PAYMENT（已支付/已取消）则跳过，防止与手动操作竞态导致重复取消。
- **只取消 PENDING_PAYMENT**：已支付/已发货等状态不受影响。

## 商品库存乐观锁（防并发超卖）

> 路线图任务 2（库存部分）。`createOrder` 扣减与 `updateStock` 调整均改为乐观锁更新。

### 字段与迁移

- `Product` 实体加 `@Version private Integer version`；迁移 `V2__add_product_version.sql`：`ALTER TABLE product ADD COLUMN version INT NOT NULL DEFAULT 0`。
- **未注册** `OptimisticLockerInnerInterceptor`：避免所有 `updateById(product)`（如 `restoreInventory`/`updateProduct`，均未检查返回值）被自动加版本校验而静默失败。版本号仅由下面两个自定义 SQL 推进。

### ProductMapper 自定义 SQL

- `updateStockWithVersion(id, quantity, version)`：`UPDATE product SET stock = stock - #{quantity}, version = version + 1 WHERE id = #{id} AND version = #{version} AND stock >= #{quantity} AND deleted = 0`。**防超卖的核心是 `stock >= quantity` 原子条件**，版本号做并发冲突检测。
- `updateStockTo(id, stock, version)`：绝对值设置（Staff 入库/出库），`SET stock = #{stock}, version = version + 1 WHERE id = #{id} AND version = #{version} AND deleted = 0`。

### 重试逻辑（最多 3 次）

- **createOrder**（`deductStockWithOptimisticLock`）：循环最多 3 次 → `selectById` 重读最新 stock/version → 库存不足直接抛「库存不足」（不重试）→ `updateStockWithVersion`，影响行数 >0 成功返回；==0 说明版本被并发抢先修改，重读后重试。3 次仍失败抛 `BusinessException("库存更新失败，请重试")`。
- **updateStock**（Staff）：同样 3 次重试，用 `updateStockTo`；该方法无 `@Transactional`，每次 `getById` 都是新读取，重试能拿到最新数据。

### 边界 / 说明

- **REPEATABLE READ 注意**：`createOrder` 带 `@Transactional`，同一事务内重读受 MySQL 快照影响、未必见到其他事务最新提交的 version，故事务内重试常无效；但 `stock >= quantity` 与 version 条件保证**不会超卖**，重试耗尽即抛错由客户端整单重试（新事务、新快照）。安全性不依赖重试是否命中。
- **遗留**：`restoreInventory` 仍为「读-改-写」`updateById`（仅做加库存，不会超卖，但与并发扣减存在丢失更新的理论窗口）；优惠券领取的 `remain_count` 下限保护未做。二者列入任务 2 剩余项。

## 优惠券领取 Redis 分布式锁（防并发超发）

> 路线图任务 2（优惠券部分）。`claimCoupon` 用 Redis 分布式锁把「检查 remainCount → 扣减」串行化。

### RedisLockUtil（`util/RedisLockUtil`）

- `tryLock(key, value, expireSeconds)`：`SET key value NX EX`（`StringRedisTemplate.opsForValue().setIfAbsent(...)`），成功返回 true。`NX` 保证互斥，`EX` 防持有者宕机死锁。
- `unlock(key, value)`：Lua 脚本 `if get(KEYS[1])==ARGV[1] then del else 0`，保证「判断归属 + 删除」原子，防止误删他人在锁过期后重新持有的锁。`value` 用 UUID 标识持有者。

### claimCoupon 执行流程

1. `requireRole(CUSTOMER)`（鉴权先于加锁，未授权不占锁）。
2. `lockKey = coupon_lock:groupId:{groupId}`、`lockValue = UUID`；`tryLock(..., 5s)` 失败抛 `BusinessException("系统繁忙，请稍后重试")`。
3. `try { ... } finally { unlock }`：确保锁一定释放。临界区内：校验组存在/未过期 → **双重检查 remainCount > 0**（持锁后再查，避免等锁期间被领完）→ 校验未重复领取 → 扣减 → 建券记录。
4. 扣减：`UPDATE ... remain_count = remain_count - 1 WHERE id = ? AND remain_count > 0`，**影响行数 0 抛「已被抢完」**。
5. 方法带 `@Transactional`，扣减与建券原子。

### 锁粒度

- 锁 key 含 `groupId`，**粒度为优惠券组**：同组并发领取互斥，不同组互不影响。

### 关键边界 / 已知点

- **锁在事务提交前释放**：锁在 `@Transactional` 方法体的 finally 释放，而事务由代理在方法返回后才提交，故存在「释放锁→他线程拿锁→读到未提交的旧 remainCount」的窗口。**靠扣减的 `remain_count > 0` 守卫兜底**：即使他线程读到旧值，扣减条件也保证不会减成负数（影响 0 行即拒绝）。即超发的最终防线是 DB 守卫，分布式锁主要降低无效竞争与重复领取的并发冲突。彻底消除该窗口需将锁移到事务外（锁包事务），属后续优化。
- **未引入 Redisson**：当前是不可重入、无看门狗续期的轻量实现，临界区短（仅几条 SQL）、5s 过期足够；需要可重入/自动续期再升级。

## 热点读缓存（任务 3）

> 手写 `CacheUtil.getOrLoad` + `RedisUtil.deleteByPrefix`，非 Spring Cache 注解。识别见 `缓存热点数据识别.md`，取舍见决策第 47 条。

### 基础设施

- `util/CacheUtil`：`getOrLoad(key, baseTtl, randomRange, loader, Class<T>)`（单实体，空值占位防穿透 + 命中抛 404）与 `getOrLoad(..., TypeReference<T>)`（集合/分页，不做 404 占位）。JSON 用注入的 Spring `ObjectMapper`；实际 TTL=base+random(range) 防雪崩；反序列化失败回源容错。
- `util/CacheKeys`：key 构造与 TTL/抖动常量集中。
- `util/RedisUtil.deleteByPrefix`：SCAN 游标分批删除（非 KEYS）。

### 缓存点与失效

| 对象 | key | TTL | 失效触发 |
|---|---|---|---|
| 分类树 | `category:tree` | 1h | createCategory/deleteCategory → delete |
| 商店详情 | `store:detail:{id}` | 30m | updateStore → delete |
| 商店列表 | `store:list:{page}:{size}` | 10m | createStore/updateStore → deleteByPrefix |
| 商品详情 | `product:detail:{id}` | 5m | updateProduct/updateStock/deleteProduct → delete |
| 商品评论 | `product:reviews:{id}:{page}:{size}` | 10m | createReview/replyToReview → deleteByPrefix(`product:reviews:{id}:`) |
| 店铺/全局报表 | `report:store:{id}:{s}:{e}` / `report:global:{s}:{e}` | 5m | 纯 TTL，不主动清 |

### 关键点

- **回源改造**：各读方法把原逻辑抽成私有 loader（如 `loadProductDetail`/`loadCategoryTree`/`loadProductReviews`/`loadStoreOrderReport`），单实体 loader「不存在返回 null」交由 CacheUtil 写占位并抛 404；评论分页的「商品不存在」仍在 loader 内抛（带专属文案，不缓存该 404）。
- **IPage 缓存**：`getStoreList`/`getProductReviews` 的 `convert(...)` 结果转为具体 `Page<T>` 缓存，命中用 `TypeReference<Page<T>>` 反序列化。
- **库存一致性（方案 1）**：商品详情含 stock，订单下单/取消改库存不主动清缓存，靠 5min 短 TTL；超卖由下单时 `stock >= q` 守卫兜底。
- **不缓存**：优惠券组列表（remainCount 高频变）、商品搜索/门店商品列表（多维参数键爆炸 + 含 stock）、各用户私有接口。

## 多优惠券叠加（任务 5）

> 券类型拆 3 类、多券按最优顺序计价、试算接口。规则与取舍见决策第 49 条。

### 券类型

| type | 含义 | value | 门槛 min_order_amount | 计价 |
|---|---|---|---|---|
| DISCOUNT | 折扣券 | 折扣率(0,1) | 任意 | 乘性：running × value |
| FULL_REDUCTION | 满减券 | 减免额(>0) | 必须 > 0 | 加性：running − value |
| DIRECT_OFF | 直减券 | 减免额(>0) | 必须 = 0 | 加性：running − value |

叠加规则：**同类型至多一张，不同类型无限叠加**。

### CouponCalculator（纯函数）

- `calculate(totalAmount, List<CouponSpec>)`：穷举券的所有应用顺序（全排列），每种顺序链式计价，取**折扣最大**者。
- 链式计价：`running` 从总额起，DISCOUNT 乘 value、满减/直减减 value；每步四舍五入到分、并以 0 兜底（券额超额不为负）；最终实付 `max(running, 0.01)`。
- 返回 `{discountAmount, payableAmount, appliedCouponIds(最优顺序)}`，`discount = total − payable`（保证折扣+实付=总额，无舍入泄漏）。
- 券数 ≤3 ⇒ ≤6 种排列，开销可忽略，无并发。已证最优为「先乘性折扣后加性减免」，穷举只为「显然正确 + 鲁棒」。

### resolveCoupons（Service 层校验 + 计价，createOrder/previewCoupon 共用）

按序对每张候选券校验，任一失败即抛 BusinessException（不写库）：
1. 去重（同券不可重复传）。
2. 存在且属当前用户、状态 UNUSED。
3. 所属券组存在且未过期。
4. **店铺范围**：店铺券仅适用于本店订单，全局券不限。
5. **同类型限一张**（`seenTypes` 去重）。
6. **满减门槛按原始订单总额判定**（达标后顺序优化不影响资格）。

通过后构造 `CouponSpec` 列表交 `CouponCalculator.calculate`，返回 `{coupons, result}`。

### createOrder 变化

- 取消旧的单券分支计价；总额与 storeId 提前计算，调 `resolveCoupons` 得折扣/实付。
- 写库：`orders.coupon_id` 不再写（保留列兼容旧数据）；逐张券标记 USED 并插入 `order_coupon` 关联。

### previewCoupon（POST /api/orders/coupon-preview）

- 校验购物车归属 + 算总额/storeId（不校验库存、不写任何表）→ 调 `resolveCoupons` → 返回 `{totalAmount, discountAmount, payableAmount, appliedCouponIds}`。
- 下单时后台**重新计算**，不信任前端试算结果。

### 取消/退款恢复（多券）

- `restoreCoupons(orderId, legacyCouponId)`：券来源 = `order_coupon` 关联表 ∪ `orders.coupon_id`（兼容历史单券），逐张恢复为 UNUSED 并清 used_at/order_id。
- `cancelOrder` / `refundOrder` / `cancelExpiredUnpaidOrder` 均改用之。

### 迁移 V3__coupon_stacking.sql

- 数据迁移：`AMOUNT_OFF` → `min_order_amount>0` 转 `FULL_REDUCTION`、否则 `DIRECT_OFF`。
- 建 `order_coupon`（order_id, coupon_id, 唯一键 (order_id, coupon_id)，FK orders/coupon）。

### WebSocket 连接流程

```
客户端 TCP Connect + HTTP Upgrade → /ws（SecurityConfig 放行握手）
  → STOMP CONNECT 帧，header: Authorization: Bearer <jwt>
      → StompAuthChannelInterceptor 验证 JWT
          → 合法：绑定 ChatPrincipal（name=userId），连接建立
          → 非法/缺失：抛异常，连接拒绝
  → WebSocketPresenceListener 记录在线（写 Redis Set）
  → 客户端订阅目的地（/user/queue/messages、/topic/store.{id}、/user/queue/errors）
  → ...（消息收发）
  → 断开：WebSocketPresenceListener 移除在线
```

### 消息路由

**买家发消息**（`/app/chat.customer.send`）：

```
@MessageMapping("chat.customer.send")
  → 从 ChatPrincipal 取 customerId，AuthUtil.requireRole(authUser, CUSTOMER)
  → 查或建 chat_session（UNIQUE(store_id, customer_id)，首条消息自动建）
  → 写 chat_message（sender_role=CUSTOMER）
  → 更新 chat_session.last_message / last_message_at
  → assignee_staff_id IS NULL（未接入）
      → convertAndSend("/topic/store.{storeId}", StoreTopicEvent{type:"MESSAGE", ...})
  → assignee_staff_id 有值（已接入）
      → convertAndSendToUser(staffId, "/queue/messages", ChatMessageResponse)
```

**客服发消息**（`/app/chat.staff.send`）：

```
@MessageMapping("chat.staff.send")
  → 从 ChatPrincipal 取 staffId，AuthUtil.requireRole(authUser, STAFF)
  → 查 chat_session，校验 assignee_staff_id == staffId（否则 403）
  → 写 chat_message（sender_role=STAFF）
  → 更新 last_message / last_message_at
  → convertAndSendToUser(customerId, "/queue/messages", ChatMessageResponse)
```

**认领/释放（REST）**：

```
POST /api/chat/sessions/{id}/claim
  → UPDATE chat_session SET assignee_staff_id=#{me} WHERE id=? AND assignee_staff_id IS NULL
  → 影响 0 行 → BusinessException（已被他人接待）
  → 影响 1 行 → 广播 StoreTopicEvent{type:"CLAIMED"} 到 /topic/store.{storeId}

POST /api/chat/sessions/{id}/release
  → UPDATE chat_session SET assignee_staff_id=NULL WHERE id=? AND assignee_staff_id=#{me}
  → 影响 0 行 → BusinessException（非本人持有，403）
  → 影响 1 行 → 广播 StoreTopicEvent{type:"RELEASED"} 到 /topic/store.{storeId}
```

### 在线状态

- Redis Set 键：买家 `cs:online:customers`（成员=userId）；客服 `cs:online:store:{storeId}`（成员=userId）。
- `WebSocketPresenceListener`：连接成功 (`SessionConnectedEvent`) → 从 principal 取角色和 storeId，`SADD` 对应 Set；断连 (`SessionDisconnectEvent`) → `SREM`。
- 会话列表内联在线状态：买家视角 → `SCARD cs:online:store:{storeId} > 0`（本店有客服在线）；客服视角 → `SISMEMBER cs:online:customers {customerId}`（该买家是否在线）。

### 会话列表（`GET /api/chat/sessions`）

按 JWT 中角色感知返回：
- **CUSTOMER**：返回自己参与的所有会话（每店至多一个），含店名、最后消息、本店有无客服在线（`staffOnline`）。
- **STAFF**：返回本店全部会话，按 `assignee_staff_id` 分组——未接入（null）、我接待（=当前 staffId）、他人接待（其他 staffId），含买家昵称、是否在线（`customerOnline`）、归属客服昵称。

### 历史消息游标分页

`GET /api/chat/sessions/{id}/messages?before={msgId}&size=20`

- 按 `id DESC` 排序，`before` 传上次最小 msgId 实现向上翻页（游标分页，避免 OFFSET 跳页偏移）。
- 权限：同店任意 STAFF 可读本店任意会话；CUSTOMER 只能读自己的会话；越权 403。
- `INDEX(session_id, id)` 覆盖索引，分页查询高效。

### 数据模型（V4__chat.sql）

```sql
chat_session(id, store_id, customer_id, assignee_staff_id NULL,
             last_message, last_message_at, created_at, updated_at, deleted)
  UNIQUE(store_id, customer_id)  -- 一买家×一店铺=一个可复用会话
  INDEX(store_id), INDEX(customer_id)

chat_message(id, session_id, sender_role[CUSTOMER/STAFF], sender_id,
             content VARCHAR(1000), created_at, deleted)
  -- append-only，无 updated_at
  INDEX(session_id, id)  -- 游标分页覆盖索引
```

### 边界与已知限制

- **离线粘性**：客服断开时 `assignee_staff_id` 保持不变；买家消息继续落库；重连后拉历史补齐。后续须做超时自动释放（见决策 #51）。
- **WS 线程无 SecurityContext**：已通过 `AuthUtil.requireRole(AuthUser, roles...)` 重载解决，WS 路径传入来自 `ChatPrincipal` 的 `AuthUser`，不读 `SecurityContextHolder`（详见决策 #51）。
- **错误帧**：当前未注册 `StompSubProtocolErrorHandler`，CONNECT/SUBSCRIBE/SEND 鉴权失败时客户端收不到结构化 ERROR 帧（后续可补）。

## 推荐算法：item-based CF 与多级缓存（任务 8）

> item-based 协同过滤，加权余弦，离线预计算 + MySQL 持久 + Redis ZSET 缓存。选型见决策第 52 条，知识背景见 `学习笔记-推荐算法与实时客服.md`。

### 组件结构

| 类 | 职责 |
|---|---|
| `util/CosineSimilarity` | 加权余弦纯函数：`cosine(Map<userId,weight> a, b)`，遍历较小向量求点积 / 模长归一化 |
| `mapper/RecommendationMapper` | `selectInteractions`（用户×商品×状态）、`selectTopSimilar`、`selectGlobalHotProductIds`、`selectCategoryHotProductIds`、`deleteAllSimilarities` |
| `service/RecommendationService(Impl)` | 重建、接口 A/B 逻辑、状态权重映射、ID→DTO 转换 |
| `controller/RecommendationController` | 接口 A（开放）、B（需登录） |
| `controller/AdminController` | 手动重建端点（追加） |
| `job/RecommendationRebuildJob` | 每日 03:00 cron 触发重建 |
| `entity/ProductSimilarity` | 映射 `product_similarity`（V5） |
| `util/RedisUtil` | 追加 ZSet 操作 `zAdd` / `zRevRange` |

### 状态权重（集中定义）

`RecommendationServiceImpl.weightOf(status)`：`PAID/SHIPPED/COMPLETED → 1.0`，`PENDING_PAYMENT → 0.5`，`CANCELLED → 0.3`，其它 → 0（忽略）。同一用户对同一商品多笔订单**取最大权重**（`merge(userId, w, Math::max)`）。

### 离线重建流程（`rebuildAll()`，`@Transactional`，不读 SecurityContext）

```
selectInteractions(null) 取全量 (userId, productId, status)
  → buildVectors：productId -> (userId -> 最大权重)
deleteAllSimilarities() 清表
for 每个商品 pid:
    for 每个 other≠pid: cosine(vec[pid], vec[other])，>0 才保留
    按 score 降序取 Top-N(=50) → 逐条 insert
redisUtil.deleteByPrefix("rec:sim:")  清缓存，read-through 懒重建
```

> 复杂度 O(商品数²)，相似度慢变量，离线低峰期跑可接受。触发：每日 03:00 cron（`RecommendationRebuildJob`）或 `POST /api/admin/recommendations/rebuild`（Admin 手动，本地调试免等）。

### 接口 A：商品相关推荐（`GET /api/products/{id}/recommendations`，开放）

```
readSimilarIds（read-through）：
  zRevRange rec:sim:{id} → 命中直接返回
  未命中 → selectTopSimilar 回表 → 逐条 zAdd 回填 + expire(1天) → 返回
不足 limit → 取商品 categoryId → fillWithHot：
  selectCategoryHotProductIds 补 → 仍不足 selectGlobalHotProductIds 补（去重 + 排除自身）
toListItems：批量 selectBatchIds 查商品 + 类目名（避免 N+1），保序截断
```

### 接口 B：个性化猜你喜欢（`GET /api/recommendations`，需登录）

```
selectInteractions(当前userId) → mine: productId -> 最大权重
mine 为空（新用户）→ selectGlobalHotProductIds 兜底返回
否则聚合：for 每个已购 h: for h 的相似 s: scores[s] += w(u,h)·sim(h,s)（排除已购）
  → 按累加分降序 → 不足补全站热销（排除已购/已在列表）→ toListItems
```

### 多级缓存与持久

- **真相来源 = `product_similarity` 表**（MySQL，关机不丢；派生数据，丢了可从订单重算）。
- **缓存 = Redis ZSET** `rec:sim:{productId}`（member=相似商品 id，score=相似度），TTL 1 天，read-through 回填、重建清空。
- 关机清空 Redis 后，首个请求自动从表 read-through 重建缓存，无需手动预热。

### 边界与已知限制

- 空相似结果未做缓存哨兵：无相似的冷门商品每次请求都会回表（miss），可后续加空值占位。
- 相似度全量重建（非增量）；商品/订单量大后可改增量更新。
- 评分信号（`review.rating`）暂未纳入加权，余弦已留扩展口。
- 热销榜按需 SQL 聚合、未预计算缓存（决策 #52 的实现期细化）。

## HTTP 语义与并发健壮性修正（第二轮 A）

- **未登录 → 401**：新增 `config/RestAuthenticationEntryPoint`（实现 `AuthenticationEntryPoint`，写 401 + `Result.unauthorized`）与 `config/RestAccessDeniedHandler`（403 + `Result.forbidden`），在 `SecurityConfig.exceptionHandling` 注册。开启 anonymous 时，未认证请求经 `ExceptionTranslationFilter` 判定为匿名 → 走 entryPoint 返回**真实 HTTP 401**（替代此前默认 403）。注意：Service 层角色/归属校验仍由 `AuthUtil` 抛 `BusinessException` 经 `GlobalExceptionHandler` 处理（HTTP 200 + 业务码），两条路径分属安全层与业务层。

## 三级缓存：Caffeine L1 + single-flight（第二轮 F）

在原 `CacheUtil`（Redis L2 + DB）之上加 **Caffeine 本地 L1**，并补 **single-flight 防击穿**与**两级一致失效**。选型见决策第 53 条。

### 读路径：L1 → L2 → DB

```
getOrLoad(key, ...)：
  readThrough(key)：L1(Caffeine).getIfPresent → 命中即返回
                    未命中 → L2(Redis).get → 命中则回填 L1 → 返回
  decode(...)：命中反序列化返回；空值占位 NULL_SENTINEL 抛 404；反序列化失败视为未命中
  仍未命中 → single-flight 回源（见下）
```

L1 命中省去 Redis 网络往返；L2 命中回填 L1。`put` 同时写 L2(带 TTL) 与 L1。

### single-flight（防缓存击穿）

未命中时按 key 进入**条带锁**（`stripeFor(key)`，固定 64 条带、按 key 哈希取模，内存有上限）：

```
synchronized (stripeFor(key)) {
    双重检查 readThrough(key)   // 先入锁的线程可能已回填，直接复用
    仍未命中 → loader.get() 回源 → put(L1+L2)
}
```

同一 key 的并发请求只放一个去回源、其余等待复用，避免热点 key 失效瞬间的「并发回源风暴」。条带锁而非每 key 建锁，避免锁对象无上限。

### 两级一致失效

写操作改调 `CacheUtil` 统一失效，**同时清 L1+L2**：
- `invalidate(key)`：`redisUtil.delete(key)` + `localCache.invalidate(key)`。
- `invalidateByPrefix(prefix)`：`redisUtil.deleteByPrefix(prefix)`（SCAN 前缀删）+ `localCache.invalidateAll()`（L1 前缀匹配不便，整体清空；条目少、短 TTL 很快重建）。

四处缓存写点（分类树 `ProductCategoryServiceImpl`、商品详情 `ProductServiceImpl`、商店详情/列表 `StoreServiceImpl`、商品评论 `ReviewServiceImpl`）由 `redisUtil.delete/deleteByPrefix` 改为 `cacheUtil.invalidate/invalidateByPrefix`，并移除各自不再使用的 `RedisUtil` 注入。L1 另设 5s `expireAfterWrite` 作兜底，限制任何漏失效场景的脏数据窗口。

> 推荐相似度的 Redis ZSET 缓存（`rec:sim:*`）非 `CacheUtil` 托管，其 `deleteByPrefix` 仍走 `redisUtil`，不受影响。

## 认证增强：令牌版本与即时撤销（第二轮 E）

在已有双令牌（access + refresh 轮换）基础上加**即时令牌撤销**并缩短 access。选型见决策第 54 条。

### 令牌版本（token version / epoch）

- `JwtUtil.generateToken(...)` 增 `ver` 声明；`getTokenVersion` 读取（旧 token 无此声明视为 0，向后兼容）。
- `TokenVersionStore`（Redis 键 `auth:tokenver:{userId}`）：
  - `current(userId)`：当前版本，键缺失返回 0；
  - `bump(userId)`：`INCR` 自增（撤销该用户全部已签发 token）；
  - `isCurrent(userId, ver)`：`ver >= current`，键缺失（默认 0）也不会误杀。
- 签发时机：`login` / `refreshToken` 均以 `current(userId)` 作为 token 的 `ver`。
- 校验时机：`JwtAuthenticationFilter` 验签通过后，`isCurrent(userId, ver)` 为假则不写入认证上下文（受保护接口 → 401）。

### 撤销动作（登出 / 改密）

`logout` 与 `changePassword` 成功后统一：**`tokenVersionStore.bump(userId)`（令 access 立即失效）+ 删除 `refresh_token:{userId}`（阻断刷新）**，强制重新登录。
新增 `POST /api/auth/logout`（从 access token 解析当前用户；该接口在 `/api/auth/**` 放行，但依赖请求携带有效 token 才能定位用户）。

### access token 缩至 15 分钟

`jwt.expiration` 默认 `86400000`(24h) → `900000`(15min)，配合 refresh 轮换（7d）缩小令牌暴露窗口。前端需更频繁触发刷新（机制已具备）。

### 取舍与边界

- **用令牌版本而非 jti 黑名单**：一个 key + 一条 `INCR` 即撤销该用户全部令牌，契合「每用户一个 refreshToken」的单会话模型；无需在 token 里加 jti、无黑名单膨胀。代价：过滤器每请求多一次 Redis `GET`（读 `current`）。
- **版本键无 TTL**（持久），按用户数量有界。比较用 `>=`，即便键被清也不误杀有效 token。
- **RS256 未做**：E3（HS256→RS256 非对称签名）按规划标「可选」暂缓，撤销才是 E 的核心安全点；后续需要时只换 `JwtUtil` 的签名/验签与密钥，不影响上述逻辑。

## 推荐增强：空结果哨兵 + 评分加权（第二轮 C）

在任务 8 推荐基础上补两项增强（C2 增量重建按数据量小、收益有限暂缓）。

### C1 空相似结果哨兵

冷门 / 新品无相似数据时，原 `readSimilarIds` 每次请求都 `selectTopSimilar` 回表。新增空哨兵：

```
readSimilarIds：
  ZSET 命中 → 返回
  ZSET 未命中 → 查空哨兵 hasKey(rec:sim:empty:{id})：命中 → 直接返回空（跳过回表）
  回表 selectTopSimilar 为空 → setWithExpire(rec:sim:empty:{id}, 5min) 占位 → 返回空
```

哨兵键前缀 `rec:sim:empty:` 含 `rec:sim:`，故重建时 `deleteByPrefix("rec:sim:")` 一并清除，新数据产生后哨兵随之失效。5min 短 TTL 限制「商品新增了相似数据但哨兵未过期」的空窗。

### C3 评分加权

将 `review.rating`（一级评价 1-5）纳入兴趣权重，提升相似度质量。`RecommendationMapper.selectUserProductRatings` 取 `(userId, productId, rating)`；重建时 `buildVectors` 在状态最大权重之上乘以**评分乘子** `ratingMultiplier`：

| rating | 5 | 4 | 3 | 2 | 1 | 无 |
|---|---|---|---|---|---|---|
| 乘子 | 1.5 | 1.2 | 1.0 | 0.7 | 0.5 | 1.0 |

即 `w(u,p) = max(状态权重) × ratingMultiplier(评分)`。高分增强、低分削弱该用户对该商品的兴趣信号；同用户同商品多评取最高分。

- **作用范围**：仅相似度重建路径（最影响相似度矩阵质量）。`getPersonalized` 的聚合源权重仍为状态权重——它聚合的相似度分数已隐含评分影响，无需重复加权。
- 余弦支持加权是任务 8「选余弦而非 Jaccard」时留的口子，此处兑现。

## 实时客服收尾（第二轮 B）

补齐任务 7 决策 #51 记录的三项遗留。

### B1 接待会话超时自动释放

`job/ChatSessionTimeoutJob`（`@Scheduled(fixedDelay=5min)`）→ `ChatService.autoReleaseOfflineAssignees()`（系统级，不读 SecurityContext）：

```
selectClaimedSessions()  // assignee 非空的会话
for each：
  SISMEMBER cs:online:store:{storeId} {assigneeId}
    在线 → 跳过
    离线 → release(id, assigneeId) 原子释放 → 成功则广播 StoreTopicEvent{RELEASED}
```

## 模拟支付：异步回路与幂等（任务 D）

> 决策与取舍见 `重要决策说明.md` #56。可插拔模拟网关，复刻第三方支付异步回路，未来平滑替换真支付宝。

### 异步回路全流程

```
顾客 POST /api/orders/{orderId}/pay        （initiatePayment，需 CUSTOMER + 订单归属）
  → 校验订单 PENDING_PAYMENT
  → 建 payment 流水（status=PENDING, trade_no=UUID, amount=订单实付额快照）
  → paymentGateway.createPayment → 返回 {tradeNo, payUrl=/api/mock-pay/{tradeNo}, amount}

「模拟收银台」POST /api/mock-pay/{tradeNo}/success|fail   （triggerMockCallback，开放）
  → 查流水（不存在则 404）
  → 构造带 HMAC 签名的回调体
  → paymentCallbackScheduler 延迟 callback-delay-ms(默认1.5s) 后异步调 handleNotify
  → 端点立即返回（真异步：前端需轮询查单）

回调 handleNotify（异步线程 / 也可由真支付宝调 POST /api/payments/notify）
  → verifyCallback（HMAC 验签失败 → 400）
  → 查流水（未知交易 → 404）
  → 流水非 PENDING → 幂等直接返回（已处理过）
  → 金额不一致 → 400
  → advanceStatus 原子推进流水（PENDING→SUCCESS/FAILED）；返回 0 表示并发已处理 → 幂等返回
  → 若 SUCCESS：orderMapper.markPaid 原子置订单 PAID（返回 0 仅记日志：订单已被取消/支付）

前端 GET /api/payments/{tradeNo}            （queryPayment，需登录 + 订单归属）
  → 轮询直至 status 为 SUCCESS / FAILED
```

### HMAC 验签

`util/PaymentSignUtil`（纯函数）：按固定顺序 `amount=&status=&tradeNo=` 拼串后 HMAC-SHA256，hex 输出。`MockPaymentGateway` 用共享密钥（`payment.mock.secret`）验签，防伪造 notify 把订单刷成已支付。模拟支付宝 RSA2 验签的「接入缝」。

### 幂等与并发：两道原子守卫

- **流水守卫**：`PaymentMapper.advanceStatus` —— `UPDATE payment SET status=?,paid_at=? WHERE trade_no=? AND status='PENDING'`。仅 PENDING 可推进，重复/并发回调中只有一条 `affected=1`，其余 0 → 幂等返回。
- **订单守卫**：`OrderMapper.markPaid` —— `UPDATE orders SET status='PAID',paid_at=? WHERE id=? AND status='PENDING_PAYMENT'`。仅待支付订单可置 PAID；订单已被自动取消时 `affected=0`，仅记日志不报错。

两者都在 `handleNotify` 的同一 `@Transactional` 内，先推流水再改订单。

### 不读 SecurityContext 的回调路径

`handleNotify` / `triggerMockCallback` 由异步调度线程与开放 HTTP 端点调用，**不读 SecurityContext**（同 `rebuildAll` / B / E 的教训）。鉴权只放在 REST 路径：`initiatePayment`（`AuthUtil.requireRole(CUSTOMER)` + 订单归属）、`queryPayment`（订单归属，越权查单 → 403）。

### 网关抽象与移除旧同步支付

`service/PaymentGateway` 接口（`createPayment` / `verifyCallback`）+ `MockPaymentGateway` 实现；未来 `AlipayPaymentGateway` 替换实现即可，`PaymentService` 不变。原同步 `OrderService.payOrder`（直接置 PAID）与 `dto/PayOrderResponse` 已移除，`/pay` 改由 `PaymentService.initiatePayment` 发起异步支付。`payment` 表见迁移 `V6__payment.sql`（`trade_no` 唯一幂等键，订单 1:N 流水）。

## AI 语义搜索：outbox 同步与向量检索（AI-1）

> 决策取舍见 `重要决策说明.md` 第 57 条。整体形态：**MySQL 仍是商品真相源，Qdrant 是向量索引，两者用 transactional outbox 解耦**。

### 写入路径（生产者，关键：同一事务）

`ProductServiceImpl` 的 `createProduct` / `updateProduct`（均加 `@Transactional`）/ `deleteProduct`（原已 `@Transactional`）在完成商品写后，调私有 `enqueueIndexEvent(productId, op)` 经 `IndexOutboxMapper.insert` 写一条 `index_outbox` 事件，**与商品写在同一事务内原子提交**：

- create / update → `op = UPSERT`；delete → `op = DELETE`；事件初始 `status = PENDING`、`retry_count = 0`。
- `updateStock` **不入队**（库存不进 embedding 文本，改了也不影响向量）。
- 通义/Qdrant 全挂时商品照样写成功，事件留表等中继补；商品写永不被 AI 链路拖垮。

### 中继路径（消费者，`OutboxRelayJob` `@Scheduled(fixedDelay)`）

`pollAndProcess` 每 `search.outbox.poll-delay-ms`（默认 5s）执行：

1. `IndexOutboxMapper.selectPending(batchSize)` 按 `id` 升序拉一批 `PENDING`；空批直接返回。
2. `vectorIndex.ensureCollection()` 兜底建 collection；**抛异常（Qdrant 不可用）→ 整批跳过、事件留 PENDING 下轮重试**（不计入重试次数）。
3. 逐条 `process(e)`：
   - `DELETE` → `vectorIndex.delete(productId)`。
   - `UPSERT` → `productMapper.selectById`；**商品已不存在/已删 → 退化为 `delete`**（处理「先 UPSERT 后被删」的乱序/补偿）；否则 `embed(buildText(p))` 后 `upsert(id, vec, payload{storeId,categoryId,price,name})`。
   - 成功 → `markDone`；抛异常 → `retry_count+1 ≥ maxRetry`（默认 5）则 `markFailed` 记 `last_error`，否则 `markRetry` 保持 PENDING。

`buildText`：`product` 无描述字段，故 embedding 文本 = 「商品名」+（有类目时）「类目名」（经 `categoryId` 查 `ProductCategory`）。

### 状态机与幂等

`PENDING →（中继成功）→ DONE`；失败且未超限留 `PENDING` 重试；失败超限 `→ FAILED`（待人工 / reindex 修复）。幂等基于 Qdrant 以 `productId` 作 point id：`upsert` 重复覆盖同点、`delete` 重复无副作用；中继「处理成功后、markDone 前」崩溃，下轮重处理同一事件仍得一致结果（至少一次投递安全）。

### 查询路径与降级

`SemanticSearchServiceImpl.search(q, categoryId, minPrice, maxPrice, topK)`：

1. `embeddingClient.embed(q)` → 查询向量。
2. `vectorIndex.search(vec, VectorSearchFilter{categoryId, price∈[min,max]}, topK)`——分类/价格作 Qdrant payload 过滤**下推**（在向量库侧筛，非取回后过滤）。
3. 命中按 `score` 降序拿 `productId` 列表 → `productMapper.selectBatchIds` 批量回表 → **按命中顺序重排**（保住相关性次序），过滤掉已删/缺失商品 → 映射 `ProductListItemResponse`（复用商品列表项结构）。
4. **降级**：embedding / Qdrant 任一抛异常 → 回退 `productService.searchProducts(...)` 关键词搜索，`log.warn` 标记降级。命中为空则返回空列表（不降级）。

### Admin 全量回填

`reindexAll()`：`productMapper.selectList(null)`（逻辑删除自动过滤）给每个未删商品入队一条 `UPSERT`，交同一中继消费，返回入队条数。用于索引初始化 / 灾后重建，复用可靠通路不走旁路；**不读 SecurityContext**（Admin 鉴权在 `SemanticSearchController.reindex` 层）。

### 外部 REST 封装（零新依赖）

`TongyiEmbeddingClient` 与 `QdrantProductVectorIndex` 均用 Spring `RestClient` 直调 REST：通义 DashScope `text-embedding/text-embedding`（解析 `output.embeddings[0].embedding`，校验维度 == 配置 1024），Qdrant `PUT /collections/{c}`、`PUT/POST /collections/{c}/points*`。薄封装不写单测，由集成测试（真实 Qdrant + 桩 embedding）覆盖；`SemanticSearchIntegrationTest` 在 Qdrant 不可达时 `assumeTrue` 优雅跳过。`index_outbox` 表见迁移 `V7__index_outbox.sql`。

## AI 导购问答（RAG）：检索增强生成与 SSE 流式（AI-2）

> 决策取舍见 `重要决策说明.md` 第 58 条。形态：**RAG = 检索（复用 AI-1）+ 增强（构造 prompt）+ 生成（qwen 流式）**，控制器返回 `SseEmitter`，生成结果边收边推。

### 接口与编排

`GET /api/products/qa?q=...&topK=`（开放，`text/event-stream`）。`RagController` 创建 `SseEmitter`（超时 `rag.emitter-timeout-ms`）后立即返回，编排交 `RagService.answer(q, topK, emitter)`：

1. `semanticSearchService.search(q, null, null, null, topK)` 检索 top-K 商品（复用 AI-1，内部含 embedding + Qdrant + 关键词降级）。检索抛异常 → 推 `error` 事件、`complete`。
2. 推 `products` 事件（商品卡 JSON 数组，空也推 `[]`）—— 前端立即渲染卡片。
3. **空结果短路**：products 为空 → 推一句 `answer`（「没找到相关商品…」）+ `done`，**不调 qwen**（省 token）。
4. 否则 `RagPromptBuilder.build(q, products)` 构造 messages，提交到 `ragStreamExecutor` 后台线程：`chatClient.streamChat(messages, delta -> 推 answer 事件)`；正常结束推 `done`，生成抛异常推 `error`。

### SSE 事件协议

`products`（先，商品卡数组）→ `answer`（多次，回答增量 token）→ `done`（末，正常结束）；任一步失败用 `error` 替代。先推 products 后推 answer，用户「秒看到商品、再看到逐字推荐」；后台线程推流，主线程不阻塞容器请求线程。

### Prompt 与严格 grounding

`RagPromptBuilder` 产出 `[system, user]`：system 是固定的导购人设 + 约束「**只能**根据候选商品推荐、**不得编造**清单外商品」；user = 用户问题 + 候选商品紧凑文本（带序号，至多 `rag.context-size` 条）。grounding 全靠 system 约束 + 只喂检索结果（不喂全库），防幻觉推荐不存在的商品。

### qwen 流式解析（QwenChatClient）

`ChatCompletionClient` 抽象（呼应 `EmbeddingClient`/`PaymentGateway`），`QwenChatClient` 实现：`RestClient.exchange` 以 `stream=true` 调 qwen DashScope 兼容端点 `/chat/completions`，`consumeStream` 逐行读 `data: {chunk}`——`extractDelta` 取 `choices[0].delta.content` 经 `onDelta` 回调吐出，遇 `data: [DONE]` 终止。非 2xx 抛异常。`consumeStream`/`extractDelta` 为包级方法、单测覆盖（喂样例 chunk 串）；真实 qwen 调用不进自动化测试。

### 关键设计

- **检索一份数据两用**：`List<ProductListItemResponse>` 既作 `products` 商品卡，又作 LLM 上下文。
- **后台 executor 不读 SecurityContext**：开放接口 + 系统线程；qwen key 复用 `DASHSCOPE_API_KEY`。
- **可插拔生成**：OpenAI 兼容，切 DeepSeek 仅改 `rag.qwen.base-url`/`model`/`api-key`。
- **零新增 Maven 依赖、无数据库迁移**：`RestClient` + `SseEmitter`。

### 本地联调与验证（真实 embedding，2026-06-27）

**前置**：Qdrant 在跑（容器名 `qdrant`，`SessionStart` 钩子自动 `docker start`）、MySQL/Redis 在跑、应用启动时注入 `DASHSCOPE_API_KEY`。

**embedding key 与端点结论**：使用阿里百炼 workspace API key（`sk-ws-…`）。实测该 key 在**公网** DashScope 端点 `https://dashscope.aliyuncs.com/api/v1/services/embeddings/text-embedding/text-embedding` 上即可调通 `text-embedding-v3`（返回 1024 维），**无需**改用 CSV 里给的专属部署地址、也无需覆盖 `TONGYI_EMBEDDING_URL`——只设 `DASHSCOPE_API_KEY` 即可。

**测试步骤**：① 启动应用（注入 key）→ ② 管理员（`13000000000`）登录拿 token → `POST /api/admin/products/reindex` 给 14 个种子商品入队 UPSERT → ③ 等中继（每 5s）embed+upsert 完，Qdrant `products` collection points=14 → ④ 调开放接口 `GET /api/products/semantic?q=...` 查。

**验证结果**（查询词均**不出现**在商品名中，纯靠语义召回，topK=3）：

| 自然语言查询 | Top 命中（品类） |
|---|---|
| 做饭用的调味料 | 特级初榨橄榄油（调味品）/ 古法酿造生抽酱油（调味品） |
| 夏天解渴的饮料 | 蓝鲸气泡水（饮料）/ 冷萃黑咖啡（饮料） |
| 送朋友的健康礼物 | 每日坚果（零食）/ 手工饼干（零食） |
| 耳机（目录中无耳机） | 65W 充电器（数码）/ 摄像头（数码）——返回语义最近的同类数码品，非空 |

结论：语义检索能召回名称无字面匹配但语义相关的商品（关键词搜索做不到），且无精确匹配时返回最近邻而非空结果。
