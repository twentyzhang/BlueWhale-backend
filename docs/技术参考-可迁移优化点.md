> 标记含义：✅ 已排入对应轮次 / 🔜 强烈建议、自成一轮 / 🔭 远期（重型基础设施） / ⚠️ 按本项目规模属过度设计。

## 参考项目概述

- **形态**：知识社区 APP（发布知识、点赞/收藏、关注、首页 Feed、对象存储直传、AI 摘要、RAG 问答、搜索），冲高并发高可用。
- **技术栈**：Java 21 + Spring Boot + Spring Security + Spring AI + MyBatis + MySQL + Redis + Kafka + Caffeine + 阿里云 OSS + Canal + Elasticsearch + RAG；前端 React + Vite。

---

## 八大系统 → 本项目映射

### 1. 认证系统：RS256 双令牌 + Redis 白名单 + 即时撤销 ✅（第二轮 E）
- **原项目**：15min access + 7d refresh，RS256 签名，刷新令牌白名单，支持即时令牌撤销。
- **本项目现状**：已有双令牌（access 24h + refresh 7d 轮换，存 Redis）。
- **可学/可迁移**：①**即时令牌撤销**（退出登录 / 改密让旧 token 立刻失效，access 用 jti 黑名单或版本号）；②缩短 access 到 15min；③RS256 非对称签名（私钥签、公钥验）。
- **判定**：✅ 已排入**第二轮 E（认证增强）**。属增量增强，基础设施零新增。

### 2. 计数系统：定制 Redis SDS 二进制紧凑计数 + Lua 原子 + 采样校验 + 自愈重建 ⚠️
- **原项目**：笔记维度(点赞收藏)/用户维度(关注)以 Redis 为底层，二进制紧凑计数 + Lua 原子更新 + 一致性采样校验 + 自愈重建。
- **本项目对应**：商品销量、收藏数、券剩余量等计数。
- **可学/可迁移**：「Redis 计数 + Lua 原子 + 从 DB 自愈重建」这套**最终一致计数**思路有价值。
- **判定**：⚠️ **SDS 二进制紧凑计数**对本项目规模是过度设计；如需，仅取 light 版（普通 Redis 计数 + Lua + DB 重建），可在做「关注店铺 / 商品收藏」时顺带。

### 3. 发布系统：OSS 预签名 + 前端直传 + AI 摘要 🔜（建议下一轮）
- **原项目**：图片/视频/Markdown 存 OSS，后端发预签名 URL、前端直传，省传输资源；接入 AI 一键生成摘要。
- **本项目对应**：商品图片 / 评论图片 / 店铺 logo（现在 `imageUrl` 只是字符串，无真实上传）。
- **可学/可迁移**：**预签名直传模式**（后端签名 → 前端直传对象存储，不经后端中转）。本机用 **MinIO**（S3 兼容，Docker 起，免云账号）即可完整复刻。AI 摘要可作为商品描述/评论摘要的可选小功能。
- **判定**：🔜 **下一轮**优先候选（独立子系统，基础设施轻——MinIO 本地化）。

### 4. 用户关系系统：关注/取关，一主多从 + Outbox + Canal binlog → Kafka 🔭
- **原项目**：关注事件同事务写「关注表 + Outbox 表」，Canal 订阅 Outbox 的 binlog 发到 Kafka，异步更新粉丝表/计数/列表缓存等「伪从」。
- **本项目对应**：「关注店铺 / 收藏商品」功能。
- **可学/可迁移**：**Outbox 事务发件箱**模式（解决「写库 + 发消息」的双写一致性）很经典、值得学。
- **判定**：🔭 远期。**Canal + Kafka 太重**；若想学事件驱动，做「关注店铺」时用**轻量 Outbox（Outbox 表 + 定时轮询发布，不上 Canal/Kafka）**即可拿到核心模式。

### 5. 点赞系统：Kafka 异步写 + 写聚合 + 分片位图幂等 + 按需重建 + 灾难回放 🔭
- **原项目**：高并发写用 Kafka 异步写 + 写聚合；位图结构做幂等判重；读时缺失按位图重建；Kafka 做灾难回放兜底。
- **本项目对应**：商品收藏 / 评论点赞。
- **可学/可迁移**：**Redis 位图做幂等判重**（如「用户是否已收藏某商品」）是 light 可借鉴点。
- **判定**：🔭 远期。**Kafka 异步写聚合**是为高并发写设计，本项目无此场景；位图幂等可在做收藏功能时 light 引入。

### 6. Feed 三级缓存 + hotkey 探测 + single-flight ✅（第二轮 F）+ 🔜（hotkey 进阶）
- **原项目**：Caffeine 本地 + Redis 页面缓存 + Redis 片段缓存三级；自定义 hotkey 探测，按热度分层延长 TTL + 随机抖动抗雪崩；single-flight 锁避免同页并发回源风暴。
- **本项目现状**：已有 Redis 缓存（任务3，含 TTL 抖动防雪崩）+ 推荐多级缓存（MySQL+Redis）。
- **可学/可迁移**：①**single-flight 单飞锁**（防缓存击穿——当前 `CacheUtil` 并发未命中会一起打 DB）；②**Caffeine 本地 L1**（叠加成三级缓存）；③hotkey 热点探测（进阶）。
- **判定**：✅ single-flight + Caffeine L1 已排入**第二轮 F（缓存增强）**；hotkey 探测 🔜 后续进阶。

### 7. AI 问答 RAG：索引检查 → 向量检索 → Prompt 构造 → 流式生成 🔭
- **原项目**：围绕单篇知文的 RAG 问答，合理分块 + 幂等删除保持单一版本 + 预索引降低首问延迟 + 流式生成。
- **本项目对应**：**AI 客服**（可与现有实时客服结合）/ 商品智能问答。
- **可学/可迁移**：RAG 全流程（分块、向量检索、Prompt、流式）。
- **判定**：🔭 独立大项目（需向量库 + LLM）。是「实时客服」之上很自然的升级方向，自成一轮。

### 8. 搜索系统：Elasticsearch search_after + function_score + completion suggester 🔜（独立一轮）
- **原项目**：ES 内容搜索 + 联想；`search_after` 游标深分页；`function_score` 融合 BM25 相关性与点赞等业务权重；`completion suggester` 低延迟前缀联想。
- **本项目现状**：商品搜索是 MySQL `LIKE`（关键词 + 分类 + 价格区间）。
- **可学/可迁移**：相关性排序融合业务权重（销量/评分）、`search_after` 深分页、前缀联想——**全部直接适用于商品搜索**。
- **判定**：🔜 **独立一轮**。电商搜索是核心、价值极高，但 ES 是重型件，值得专注一轮。
